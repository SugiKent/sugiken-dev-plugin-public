# テストを速くする

ゴールは「GitHub Actions 上で、テストが同じ結果のまま、より短い wall time で終わること」。手元の速さは参考値で、採否は GitHub Actions の計測で決める。

このスキルは手法を指定しない。どこを見れば速くする手立てが見つかりやすいかだけを渡す。手立ては対象プロジェクトの言語・フレームワーク・テストの性質を読んで自分で選ぶ。

## 進め方

計測 → 仮説 → 検証 → 修正 を 1 周とし、1 周で変えるのは 1 つだけにする。複数を同時に変えると、どれが効いたか・どれが悪化させたかを切り分けられない。

### 1. 計測（ベースライン）

改善の前に、今の姿を数字で残す。

* **対象環境を確かめる。** ワークフローの `runs-on` と、runner 上の `nproc`・空きメモリをログに出して確認する。GitHub-hosted の標準 Linux runner は、public repo と private repo で vCPU・メモリが異なる（目安: public 4 vCPU / 16 GB、private 2 vCPU / 8 GB。正本は [GitHub の runner 仕様](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)）。手元マシンの最適値はそのまま持ち込めない。
* **ジョブ全体を分解する。** checkout・依存インストール・ビルド・サービス起動・テスト本体・後処理のそれぞれにかかる時間を step 単位で見る。テスト本体以外が支配的なら、テストの中を触っても効かない。
* **テスト本体を分解する。** ファイル単位・テスト単位の所要時間を出す。各テストランナーの duration 出力・レポーター・JUnit XML などで取れる。あわせて、起動・収集・ワーカー立ち上げなど、テストが 1 つも走っていない時間も見る。
* **資源の使われ方を見る。** テスト実行中の CPU 使用率・メモリ使用量・スワップ・I/O 待ちを記録する。wall time と、全ワーカーの CPU time 合計の比から、コアが遊んでいるのか飽和しているのかが分かる。
* **ばらつきを測る。** 同じコミットで複数回（最低 3 回）走らせ、中央値と幅を記録する。差がばらつきの幅に収まる変更は、効果ありと判断しない。

計測結果は、後で比較できる形（表など）で残す。

### 2. 仮説を立てる

計測結果から「ここを変えれば短くなるはず」を立てる。2 つの角度から見ると、手立てが見つかりやすい。

**具体的な角度: 遅いテストを特定する**

所要時間の上位から順に、1 本ずつ「なぜこの時間がかかるのか」を読む。注目点:

* そのテストは、時間の大半を何に使っているか（計算・待機・I/O・外部呼び出し・準備）。
* 時間の経過そのものを待っていないか。固定の待ち時間や長いタイムアウトは、成功時にも払われる。
* 検証したい振る舞いに対して、準備しているものが大きすぎないか。
* 本来そのレイヤーで確かめる必要のない経路まで通していないか。
* 並列実行時、最も長いファイル 1 本が全体の終了時刻を決めていないか（末尾の待ち）。
* 失敗とリトライを繰り返していないか。不安定なテストは、その分だけ時間を食う。

**抽象的な角度: 遅い共通処理を特定する**

個々のテストは速くても、全テストが払っている共通コストが積み上がっていないかを見る。注目点:

* テストごと・ファイルごと・ワーカーごとに繰り返されている準備と後始末は何か。その単位で繰り返す必要が本当にあるか。
* 共通のセットアップ・フィクスチャ・ヘルパーのうち、一部のテストしか必要としないものを全員が払っていないか。
* 起動時の読み込み・変換・コンパイル・モジュール解決など、テストの中身と関係なく毎回かかる時間はどれだけか。
* 隔離（プロセス・環境・データ）の粒度は、テストが実際に必要とする粒度と釣り合っているか。
* 実行のたびに作り直しているもののうち、前回の結果を再利用できるものはないか。
* 変更と無関係なテストまで毎回すべて走らせていないか。

**資源の角度: CPU・メモリの制約に合わせる**

* CPU が遊んでいるなら、並列度が足りないか、待機で詰まっている。CPU が張り付いているなら、並列度を上げても速くならない。
* メモリが逼迫している・スワップしているなら、並列度を上げると逆に遅くなる。ワーカー 1 つあたりの消費量 × ワーカー数 が上限を超えない範囲を探す。
* I/O 待ちが多いテストは、コア数より多い並列度が効くことがある。計算が重いテストは効かない。
* 1 台の runner で足りないなら、複数ジョブへの分割も候補になる。ただし分割するとジョブごとの固定コスト（checkout・インストール・起動）が増え、課金時間も増える。

仮説は「何を変えると、計測のどの数字が、どれくらい変わるはずか」まで書く。期待値を先に書かないと、検証で外れたことに気付けない。

### 3. 検証

* 仮説を、修正の前に安く確かめる。該当テストだけを走らせる、共通処理だけの時間を測る、並列度を何段階か変えて走らせる、など。
* 並列度・ワーカー数のような数値は、1 点で決めずに複数の値（たとえば vCPU 数の 0.5 倍・1 倍・1.5 倍・2 倍）を GitHub Actions 上で比べ、最速点を探す。手元の結果では決めない。
* 効果がばらつきの幅に収まるなら、その仮説は捨てて次へ進む。

### 4. 修正

* 検証で効果が確認できたものだけを入れる。
* テストが守っている振る舞いを弱めない。速くするために検証を削る・テストをスキップする・アサーションを緩めるのは改善ではない。削るべきテストかどうかは `architect:35-architect-test-audit` の基準で別途判断する。
* 速くなっても、並列化や共有化でテスト間の依存が生まれ、実行順で結果が変わるようになっていないか確かめる。順序を変えて複数回走らせ、結果が安定していることを見る。

### 5. 再計測

修正後、ベースラインと同じ条件（同じ runner・同じ回数）で GitHub Actions 上で計測し、表に追記する。次の周回は、新しい計測結果の上位から仮説を立て直す。

## 完了条件

* ベースラインと改善後の GitHub Actions 上の計測値（中央値とばらつき）が、同じ表に並んでいる。
* 入れた変更それぞれに、どの数字がどれだけ変わったかが対応付いている。
* テストの合否結果と件数が、改善前後で変わっていない（意図して変えた場合はその理由が書かれている）。
* 効果がなかった仮説も、捨てた理由と一緒に残っている。次に同じ道を通らないため。

## 報告の形

```markdown
## 環境
runner: <label> / vCPU: <n> / メモリ: <GB>

## 計測結果
| 構成 | wall time 中央値 | 幅 | CPU 使用率 | 最大メモリ | 備考 |
| --- | --- | --- | --- | --- | --- |
| ベースライン | | | | | |
| 変更 1: ... | | | | | |

## 採用した変更
- 変更内容 / 根拠となった仮説 / 効果

## 捨てた仮説
- 仮説 / 検証結果 / 捨てた理由

## 次に見るべき候補
```

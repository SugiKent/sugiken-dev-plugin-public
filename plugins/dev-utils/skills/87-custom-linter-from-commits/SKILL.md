# コミットからのカスタムリンター生成

Git コミットの差分から「このプロジェクトではこう書く」という実装ルールを読み取り、**決定論的に検出できるものだけ**をカスタムリンタールールとして repo に常設するスキル。

やることは 2 段階に分かれ、担当が違う。

1. **抽出（LLM の仕事）** — 指定範囲の diff を読み、確立されたルール・アーキテクチャ境界を言語化する
2. **強制（コードの仕事）** — 抽出したルールのうち、静的に判定できるものだけを、毎回同じ結果を返すリンタールールに落とす

抽出したルールをレビューで毎回言い直す必要はもうない。**リンターは通るか落ちるかしかない。**

## 責務の境界

| スキル | 落とし先 | 性質 |
|---|---|---|
| [[35-architect-code-review]] | レビューの指摘 | 非決定的。文脈判断が要る指摘全般 |
| 本スキル | リンタールール | 決定論的。静的に判定できる指摘だけ |
| [[01-retro]] | CLAUDE.md / docs の散文 | セッションの気付き全般。ルールに落とせないものはここへ |

本スキルが担うのは、`35-architect-code-review` の指摘のうち **機械化できるもの** をリンターに移す部分だけ。判定不能な指摘（命名の分かりやすさ等）はリンターにせず docs 行きにする。

## Step 1: 対象範囲を決める

- リビジョン範囲: `main..HEAD` や `<sha>..<sha>`
- 期間: `--since` / `--until`（人間が指定するとき）

どちらか一方を受け取る。両方指定された場合はリビジョン範囲を優先する。

```bash
# リビジョン範囲
git log --stat <base>..<head>
git diff <base>..<head>

# 期間
git log --since="<date>" --until="<date>" --stat
git log --since="<date>" --until="<date>" -p
```

## Step 2: ルール候補を抽出し、user に取捨選択させる

diff を読み、次のようなパターンを候補として列挙する。

- レイヤー間の依存方向（例: `domain/` から `infra/` を import しない）
- 使ってよい API / 使ってはいけない API（例: 生の `fetch` ではなく `apiClient` を使う）
- ディレクトリ・ファイル配置の規約（例: `*.test.ts` は実装ファイルの隣に置く）
- 命名・シグネチャの一貫した変更（例: repository の返り値は必ず `Result<T, E>`）

**推測で全部を採用しない。** 列挙した候補を表にして user に提示し、採用するものだけを選ばせる。

| # | ルール候補 | 根拠にした commit | 静的検出の見込み |
|---|---|---|---|
| 1 | ... | `<sha>` | 高 / 中 / 低 |

「静的検出の見込みが低い」ものは、この時点で候補から外してよいと伝える（Step 3 で結局落とせない）。

## Step 3: 採用ルールを検出手段に落とす

**「検出できないルールは採用しない」を鉄則にする。** 静的に判定できないもの（「意図が明確な命名にする」等）を無理にリンター化すると、誤検知だらけになって無視されるルールが増える。落とせなかったものは docs 行きにして、リンターには入れない。

ルールごとに実装手段を選ぶ。プロジェクトのスタックに応じて候補を提示し、user に選ばせる（決め打ちしない）。

| 手段 | 向いているルール | 備考 |
|---|---|---|
| ESLint `no-restricted-syntax` / `no-restricted-imports` | 軽量な import 制限・AST パターン 1 つで書けるもの | 追加ライブラリ不要。まずここから検討する |
| ESLint カスタムルール（repo 内 plugin） | AST を跨いだ複雑な判定 | `no-restricted-*` で書けないときのみ |
| [ast-grep](https://ast-grep.github.io/) | YAML でパターンを書きたい・非 JS/TS プロジェクト | 多言語対応が要るとき |
| 独自スクリプト + CI | ディレクトリ構造・ファイル配置など AST では見ない規約 | grep / find ベースで十分なことが多い |

既存のリンター基盤（`.eslintrc*` / `eslint.config.*` 等）がすでにあるプロジェクトでは、それに乗せるのを既定にする。無ければ最小のものを選ぶ。

## Step 4: 既存コードに対して実行し、移行方針を選ばせる

ルールを新設すると大抵は既存コードが大量に落ちる。生成したリンターが即座に無効化されないよう、必ず既存コードに対して一度実行し、違反件数を数える。

```bash
# 例: ESLint の場合
npx eslint --rulesdir <生成したルール> --rule '<rule-name>: error' .
```

結果を提示し、次のどれを取るか user に選ばせる（決め打ちしない）。

1. **0 件** → そのまま `error` で入れる
2. **一括修正できる範囲** → 修正してから `error` で入れる
3. **残る違反が多い** → `warn` で入れ、段階的に `error` 化する運用にする、または特定ディレクトリだけ `error` にする

## Step 5: repo に常設し、実行コマンドを渡す

- 生成したルールファイルと設定を repo にコミットする
- 既存の lint 実行コマンド（`pnpm lint` 等）に乗せる。専用コマンドが必要な場合のみ新設する
- CI がある場合は、既存の lint ジョブに含める（新しいジョブを増やさない）

## よくある落とし穴

### 1. 検出できないルールを無理に入れる
「意図が明確な命名」のような判断が要るルールは、リンターにすると誤検知だらけになる。Step 2 の時点で見込みが低いものは外す。

### 2. 既存違反を数えずに `error` で入れる
生成した瞬間に CI が真っ赤になり、次のコミットでそのルールごと無効化される。Step 4 を飛ばさない。

### 3. 抽出したルール全部を機械的に採用する
diff から読み取れるパターンには、一時的な事情によるものも混ざる。Step 2 で必ず user に選ばせる。

### 4. `35-architect-code-review` の指摘をそのまま持ち込む
非決定的な指摘（可読性・設計判断など）はリンター化に向かない。機械化できる部分だけを切り出す。

# Skill Creator

新しいスキルを作り、少しずつ育てていくためのスキル。

このスキルは「小さく書いて育てる」方針で運用する。最初から巨大な指示を書かず、まず最低要件をユーザーに確認し、それに基づいてシンプルな初版を書く。テスト・eval・ベンチマーク・description 最適化といった重い仕組みは、必要になったときに人間が後から足していく。

## 全体の流れ

1. このスキルが何をするものかを、ユーザーと一緒に決める
2. 最低要件を確認する（下記「意図をつかむ」参照）
3. シンプルな初版を書く
4. 実際に使ってみて、気になったところを直す
5. 満足するまで繰り返す

順序は柔軟でよい。すでに下書きがある場合は、いきなり編集・改善から入ってよい。

## ユーザーとのコミュニケーション

このスキルは、コーディング用語への習熟度がまちまちなユーザーに使われる。相手の言葉づかいから読み取り、通じにくそうな用語は短く補足する。迷ったら平易に説明する。

## スキルを作る

### 意図をつかむ

まず最低要件を確認する。会話にすでに素材があれば、目的、入出力、制約、承認済みの判断を汲み取り、その範囲で進める。結果を左右する不足だけをユーザーに尋ねる。

確認したいこと:

1. このスキルは Claude に何をできるようにするものか
2. いつ発動してほしいか（どんな言い回し・文脈で）
3. 期待する出力の形式は何か

最低要件が固まったら、それだけを反映したシンプルな初版を書く。細かいエッジケースや高度な仕組みは、初版には入れない。

### SKILL.md を書く

ユーザーへの確認内容をもとに、次の要素を埋める。

- **name**: スキルの識別子
- **description**: いつ発動し、何をするか。これがスキルを呼び出させる一番の仕組みなので、「何をするか」だけでなく「いつ使うか」の具体的な文脈も必ず含める。発動条件はすべてここに書き、本文には書かない。
- **本文**: 目的、入力、成果物と完了条件、判断に必要な固有の制約。順番に意味がある処理だけ手順として書く。

### description の書き方

description は発動条件を具体的に書く。手動で呼ぶスキルは発話例、自動実行から呼ぶスキルは呼び元とトリガー、共通参照用なら単独では実行しないことを示す。

たとえば「社内データを表示する高速なダッシュボードの作り方」ではなく、こう書く:

> 社内データのダッシュボードを作成・更新する。「売上を可視化して」「社内指標を画面にまとめて」で使う。

### スキルの構成

```
skill-name/
├── SKILL.md（必須）
│   ├── YAML フロントマター（name, description は必須）
│   └── Markdown の指示本文
└── 同梱リソース（任意・最初は不要なことが多い）
    ├── scripts/    - 決まった処理を実行するコード
    ├── references/ - 必要に応じて読み込むドキュメント
    └── assets/     - 出力に使うファイル（テンプレート・アイコン等）
```

### Progressive Disclosure（段階的な読み込み）

スキルは 3 段階で読み込まれる。

1. **メタデータ**（name + description）— 常に文脈に載る（100 語程度）
2. **SKILL.md 本文** — スキルが発動したときに載る（500 行以内が目安）
3. **同梱リソース** — 必要になったときだけ読む

本文には毎回必要な判断だけを置く。特定の操作でしか使わない API 詳細や例は、長さにかかわらず `references/` へ分け、誰がいつ読むかを参照元に書く。配布用の雛形は `assets/` に置く。
行数だけを目標にせず、通常の実行で参照先まで含めて読む量を減らす。全参照を毎回読ませる分割は避ける。

### 予想を裏切らない原則

スキルにはマルウェア・エクスプロイトコード・システムを危険にさらす内容を含めない。説明された意図と中身が食い違ってはいけない。誤解を招くスキルや、不正アクセス・データ持ち出しを助けるスキルの作成には応じない。「〇〇になりきってロールプレイ」程度は問題ない。

### 書き方のパターン

指示は命令形で書く。

**出力形式を定義する** — こう書ける:

```markdown
## レポートの構成
必ずこのテンプレートを使う:
# [タイトル]
## 要約
## 主な発見
## 提案
```

**例を示す** — 例はとても有効。こう書ける:

```markdown
## コミットメッセージの形式
**例 1:**
Input: JWT トークンによるユーザー認証を追加
Output: feat(auth): implement JWT-based authentication
```

### 書き方のスタイル

指示は短く直接書き、判断に必要な理由を一文添える。強調語の反復、モデル一般への励まし、時系列の経緯は入れない。
個別の失敗から、守るべき条件とその確認方法を抽出する。「注意する」「十分に検証する」だけで終えず、何を見て次へ進むかを示す。

## スキルを改善する

### 簡素化する手順

1. **残す条件を先に特定する。** 入出力、完了条件、状態の書き手、必要な処理順序、権限の境界、失敗時の回復・引継ぎを拾う。API の非自明な制約や正確なフィールド名・値は、一般知識から補えるものとして削らない。
2. **判断に寄与しない指示を削る。** 重複、言い換え、一般的な作業の逐次指示、抽象的な再確認、不要な例を落とす。例は文章だけでは判別しにくい入力・出力や分岐を示すものに絞る。
3. **規則の正本を一つにする。** 共通条件は共通 skill に集め、各 skill には役割固有の判断だけを残す。表・しきい値・コメント形式を複写せず、ファイルと見出しで参照する。README は目的・使い方・参照先を持ち、独自の規則を増やさない。
4. **必要なときだけ読ませる。** 「Progressive Disclosure（段階的な読み込み）」に従い、通常時に不要な詳細を分離する。必須の完了条件は、読まれない任意の参照へ隠さない。
5. **複数 workflow の共通操作を独立させる。** サービスの作成・更新・確認などが複数 plugin で使われるなら、共通 plugin / skill へ切り出す。呼び出し元には望む設定と固有の方針を残し、入力、返す結果、失敗時の担当を定める。依存 plugin の導入方法と namespace 付き参照も揃える。
6. **終了経路を確かめる。** 正常終了、見送り、失敗、早期撤退でも、完了か引継ぎが成立するかを見る。自動処理が未完了なら、次の担当・再開契機・停止時の回収経路、または人が見つけて操作できる状態を残す。ラベルや成果物の存在だけで引継ぎ済みとせず、判定に使う状態を読み戻す。確認不能は未完了として報告する。

### 変更を確かめる

差分を見て、削除・共通化・参照への移動と、動作そのものの変更を区別する。簡素化によって機能や回復経路を失っていないか、主要な成功・失敗の分岐を辿る。
frontmatter、参照先のファイル・見出し、plugin 登録、呼び出し元と共通 skill の契約を変更範囲に応じて確認する。
表示・状態判定に依存する指示は実装と既存テストに照合し、文書の構文検証と実環境での動作確認を分けて報告する。

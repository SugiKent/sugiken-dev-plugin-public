# 機能

**設計の責任は自分が持つ。計画し、レビューし、確かめる。** 実装は委任してよいが、主導は手放さない。

1. 触るサブシステムを `investigation.md` の「仕組みを説明する」で掴む。
2. `architect:35-architect-sketch` で設計を並行に探る。
3. スループット点検を 4 つの todo として書く。当てはまらない観点（1 ファイルだけ、並行作業なし）も項目を消さず、`該当なし: <理由>` を書いて残す。
   - **先に塞ぐ手順。** 並行に広げる前に通す関門。
   - **独立した作業の流れ。** 互いに素なファイル・サービス・層は並行にできる。共有する書き込みは直列にする。
   - **書き換え可能な共有状態。** 既定では書き込み先を分ける（Separate Before Serializing Shared State）。直列にするのは本当の不変条件があるときだけ。
   - **安全な最小の分け方。** 1 人で作るのが最善なら、その理由を名指しする。
4. コードを書く作業をサブエージェントに委任するときは、範囲を具体的に渡す。ファイルのパス、名指ししたデータの形とそれをまとめる構造（Model the Domain に従い、散らばった真偽値より状態機械、分岐より表や登録簿、繰り返す形の前提より型付きのモデル。委任先がロジックを書く前に決める）、成功の条件。実装に正しい形が複数ある（エラー処理、抽象の層、テストの構造）なら、`35-architect-sketch` の Phase B の競作で委任し、候補に別案を出させ、相互審査に選択を守らせる。この委任は飛ばさない。Laziness Protocol もこれを覆さない（ここで得るのはレビューの分離で、行数の節約は目的にしていないため）。サブエージェントを起動できない立場なら、同じレビューの分離を保って自分で差分を持つ。入れ子のエージェントを待つだけの「待機中」の返答はしない。コメントは poteto-mode の「コメント」に従う。編集は外科的に行い、上流から派生したファイルは元に照らして直す。共有の部品を改善したら、すべての利用側へ移して、それぞれ確かめる。こまめにコミットする。
5. 変更した面で確かめる。「INCONCLUSIVE」や別の面での確認は合格ではない。そう明記する。
6. 小さく順序立ったコミットに整える。後続の作業は積み重ねる。Sequence Work into Verifiable Units に従い、小さな単位ごとに作り、確かめ、コミットを済ませてから次へ進む。
7. 設計に異論があるなら、出荷前に `architect:35-architect-interrogate` を回す。
8. コミットと PR は、リポジトリとハーネスの規則に従う（`basic:20-commit-meaningful-diffs`）。

コードで結合した作業（1 つの機能、1 つの移行）は、点検を内に持った 1 人の持ち主に渡す。その持ち主が、先に塞ぐ段階の後で内部的に並行に広げる。親の段階で並行に広げるのは、独立した成果物を生む断面（監査、サブシステムをまたぐ調査、競合する実験）だけ。段階の区切りで点検を書き直す。割り込みをつなぐより、新しい持ち主を起動する。

**返答。** 作ったもの、選んだものとその理由、スループット点検、未決の判断。設計の代替案は表にする。

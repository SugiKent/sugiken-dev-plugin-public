# 型が合わない大きな作業（figure-it-out）

どの作業の型にも合わないとき、その作業専用の型を設計する。コードの前に出す成果物は手順そのもの。作業に見合った厳密さに調整した段階の列で、科学的な方法で回し、人間が離席した後で監査できる判断の記録を残す。

最初に、poteto-mode の「原則」を読むことをタスクリストの 1 項目目に置く。次に、下の段階を todo として足す。

## Phase A: 枠を決める

先に足場を固めてから、取り組むと決める。次を言えるまで走り出さない。

- 合否を判定できる完了条件（Prove It Works）。
- 量で表した範囲。おおよその単位数と工数、足場固めで見つかった障害。
- 厳密さの水準。高めに寄せる。一方通行の扉と、影響範囲の大きい作業はさらに上げる。可逆で低リスクの手順は下げる。厳密さとは関門と成果物のことで、「もっと頑張る」ことではない。

長い作業に取り組む前に、枠とトレードオフを示す。可逆な作業は進める（Never Block on the Human）。ただし数時間の作業には一度だけ確認点を置く。

## Phase B: 手順を設計する

独立して取り込める最小の単位に分ける。いちばん危ない未知を先に並べる。足場と検証を機能より先にする（Foundational Thinking）。

- 作業の前に検証の仕組みを作り、変更前の状態から基準値を取っておく。確認が「古い値と新しい値」の比較として読めるようにする。
- 一方通行の扉になる設計判断には `architect:35-architect-sketch` を回す。形が既に具体的な機械的作業では飛ばす。決まった設計に 2 回目の競作をするのは作り込みすぎ（Laziness Protocol）。
- 何を並行に広げるかを決める。並行にするのは継ぎ目に沿ってだけで、ワーカーごとに worktree かブランチを分ける（Separate Before Serializing Shared State）。広げすぎない。
- 設計した段階の一覧を書き出す。人間がレビューするのはその一覧。

それから設計を実行する。設計の手順を、Phase C と Phase D の間に具体的な項目としてタスクリストへ足す。各手順を Phase C のループの規律で回し、Phase D の記録は最後にまとめず、手順が終わるたびに 1 行ずつ書く。

## Phase C: ループを回す

各単位を一つの実験として扱う。仮説を述べ、最小の変更をし、実物で完了条件と照らして測り、前に進んだなら残し、進まなかったなら戻す。Sequence Work into Verifiable Units に従い、検証をまとめて最後にせず、各単位を確かめてから次に入る。

- 自己申告を信じず、成果物を見て確かめる。あまりに簡単に通ったら、システムより先に観察の方法を疑う。
- 委任した作業には審査役を組にする。ワーカーが関門をすり抜けたら、やり直して約束を固くする。関門そのものが誤っているなら、迂回せず、関門を別の変更で直す。
- 判定は VERIFIED、NOT VERIFIED、INCONCLUSIVE のどれか。INCONCLUSIVE は合格ではない。否定的な結果を隠さない。

## Phase D: 監査の記録を残す

`../decision-trail.md` で記録する。この型の作業はたいてい大きいので、記録をコミットし、レビュアーが PR の中で読めるようにする。記録と差分が揃って、人間は戻ってきたときに作業を信頼できる。

## Phase E: 確かめて返す

全体を、検証の仕組みに加えて実際の製品でも、Phase A の完了条件と照らして確かめる。繰り返す指摘は、関門・lint・検査・スクリプトにする（Encode Lessons in Structure）。

**返答。** 返答には、設計した型、厳密さの水準とその理由、判断の記録のパス、完了条件に照らして確かめたこと、まだ開いていることを書く。

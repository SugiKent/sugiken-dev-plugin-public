# Experience First（体験を先に）

製品・UX・機能範囲のトレードオフが出たときに当てる。実装の都合より利用者の喜びを取る。荒い機能をたくさん出すより、磨いた機能を少なく出す。

実装の都合と利用者の喜びがぶつかったら、喜びを取る。

- 機能、操作、選択肢のどれも、ある理由を説明できなければならない。
- 少なく出し、よく出す（磨いた 3 機能は、荒い 10 機能に勝つ）。
- 作り込む前に試作する（設計の判断は、本番コードより使い捨ての HTML のほうが安い）。
- 細部を正す（遷移、揃え、余白、反応、エラー状態）。
- 中心の流れを締める（どの機能も中心の作業に仕えるか、邪魔をしない）。

利用者とは、その仕事を受け取る人すべて。UI ならエンドユーザーが、ライブラリや内部 API なら import する同僚が利用者になる。次にそのコードを保守するエンジニアも利用者になる。その人たちの体験も同じ重さで量り、影響はその人の目線で説明する。

土台は体験に仕える。[Foundational Thinking](foundational-thinking.md) は作業の順序を決め、この原則は目標を決める。

# Model the Domain（ドメインを構造で表す）

状態を持つロジックを書くとき、分岐が多いコードや、同じ形の前提を複数ファイルで繰り返すコードに当てる。

実際のドメインを、条件分岐に散らさずデータ構造で表す。ドメインに合う構造は、不正な状態を表現できなくし、分岐を消す。書くときに選べば安い。後から取り戻そうとすると、その作業はリファクタリングに見え、後回しにされる。

手に取るもの。

- 散らばった真偽値・フェーズ・ライフサイクルの検査を、状態機械にする。
- ばらばらの引数や、繰り返される形の前提を、型付きのモデルにする。
- ファイルをまたいで広がる分岐を、map・登録簿・参照表・判別可能な union にする。
- 場当たりの状態変更を、reducer やコマンド・イベントのモデルにする。
- 読み込み・検証・変換・保存のような処理の順番で分けたモジュールを、1 つのドメイン知識の周りにまとめ直す。実行の順番は所有の単位にならない。
- 繰り返される振る舞い、所有、不変条件を、小さなモジュールの境界に集める。
- アクセスパターンが求めるなら、キュー・キャッシュ・索引・グラフ・木・正規化したコレクションを使う。
- ほかに合う構造があれば、それを使う。合うものがなければ、コードが決して許してはいけない状態とデータの読まれ方を書き出し、ちょうどそれを表す構造を探す。

抽象を無理に入れない。今の形が既に明快で、局所的で、育ちそうにないなら、退屈なコードのほうがよい。分岐・重複した規則・不正な状態・ライフサイクルの危険のどれも消さずに間接参照だけを足す抽象は疑う。

この原則を飛ばした印は 2 つある。新しい機能が既存の if/else の連鎖を 1 本伸ばすこと、1 つ目と同期させ続けなければならない 2 つ目の真偽値が生まれること。処理の順番による分割（temporal decomposition）も印になる。フェーズの名前を付けたモジュールが、同じドメインの規則を段階ごとに繰り返す。

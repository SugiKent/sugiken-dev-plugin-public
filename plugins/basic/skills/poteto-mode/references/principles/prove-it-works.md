# Prove It Works（動くことを証明する）

作業を終えた後、完了を宣言する前に当てる。代理の指標、自己申告、「コンパイルが通った」で済ませず、実物（機能を動かす、実際の値を読む、差分を見る）で確かめる。

すべての作業結果を、実物を直接見て確かめる。代理の指標、自己申告、「コンパイルが通った」から推し量らない。

**理由。** 確かめていない作業は、正しさが分からない。間接的な確認（ファイルの更新時刻、出力の新しさ、エージェントの自己申告、キャッシュされたスクリーンショット）は、直接の観察より安く感じる。誤った推測で動いたときのコストは、元を確かめるコストよりはるかに高い。

確かめるのは実物で、代理の指標は使わない。

- プロセスが生きているかは、プロセスそのものを直接確かめる。派生した状態は、プロセスが死んでも残る。
- 実際の値を読む。キャッシュや派生した表現は、元の値と食い違うことがある。
- 確認が失敗したら、システムを疑う前に観察の方法を疑う。

## 確認はできるだけスクリプトにする

いちばん強い証明は、同じ比較を何度でも再実行する決定的なスクリプトになる。一度きりの目視は、次に誰かが確かめるときに再現できない。スクリプトを書き、実行し、その出力を、レビュアーが言葉を信じる代わりに再実行できる成果物として残す。

成果物は人間に見える場所に置く。コミットするのは、後から監査できる記録が要る大きく複雑な作業（大きな移植や移行など）のときだけ（`../decision-trail.md`）。

判定は VERIFIED（確かめた）、NOT VERIFIED（確かめて違った）、INCONCLUSIVE（決め手がない）のどれかで書く。INCONCLUSIVE は合格ではない。別の面で確かめただけのものも合格ではない。

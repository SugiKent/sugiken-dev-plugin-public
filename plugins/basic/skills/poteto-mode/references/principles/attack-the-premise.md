# Attack the Premise（前提を攻める）

同じ前提に立つ修正が 2 つ以上、同じ関門で失敗したら、修正を疑う前に前提を疑う。

**理由。** 失敗した修正は、それが置いた信念に反する証拠になる。同じ前提で 3 つ目の修正を書くと、原因がないと証拠が既に示している場所に労力を使う。

**やり方。**

- **前提を書き出す。** 前提とは、失敗したどの修正も置いていた一文のこと。
- **次の修正の前に前提を確かめる。** 前提が偽なら結果が変わる観察を見つけ、実際に観察する。失敗の大きさに加えて、失敗の分布を見る。確認は [Build the Lever](build-the-lever.md) に従い、再実行できる形にする。
- **証拠に従う。** 証拠が前提と矛盾するなら、原因は別の場所にある。前提が予測していなかった、失敗同士の共通点を探す。証拠が前提を支持するなら、[Fix Root Causes](fix-root-causes.md) に従って次の「なぜ」を問う。これまでの修正は、原因の代わりに結果を手当てしていたのかもしれない。
- **条件を補う仕組みを足さず、条件そのものを取り除く。** [Laziness Protocol](laziness-protocol.md) もこれを求める。ある部分がいつも負ける側に落ちると証拠が示すなら、そこへ落とすものを変える。後始末をする仕組みは原因を残したまま、毎回の実行に手間を足す。

**止まる条件。** 前提を書き出して確かめるまで、次の修正を始めない。

[Redesign from First Principles](redesign-from-first-principles.md) とは別物。あちらは新しい要求に合わせて設計を組み直す。こちらは今の設計が置いている事実を疑う。

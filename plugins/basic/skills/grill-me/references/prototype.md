# 試作

`grill-me` の「質問する前に分ける」で「動かせば分かる事実」に分類した分岐を、人間に尋ねる代わりに観察で決める手順。`openspec-propose` のグリリングから使う。pstack の poteto-mode の Prototype playbook を日本語化したもの。

**持つ責任は設計の判断で、コードではない。試作は使い捨ての計器で、本番の作り込みは apply で行う。**

試作では、Laziness Protocol の「最小の変更」と検証の水準が逆転する。磨くより速さを取り、コードの質は問わず、計画もしない。厳密さは、正しい設計を安く選ぶことに置く。人間が頼んでいない変種も出し、一つのやり方を捨てて別を試す。

1. 試作で下す判断の範囲を決める。どのレイアウト、どの操作、どの密度か。実験で決まる分岐なら、どの挙動・タイミング・やり方か。決める判断がないなら試作しない。
2. 設計の空間が開いているなら参考を集める。先行例を探し、テーマ・配色・レイアウトの moodboard を要約し、作る前に人間に方向を選んでもらう。方向が決まっているなら飛ばす。
3. 試作は、本番のソースから切り離した scratch のディレクトリに使い捨てで作る。見た目の判断なら、素の HTML/CSS/JS か、その考えを描けるいちばん軽い構成、CDN の依存、ホットリロードする dev サーバ。挙動やタイミングの判断なら、その問いを動かす最小のスクリプト。本番のフレームワーク、テスト、抽象は使わない。
4. 代替案を比べるときは、1 つの切り替え（ボタンかキー操作）の後ろに並べ、各変種にラベルを付ける。Exhaust the Design Space（`architect:35-architect-principle` の「pstack の原則」）を安く行う形がこれになる。
5. 判断する面で確かめる。見た目の判断なら、各変種のスクリーンショットを撮り、操作を実際に動かす（Playwright など）。挙動やタイミングの判断なら、決めたいものそのものを観察する。タイミングをログに出す、出力を印字する、描画を見る。ここでは観察がテストになり、assert は要らない。
6. 代替案、トレードオフ、推奨を示す。成果物は、判断と使い捨ての試作物で、出荷できるコードではない。選んだ方向は design に書き、形を決めるなら `architect:35-architect-sketch` へ渡す。

SDD の propose で試作したら、判断と証拠（スクリーンショットのパス、観察した出力やタイミング）を design.md の根拠に残す。

**返答。** 返答には、探った変種、証拠（見た目ならスクリーンショット、挙動なら観察した出力やタイミング）、トレードオフ、推奨、scratch のパスを書く。試作は使い捨てだとはっきり書く。

# UI を説明するな

インターフェースは、ユーザーにできることを見せる。自分自身を説明しない。文は 1 つずつ、ユーザーが操作の前に読まされるものである。文を残すのは、それがないとユーザーが実際に間違えるときだけにする。

UI を書くときは、書きながら下のルールを適用する。UI をレビューするときは、すべての文字列に各ルールを適用し、結果を Before / After で示す。

## ルール

### 1. 機能を説明しない

説明する代わりに、操作に名前を付ける。見出しと操作要素とそのラベルが、画面の目的をすでに伝えている。

Before

```
# プロジェクト
## まだプロジェクトがありません。
### GitHub リポジトリを選ぶと、push のたびにデプロイします。
+ 新規
```

After

```
# プロジェクト
+ リポジトリを接続
```

### 2. 具体的な動詞を使う

実際に起きることを表す動詞を選び、その動詞が作用する対象を付ける。より正確な動詞があるなら、「新規」「作成」「管理」「設定」「構成」「移動」「OK」のような汎用的な動詞は使わない。上の例では「新規」が「リポジトリを接続」になる。

### 3. 最も重要な結果だけを残す

1 つの操作に複数の効果があるときは、最も重要なものを 1 つ書き、残りは消す。そこから派生する効果は書かなくても伝わる。AI 自動返信で予約を受け付ける予約サービスなら、自動返信を止めれば予約も止まるのは自明である。

Before

```
オフにすると AI 自動返信と Web 予約が停止し、お客様からのメッセージは会話ログにのみ保存されます。オンに戻すときは、ヘッダーの「返信オフ」からいつでも操作可能です。
```

After

```
AI 自動返信を一時停止します。
```

データの削除、課金、顧客への通知のように取り消せない・破壊的な効果は、それ自体が最も重要な結果なので必ず残す。

### 4. バックエンドの挙動を書かない

データの保存先、記録される内容、同期されるもの、裏で動く処理は、ユーザーの関心事ではない。上の例では「お客様からのメッセージは会話ログにのみ保存されます」を消す。

### 5. 同じ操作要素で元に戻せるなら、戻し方を書かない

オフにするトグルは、オンにも戻せる。戻し方を書くのは、元に戻すのに別の操作要素や別の場所が必要なときだけにする。

### 6. ページがすでに伝えていることを書かない

ページタイトル、ナビゲーション、セクション構成はそれ自体が意味を持つ。オプションのページにいるユーザーは、自分がオプションを見ていることをすでに知っている。

Before

```
# その他のオプション
### 契約により利用可能になるオプションです。オン・オフの切り替えはできません。
```

After

```
# その他
```

### 7. 存在しないものを書かない

画面がすでに示しているなら、「まだ項目がありません」「切り替えできません」「この機能は利用できません」と書かない。明確な操作が置かれた空のリストは「まだ何もない」を伝えている。トグルのない行は「切り替えできない」を伝えている。

例外は、書かなければユーザーが試して失敗する制限である（自分のロールでは実行できない操作など）。これはルール 9 のとおり、アイコン付きの短い 1 行で残す。

### 8. 有効化の方法は文で書かず、操作要素を置く

購読、アップグレード、連携、設定のオンなどで使えるようになるものは、それを実行するボタンやトグルを画面に置く。どこへ行って何をすればよいかを文で書かない。

Before

```
このオプションを使うには Pro プランに登録してください。
```

After

```
[Pro にアップグレード]
```

### 9. テキストだけに頼らない

文章は短い行に分け、各行の先頭にアイコンを置く。構造は余白とグルーピングで表す。

`->`、`>`、`|`、`✔️`、`!`、`→`、`:`、`：` を区切り・矢印・箇条書き記号・強調として使わない。アイコンか余白を使う。

Before

```
すべての店舗を横断して検索し、結果を表示します。所属していない店舗では「オペレーター」として表示され、すべての操作はどの店舗で誰が何をしたかが記録されます。申込内容、支払方法、プランの変更や、お客様へのメッセージ送信（返信、仮予約の承認・却下）はできません。
```

After

```
(アイコン) すべての操作が記録されます
(アイコン) 申込内容・支払方法・プランの変更と、お客様へのメッセージ送信はできません
```

「すべての店舗を横断して検索し、結果を表示します」はルール 1、「オペレーターとして表示」は UI がすでにそう表示しているのでルール 6、記録形式の詳細はルール 4 で消える。

## チェックリスト

各文字列について、順に問う。

1. 機能が何かを説明しているか。消すか、具体的な操作ラベルに変える。
2. 動詞が汎用的か。実際の操作とその対象を表す動詞に置き換える。
3. 複数の結果を並べているか。最も重要な 1 つだけ残す。
4. 保存、記録、同期などの内部処理に触れているか。消す。
5. 同じ操作要素での戻し方を説明しているか。消す。
6. ページタイトルやナビゲーションがすでに伝えているか。消す。
7. 何かがない・使えないと書いているか。消す。ただし、書かなければユーザーが試して失敗する場合は残す。
8. 有効化の方法を文で伝えているか。ボタンやトグルに置き換える。
9. 段落になっているか、記号を区切りに使っているか。アイコン付きの行に分け、余白を使う。

チェックリストを通して何も残らなければ、何も置かない。埋め草の文より、空のヘルパーテキスト欄のほうがよい。

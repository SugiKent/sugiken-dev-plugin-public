# 並行案出しと統合

1案を練り上げるより、**別々の切り口で作った複数案を突き合わせたほうが良い答えが出る**種類の仕事がある。正解が1つに決まらず、どの切り口から考えるかで答えが変わる仕事（構成案・要件定義・設計方針・提案資料）が対象。

流れは3段。**共有ブリーフ → 並行案出し → 独立採点 → 統合**。

このスキルの価値は並行実行の速さではなく、**単一の視点では出てこない欠落が、複数案の突き合わせで露出すること**にある。3案すべてが同じものを見落としていた、という発見が最も価値が高い。

## 0. 共有ブリーフをファイルに書く

全エージェントが読む一次資料を1ファイルにまとめ、パスを渡す。プロンプトに背景を都度書くのではなくファイルにする。判断の根拠が全員で揃い、後段の採点者が「この案は前提を読み違えている」と指摘できるようになる。

ブリーフに必ず入れるもの:

- **ユーザーの発言の逐語引用**。要約して渡すと、要約時に落とした制約が全案から消える
- 既存の決定事項・過去の議論・技術制約
- スコープ外の明示
- 成果物の形式制約

**ブリーフの冒頭に書く**: 「最終成果物の見た目だけを見て判断してはいけない。この背景情報が判断の一次資料である」。これがないと、採点者が成果物の体裁だけを見て評価する。

## 1. 並行案出し（3体以上）

**各エージェントに互いに異なる切り口を割り当て、他の切り口は別のエージェントが担当すると明示的に伝える。** これをやらないと3案が似通い、突き合わせる意味が消える。

切り口の例（対象に応じて変える）:

| 切り口 | 何から考えさせるか |
|---|---|
| 利用シーン起点 | 誰が・いつ・どんな状況でこれに触れるか。時間・場所・前後の行動まで具体的に |
| 情報設計起点 | 扱う情報の構造は本当は何か。何を主役に据えると意味が最も強く出るか |
| 失敗理由起点 | これが使われずに死ぬ理由を先に列挙し、それを構造的に潰す |

失敗理由起点には敵対的レビュー系のサブエージェント（`architect-doubt-driven-development` 等）が向く。ただし**批判リストで終わらせず、必ず構成案の形まで落とさせる**。

各エージェントへの共通指示:

- 切り口から**構成を導く過程**を書かせる（結論だけでは採点できない）
- 案をファイルに書かせ、返答本文には400字程度の要点を返させる
- **「あなたの構成の弱点を自分で3つ挙げろ。ここを隠すと後段の採点で必ず見つかる」**と書く。これが後段で最も効く材料になる

## 2. 独立採点（3体以上）

案出しとは別のエージェントに、**互いに異なる評価軸**で採点させる。全案＋ブリーフを読ませる。

評価軸の例:

| 軸 | 見るもの |
|---|---|
| 現場で回るか | 想定の現実性、認知負荷、既存運用との摩擦、段階導入との相性 |
| 目的整合性 | 宣言された目的に奉仕しているか。手段が目的化していないか |
| 敵対的・説得力 | 破綻条件の具体的構成。批判的な読者に一撃で棄却される箇所はどこか |

出力形式を強制する。これを指定しないと「3案とも良い点があります」で終わり、統合の材料にならない。

1. **各案を10点満点で採点し、同点を禁止する**。点差の理由を書かせる
2. この軸で決定的に優れている**1案**を選ばせ、他案の記述を引用して論証させる
3. **各案から必ず1つずつ、残すべき具体的アイデアを名指し**（抽象論を禁止、仕様・UI・情報の出し方として書かせる）
4. **殺すべきアイデアを名指しで3つ以上**、理由つき
5. **3案すべてが見落としている論点を2つ以上**
6. 統合者への指示を優先順位つきで5項目以内

さらに伝えること:

- **平均を取ることを禁じる**
- **自己申告された弱点を「正直だから減点しない」と扱うのは誤り。申告されていても致命的なら致命的**
- **自己申告されていない、より重い欠陥を探せ**

## 3. 統合

**平均を取らない。骨格として1案を採り、他案から名指しされたものを移植する。**

手順:

1. 3人の採点が収束した案を骨格にする（多くの場合収束する。しないなら評価軸の設定が対象に合っていない）
2. 各案から「残すべき」と名指しされたものを移植する。移植先を骨格側の具体的な位置として決める
3. 「殺すべき」と名指しされたものを、骨格案の中にあっても落とす
4. **3案すべての欠落として指摘されたものを、新規に足す**。ここが統合で最も価値の出る部分。どの案にもなかったものが入る
5. 採点者が「これを成果物に載せるな」と指摘したもの（社内固有名詞、内部の決定番号、設計メモ）を除く

統合案が骨格案の一部を殺している場合、それは正しく機能した証拠。骨格案がそのまま通ったなら、採点が甘い。

## 4. 成果物化の前に機械検証

統合結果を出力したら、目視ではなく機械で確認する。生成物には目で追いにくい壊れ方が残る。

- タグの開閉均衡
- 不正な値・書き損じ（生成中に混入した壊れた行）
- 載せてはいけない語の混入（社内固有名詞・製品名・人名・内部の管理番号）
- 表記の混在（英日ちゃんぽん、造語）

## 注意

- **段ごとに3体以上**。2体では「どちらが良いか」になり、3案共通の欠落が見えない
- 案出しと採点で**同じエージェントを再利用しない**。自分の案を採点させても意味がない
- 段の間で結果を読む。読まずに次を投げると、統合の判断が採点者任せになる
- 各段は独立して並行実行できる。1メッセージ内で複数のサブエージェントを起動する
- 対象が「正解が1つに決まる仕事」なら、このスキルは過剰。素直に1案作る

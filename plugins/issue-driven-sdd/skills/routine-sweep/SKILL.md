まず同じ plugin の `routine-common` skill を読み、そのラベル規約・着手可否に従う。

# 前提（無人実行）

このスキルは定期実行の Routine から**無人で**呼ばれる。対話するユーザーはいない。

- **判断に迷ったら安全側へ倒す。** 着手しない・状態を壊さない方を選ぶ。
- **何をどう数えてそう判断したかを報告する。** 数字と、それが支えた判断を書く。
- **着手可能な対象が 0 件なら、数え方を報告して終える。それが正しい終わり方である。**
  埋め合わせの作業を作らない。

このスキルは**保険と選定**を担う。通常の段階遷移はイベント起動の routine が行う。
Routines の GitHub webhook には時間あたり上限があり、**超過分は黙って破棄される**ので、
落ちた分をここで拾う。

# 順序

1〜4 を順に実行する。1〜3 は状態の修復なので「1 セッション 1 アクション」に数えない。
実際の作業は 4 の 1 件だけ。

## 1. `wip` の失効を回収する

`wip` が付いた issue を全件見て、次を**すべて**満たすなら `wip` を外す。

1. その issue 番号を title か本文に持つ open PR が無い
2. その issue の change ディレクトリを触る open PR も無い（PR の変更ファイルで見る）
3. `wip` が付いてから 3 時間を超えている（イベントのタイムラインで見る）

3 時間より短いものは触らない。apply は実装からテストまでで 1〜2 時間かかるため、
短くすると作業中の issue を横取りし、並行 apply の事故が再現する。

## 2. 段階と実態の食い違いを直す

merge 済み PR のラベルと、対応 issue の段階を突き合わせる。イベント起動が落ちた分がここに出る。

| 実態 | 直し方 |
| --- | --- |
| `propose` PR が merge 済みなのに issue が `stage:propose` | `stage:apply` へ進める |
| `apply` PR が merge 済みなのに issue が `stage:apply` | `stage:archive` へ進める |
| `archive` PR が merge 済みなのに issue が open | issue を close する |
| PR が merge されず close されたのに `wip` が残る | `wip` を外す（1 の 3 時間を待たずに外してよい） |
| 段階ラベルが 2 つ以上 | **直さない。** 何と何が付いているかを issue へコメントする（人の判断） |

**「main に入っているか」は `origin/main` のファイルを読んで挙動で判定する。**
祖先判定コマンドは shallow clone で嘘をつく。

## 3. 応答が止まった PR を引き継ぐ

auto-fix はセッションが受け取るので、VM が回収された後も通常は再開する。それでも止まった
ものを拾う。open PR のうち、次を満たすものを探す。

1. ラベルが `propose` または `apply`
2. 最新のコメントが人のもの（`<!-- routine -->` で始まらない）
3. そのコメントから 3 時間を超えて routine の返信が無い

見つかったら、PR のスレッド全体と diff を読み、**そのラベルに対応するスキル**
（`routine-propose` / `routine-apply`）の続きを引き受ける。auto-fix を有効化し直す。
これを実行したらそれがこのセッションの 1 アクションであり、4 へは進まない。

## 4. 着手可能な issue を 1 つ実行する

次の条件で候補を集め、**1 つだけ**選ぶ。

- 段階ラベルがちょうど 1 つある（`stage:propose` / `stage:apply` / `stage:archive`）
- `wip` が付いていない
- `routine-common` の「着手可否の判定」を全部通る

選んだ issue の段階に応じて、該当スキルをそのまま実行する。

| 段階 | 実行するスキル |
| --- | --- |
| `stage:propose` | `routine-propose` |
| `stage:apply` | `routine-apply` |
| `stage:archive` | `routine-archive` |

候補が複数あるときは、**進んでいる段階を優先する**（archive → apply → propose）。
出荷に近いものから片付けるほうが、仕掛かりの滞留が減る。

候補が 0 件なら、**何をどう数えて 0 件と判断したかを報告して終える。それは正しい終わり方である。**
フォールバックの作業を作らない。規約を 1 行も足さずに終えたセッションは、量産へ 1 本足した
セッションより良い。

# `.claude/` `docs/` だけの修正

規約や記録の誤りに気づいたら、`routine-common` の「openspec を通さない変更」に従って
`docs` ラベルの PR を 1 本作ってよい。ただし**次のどれかに当たるなら書いてはならない**。

1. 書こうとしているファイルを、直近 24 時間に merge された PR が触っている
2. その差分が次のセッションの行動を変えない
3. open なコード PR がある（main を進めてコンフリクトの母数を増やすため）

1 を上書きできるのは、現に書いてある規約が**実測で効いていない・誤りだと数字で反証できる**ときだけ。
その規約 1 つを直し、ついでの実測値更新や言い回しの改善は混ぜない。

まず同じ plugin の `routine-common` skill を読み、そのラベル規約・着手可否・PR の作り方に従う。

# 対象の特定

**対象はトリガーとなった Issue。起動時の `github-trigger-context` に Issue の ID が書かれている。**
これはセッション開始から遅れて届くので、`routine-common` の「`github-trigger-context` の待ち方」に
従って待ってから読み、対象を確定させる。

そこから Issue を読み取れない場合は、**推測で対象を決めてはならない。** 何が読めなかったかを
報告して終える（`routine-sweep` が後追いで拾う）。ラベルの状態だけを見て「たぶんこれだろう」と
選ぶと、別セッションが作業中の issue を横取りする。

対象は 1 件だけ。**このセッションで作る PR は 1 つ。**

# 1. 着手できるかを判定する

`routine-common` の「着手可否の判定」を実行する。着手しないと決めたら、理由を issue へ
1 度コメントして終える。これは正しい終わり方であり、空振りではない。

着手すると決めたら **最初に `wip` を付ける**（ロック）。付けたら読み直して反映を確認する。

# 2. 事実を自分で調べる

**環境で分かることを人に聞いてはならない。** 次を先に読む。

- issue の本文と全コメント
- `origin/main` の該当コード・`openspec/specs/` の関連 capability
- `openspec/changes/` の進行中 change（同じ場所を触るものが無いか）
- `docs/` の関連ノート（topic で grep する）
- プロジェクトの `CLAUDE.md` と、製品の目的地を定めた文書

人に聞いてよいのは、**複数の選択肢から何を採るかという意思決定だけ**である。

# 3. 意思決定が残っているかを判断する

残っていなければ 5 へ進み、完成した proposal の PR を作る。

残っているなら 4 の grill へ進む。**「残っている」とは、選択肢が複数あり、どれを選ぶかで
proposal の中身が変わる**ということである。調べれば決まることや、既存の規約・spec が
既に答えているものは含めない。

# 4. grill — PR 上で詰める

## 4.1 最初のラウンドで PR を作る

`openspec-propose` で change ディレクトリを作り、`proposal.md` に次の 2 節を置く。

```
## 確定した判断
（調査で確定したこと。根拠のファイル・行を添える）

## 未確定の判断
### Q1. <問い>
- 選択肢 A（推奨）: <採った場合に何がどうなるか>
- 選択肢 B: <同上>
- 依存: なし / Q2 の回答が要る
```

この状態で **ready の PR** を作る（`routine-common` の「PR の作り方」に従う。draft にしない）。
本文 1 行目は `未確定の判断: N 件 — merge しないでください`。ラベルは `propose` と `question` の 2 つ。
`question` は「人の回答を待っている」ことを示す（`routine-common` の「PR（修飾）」を参照）。
**auto-fix を有効化し、レビューコメントと会話コメントの両方を文脈として扱う方針を明示する。**

## 4.2 問う

PR のコメントとして投稿する。冒頭に `<!-- routine -->` を付ける。

- **独立な問いは 1 コメントに束ねる。** 往復回数を最小にする。
- **依存する問いは前の回答を待つ。** 先の判断で選択肢が消えるものを同時に聞かない。
- 各問に**推奨**を付け、その選択で何がどうなるかを書く。
- 記号だけで返信できる形にする（`Q1: A`）。
- **投稿したら `question` が付いていることを確認する。** 4.1 の後に新しい枝が出て問いを足した
  場合は、外れていれば付け直す。
- **コードを読んでいない読み手を前提に書く。** どの画面か（名前とパス）、どの処理がいつ動くか、
  誰のどの操作が起点で何が起きるかを、抽象語より先に具体で書く。

## 4.3 回答を受けて進める

auto-fix によって、同じセッションが人の返信を受け取る。

1. 回答を `## 確定した判断` へ移し、`## 未確定の判断` から消す
2. PR 本文 1 行目の N を更新する
3. push する
4. 次の枝が残っていれば `question` を付けたまま 4.2 へ戻る

**N が 0 になるまで `question` は外さない。** 1 ラウンド終えたことは、人へ問うことが
残っていないことを意味しない。

回答が曖昧なら分かったことにせず、同じ枝をさらに掘る。**未回答のまま既定で進めてはならない。**

## 4.4 詰め切る

すべての枝が解決したら、`proposal.md` に次を書き切る。

- 確定した判断
- 明示的に延期した判断
- 残っているリスク

`## 未確定の判断` の節を削除し、本文 1 行目を `未確定の判断: 0 件 — レビューをお願いします` にする。
そのうえで **`question` ラベルを外す**。外したら読み直して反映を確認する。

# 5. proposal を完成させる

`openspec-propose` の作法に従い、`proposal.md` / `design.md` / `tasks.md` / spec delta を揃える。

- **`openspec validate --strict` を緑にする。**
- proposal / design に対応する issue 番号（`#n`）を必ず書く。issue と change の対応はこれで引く。
- **`tasks.md` に「投入後の実測」「本番で確認」「デプロイ後」の節を作ってはならない。**
  archive の判定は「全タスクが `[x]`」なので、セッションで完了できない行が 1 本でもあると
  archive が永久に止まる。実測したい観点があれば**別 issue として起票する**（段階ラベルは付けない）。
- change の Impact に読み出し面があるなら、tasks に開発用の seed データを作る行を入れる
  （手元で新しい表示状態を全件再現できないと、実装は済んでいるのに画面を開けない状態で完了になる）。
- E2E ケースの列挙が要るかは `routine-common` の「リポジトリの事情に従う」で決める。
  リポジトリが E2E を要求しているなら `e2e:20-enumerate-e2e-cases` で列挙し、要求していないなら
  列挙しない。
- 画面案や図解を人に見せる必要があり、リポジトリのスキルがスクリーンショットやアーティファクトで
  伝える方針なら、同じ節に従ってアーティファクトを作り、URL を PR 本文またはコメントに載せる。

# 6. 終える

PR を作った（または grill を終えて ready にした）時点でこのセッションは完了。**merge を待たない。**
`wip` は付けたままにする（PR が open なので、`routine-sweep` の失効回収には当たらない）。

次の段階は `propose` ラベルの PR が merge された時点で `routine-apply` が起動して担う。

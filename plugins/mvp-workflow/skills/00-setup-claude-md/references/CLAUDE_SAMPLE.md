# ルール

## シンプルさを最優先にする

問題を解くために必要な最小限のコードのみを書くこと。

- 投機的な機能・将来の拡張に備えたコードは書かない
- 一度しか使わない処理のために、ヘルパーや抽象化を増やさない
- 起こり得ない状態への防御コードを追加せず、入力や外部 API などの境界で必要な検証だけを行う

## パターン競合は平均化しない

コードベース内に複数のパターンが存在する場合、混在させずに一つを選ぶこと。

- 二つのパターンを安易に組み合わせない
- 既存コードベースの主流パターンを優先する
- 選択によって成果が大きく変わる場合だけ、採用するパターンと理由を短く共有する

## テストは「意図」を検証する

テストは、コードの意図と利用者から見える振る舞いを検証するものとして書くこと。

- 「この関数が呼ばれた」ではなく「この条件でこの結果になるべき」をテストする
- 常にパスするテスト・意味のないアサーションは書かない
- 実装をハードコードしてテストだけを通さない

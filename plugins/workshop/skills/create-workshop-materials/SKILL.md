# 勉強会資料作成

入力は次の 2 つとして扱う。

- `title`: 勉強会の題名
- `内容`: 箇条書き、断片、独り言を含む未整理の考え。省略・矛盾・未確定の部分を許容する。

内容だけから断定できない事実は作らない。不明点は構成案で仮説または確認事項として明示し、必要になった時点で一度に少数だけ質問する。

## 進め方

必ず次の順序を守る。構成承認とデザイン承認を飛ばして PPTX を作らない。

1. **格納場所を確認して準備する**
   - 最初に「勉強会」フォルダを作る親ディレクトリをユーザーへ確認する。指定がなければ、現在のプロジェクト直下を提案するが、明示的な同意なしに作成しない。
   - 合意後、`<親ディレクトリ>/勉強会/` と `<親ディレクトリ>/勉強会/{YYYYMMDD-HHmm}-{title}/` を作る。`title` はファイル名として安全な短い表記に正規化する。時刻は作成時のローカル時刻を使う。
   - このフォルダを資料、HTML プレビュー、構成案、調査メモ、PPTX の一貫した保存先にする。

1. **関連情報を探索する**
   - プロジェクトがある場合、まずコードベースの知識グラフ（`search_graph`、`trace_path`、`get_code_snippet`、必要時は `query_graph`）で、題材に関係する実装、仕様、用語、既存ドキュメントを調べる。未インデックスなら `index_repository` を実行する。
   - 文字列・設定値・非コード文書は、知識グラフで不足する場合に限り `rg` などで探索する。
   - 外部調査が必要な主張は、信頼できる一次情報を優先して出典を保存し、スライドにも必要十分な出典を記載する。
   - 参照したファイル、主張、出典を `source-notes.txt` に簡潔に記録する。

1. **ペルソナを確認する**
   - 勉強会なので、聴衆ペルソナが重要
   - 聴衆はどういう人で、すでに何を知っていて、どんな学びや驚きを与えたいのかを3段階のなぜなぜ分析を行って深く言語化し人間から承認をもらえるまで修正と対話を繰り返す

1. **構成を壁打ちして承認を得る**
   - 未整理の入力を、聴衆が持ち帰るメッセージを軸に並べ替える。1 スライドにつき伝えることは 1 つにする。
   - 画像生成を使うページは、この段階で確定する。各対象ページについて、画像が担う役割、配置（例: 右 40% の横長ビジュアル）、必要な縦横比、避ける表現を決める。単なる装飾ではなく、理解を助ける画像だけを選ぶ。
   - 次の形式だけでページごとの構成案を提示する。発表者用の作業メモはスライド本文に混ぜない。

```text
Page: 1
{title}
{伝えること}
{デザインパターン/レイアウト}

---

Page: 2
{title}
{伝えること}
{デザインパターン/レイアウト}
```

   - ユーザーのフィードバックを反映して同じ形式で改訂し、「この構成で進めてよいですか」と確認する。明示的な承認を得るまで、デザイン確定・PPTX 作成・Google Slides 作成へ進まない。
   - 画像生成を使う場合は、構成案の後に `画像生成計画` を添え、ページ番号ごとに役割・配置・比率・生成プロンプトの要点を示す。この計画も構成承認の対象にする。承認後に画像の挿入先を追加・移動する場合は、構成へ戻って確認を取り直す。

1. **デザインを確認する**
   - `references/design.md` を読み、ユーザー指定があればそちらを優先する。
   - 構成に合わせて色、書体、余白、図版の方針を短く示す。情報を小さなカードや UI 風パネルへ分割しすぎず、読み順が明確な一つの構図を選ぶ。
   - 表紙または結論など、理解に重要な 2 ページを実際の HTML Artifact として作成する。見せかけのワイヤーフレームにせず、実データ・実コピー・実際の配色と書体で表現する。
   - Artifact を提示し、「このデザインで PPTX を作成してよいですか」と確認する。承認まで修正を繰り返す。

1. **PPTX を作成して品質確認する**
   - `presentations` スキルを使う。PPTX は `@oai/artifact-tool` を用いる JavaScript ES module で作成し、`python-pptx` は使わない。
   - 承認された画像生成計画がある場合、Codex CLI を呼び出して画像を生成する。画像は作業フォルダの `assets/` に保存し、生成時のプロンプトと対象ページを `source-notes.txt` に記録する。Codex CLI または画像生成機能が利用できない場合は、代替手段へ勝手に切り替えず、利用不可であることを伝えて指示を仰ぐ。
   - 生成画像は、承認されたページ・配置・比率にだけ挿入する。画像の内容、トリミング、人物や文字の可読性を確認し、メッセージを弱める場合は再生成または不使用にする。
   - 完成ファイルは作業フォルダに保存する。タイトルは最小限に、本文は原則 24pt 以上、タイトルは 36pt 以上にする。文章量が増えたらフォントを縮めず、文章を削るかページを分ける。
   - すべてのページをレンダリングして個別に確認する。テキストの折返し、はみ出し、重なり、読み順、図版のトリミング、出典、ページ間の一貫性を修正してから完成とする。

1. **Google Slides を作成・更新する**
   - Google Drive MCP が使える場合は、完成済み PPTX を native Google Slides としてインポートする。利用できない場合は `gws` CLI を使う。どちらも使えなければ、必要な連携を案内して停止する。
   - Google Drive MCP は既存の Slides を直接更新できない前提で扱う。PPTX を変更するたび、PPTX を再インポートして同名ファイルを上書き更新し、共有 URL を最新のものとして確認する。
   - 最終回答では PPTX の場所と Google Slides の URL を示し、外部調査を使った場合のみ主な出典も添える。

## 表現のルール

- 画面に見える文言は参加者のために書く。工程メモ、壁打ち用の選択肢、発表者向け指示を本文に入れない。
- 得られた文脈で一般的な用語を優先し、不用意な英語や、日本語に英訳を添えただけの装飾は加えない。
- 文章を箇条書きへ移すだけで終えず、結論、根拠、具体例、次の行動が自然につながる物語にする。
- 数字・引用・技術的主張は出典またはプロジェクト内の根拠に紐付ける。推測は推測と明記する。

まず同じ plugin の `routine-common` skill を読み、「worker の共通手順」に従う。

# 1. 対象と着手可否

「対象の特定」で issue を決め、「着手可否の判定」を上から見る。見送るなら「見送りの書き戻し」で終える。
着手するなら「着手の印」を付ける。

issue に人のコメントがあれば全部読む。`blocked-by: human` で戻され、人が答えたあとの再起動である
ことが多い。

# 2. 事実を自分で調べる

環境で分かることを人に聞かない。issue の本文と全コメント、`origin/main` の該当コード、`docs/` の
関連ノート、プロジェクトの `CLAUDE.md` を先に読む。人に聞いてよいのは**複数の選択肢から何を採るかと
いう意思決定だけ**。実装前に決めないと進めない判断が残っていれば、判定 6 で issue へ戻す。

# 3. 実装する

リポジトリのゲート（型検査・lint・関連テスト）と `.claude/rules/` の該当ルールを緑にする。E2E と
スクリーンショットは「リポジトリの事情に従う」で決める。規模に応じて `orchestration:apply-backend` /
`orchestration:apply-frontend` へスライスを委譲してよい。

このセッションで実行できない作業（本番実測・デプロイ後確認）は PR 本文に残作業として書く。
別 issue にするときは `"#<n>" in:title is:open` で既存の残作業 issue を探し、無いときだけ起票する。
ラベルは付けない。

# 4. PR を作る

「PR の作り方」に従う。title は `#<n> <要約>`、本文に `Closes #n`。

実装後にも残った意思決定（既定で進めたが人の確認が要るもの）は、`未確定の判断: N 件` として本文 1 行目に
数え、`[question]` を書き、問いを PR コメントに投稿する。独立な問いは 1 コメントに束ね、各問に推奨を付け、
`Q1: A` の形で返せるようにする。

# 5. レビューに対応して終える

PR を作った時点で実装は完了。auto-fix でレビューコメント・会話コメント・CI の失敗が届いたら反映して
push し、何をどう直したかを `<!-- routine -->` 付きでスレッドへ返す。回答が曖昧なら分かったことにせず
同じ枝を掘る。N が 0 になったら 1 行目を更新し `[]` を書く。設計に関わる曖昧な指摘は勝手に決めず
スレッドで確認する。

merge は待たない。`In Progress` は付けたままにする（close 時に dispatch が `Done` に置き換える）。

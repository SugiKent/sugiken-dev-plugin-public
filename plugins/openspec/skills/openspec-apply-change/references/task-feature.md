# 新しい振る舞いの task（機能）

`openspec-apply-change` の手順 7 で、新しい振る舞いや変わる振る舞いを作る task に使う。pstack の poteto-mode の Feature playbook を、apply の中で使う形にしたもの。仕組みの把握（Feature の手順 1）と設計の並行探索（手順 2）は、propose の「設計の形を決める」で済んでいる前提。design に型のスケッチがなければ、関数の境界をまたぐ task の前に `architect:35-architect-sketch` を回す。

**設計の責任は自分が持つ。計画し、レビューし、確かめる。** 実装は委任してよいが、主導は手放さない。

1. スループット点検を 4 つの todo として書く。当てはまらない観点（1 ファイルだけ、並行作業なし）も項目を消さず、`該当なし: <理由>` を書いて残す。
   - **先に塞ぐ手順。** 並行に広げる前に通す関門。
   - **独立した作業の流れ。** 互いに素なファイル・サービス・層は並行にできる。共有する書き込みは直列にする。
   - **書き換え可能な共有状態。** 既定では書き込み先を分ける（Separate Before Serializing Shared State）。直列にするのは本当の不変条件があるときだけ。
   - **安全な最小の分け方。** 1 人で作るのが最善なら、その理由を名指しする。
2. コードを書く作業をサブエージェントに委任するときは、下の「サブエージェントに任せるとき」に従い、範囲を具体的に渡す。ファイルのパス、名指ししたデータの形とそれをまとめる構造（Model the Domain に従い、散らばった真偽値より状態機械、分岐より表や登録簿、繰り返す形の前提より型付きのモデル。委任先がロジックを書く前に決める）、成功の条件。実装に正しい形が複数ある（エラー処理、抽象の層、テストの構造）なら、`35-architect-sketch` の Phase B の競作で委任し、候補に別案を出させ、相互審査に選択を守らせる。この競作は飛ばさない。Laziness Protocol もこれを覆さない（ここで得るのはレビューの分離で、行数の節約は目的にしていないため）。サブエージェントを起動できない立場なら、同じレビューの分離を保って自分で差分を持つ。入れ子のエージェントを待つだけの「待機中」の返答はしない。編集は外科的に行い、上流から派生したファイルは元に照らして直す。共有の部品を改善したら、すべての利用側へ移して、それぞれ確かめる。
3. 変更した面で確かめる。「INCONCLUSIVE」や別の面での確認は合格ではない。そう明記する。
4. 小さく順序立ったコミットに整える（`basic:20-commit-meaningful-diffs`）。Sequence Work into Verifiable Units に従い、小さな単位ごとに作り、確かめ、コミットを済ませてから次へ進む。
5. 設計に異論が残るなら、apply の手順 10 の前でも `architect:35-architect-interrogate` を回してよい。

コードで結合した作業（1 つの機能、1 つの移行）は、点検を内に持った 1 人の持ち主に渡す。その持ち主が、先に塞ぐ段階の後で内部的に並行に広げる。親の段階で並行に広げるのは、独立した成果物を生む断面（監査、サブシステムをまたぐ調査、競合する実験）だけ。段階の区切りで点検を書き直す。割り込みをつなぐより、新しい持ち主を起動する。

原則名（Separate Before Serializing Shared State など）の中身は `architect:35-architect-principle` の `references/pstack-principles/` にある。

## サブエージェントに任せるとき

pstack の poteto-mode の「Subagents」を Claude Code に合わせたもの。バグ修正とリファクタリングの task で委任するときもこれに従う。

- **起動の既定。** Agent ツールで起動し、背景で走らせる。文脈は貼り付けずにファイルのパスで渡す。役割ごとにモデルを選ぶ。最も難しい変更（横断的な設計、厄介な並行処理、微妙なアルゴリズム）と文章・判断は `opus`、機械的な編集は `sonnet` か `haiku` に回し、`effort` で推論の深さを調整する。書き込む委任先同士は `isolation: "worktree"` で作業ツリーを分ける。
- **仕事の責任は自分が持つ。** サブエージェントの差分を自分でレビューし、要約を自分で書く。報告をそのまま流さない。
- **セカンドオピニオンは、同じ依頼を別のモデルに投げること。** 意見の一致は強い信号になる。Claude だけでは系統が揃うので、Codex MCP など別系統のモデルが使えるなら 1 つ混ぜる。
- **新しい仕事は新しいサブエージェントへ。** 元の依頼、その後の指示、前のエージェントの報告とブランチをまとめて渡す。修正の往復、追加の依頼、再試行、次の task のどれもこの扱い。既存のエージェントへ SendMessage で続きを頼むのは、そのエージェントの中にしかない状態（手元の checkout、未コミットの変更、動かしている dev サーバやシミュレータ）が要り、移すのが高くつくときだけ。中断と再開をつなぐと指示が黙って落ちるので、「完了した」という要約を信じず、まとめた範囲で新しく起動する。
- **網羅のための並走。** 独立した範囲（パッケージごとの検査、機能ごとの検証）に分けるときは、完了条件と返す報告の形を先に決める。各ワーカーには目的・範囲・確かめ方・報告内容を自己完結で渡し、報告は `PASS` / `ISSUES` / `BLOCKED` と根拠で返させる。全範囲の結果が揃うまで合格としない。結果が欠けたワーカーは 1 回だけ起動し直し、2 回目も欠けたら欠落として報告する。生の出力は貼らず、1 つの表にまとめる。

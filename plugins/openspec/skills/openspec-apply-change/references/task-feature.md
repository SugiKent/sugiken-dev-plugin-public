# 新しい振る舞いの task（機能）

`openspec-apply-change` の手順 7 で、新しい振る舞いや変わる振る舞いを作る task に使う。仕組みの把握と設計の並行探索は、propose の「設計の形を決める」で済んでいる前提。apply では判断しないので、design に型のスケッチがないまま関数の境界をまたぐ task に来たら、ここでスケッチせず一時停止し、`openspec-propose` へ戻す。

**設計の責任は自分が持つ。計画し、レビューし、確かめる。** 実装は委任してよいが、主導は手放さない。

1. スループット点検を 4 つの todo として書く。当てはまらない観点（1 ファイルだけ、並行作業なし）も項目を消さず、`該当なし: <理由>` を書いて残す。
   - **先に塞ぐ手順。** 並行に広げる前に通す関門。
   - **独立した作業の流れ。** 互いに素なファイル・サービス・層は並行にできる。共有する書き込みは直列にする。
   - **書き換え可能な共有状態。** 既定では書き込み先を分ける（Separate Before Serializing Shared State）。直列にするのは本当の不変条件があるときだけ。
   - **安全な最小の分け方。** 1 人で作るのが最善なら、その理由を名指しする。
2. コードを書く作業をサブエージェントに委任するときは、下の「サブエージェントに任せるとき」に従い、範囲を具体的に渡す。ファイルのパス、design が名指ししたデータの形とそれをまとめる構造（委任先がロジックを書く前に渡す）、成功の条件。実装に正しい形が複数ありうる箇所は、propose が `openspec-propose` の「設計の形を決める」で決めて design に書いている。委任先には design の形を渡す。design が形を決めていない箇所に当たったら、apply で競作して決めず、一時停止して `openspec-propose` へ戻す。サブエージェントを起動できない立場なら、同じレビューの分離を保って自分で差分を持つ。入れ子のエージェントを待つだけの「待機中」の返答はしない。編集は外科的に行い、上流から派生したファイルは元に照らして直す。共有の部品を改善したら、すべての利用側へ移して、それぞれ確かめる。
3. 変更した面で確かめ、判定を apply の「9. 実物で確かめる」の書き方で書く。応答の形の検査（parser の必須キーなど）を厳しくしたら、落ちたテストより通り続けているテストを疑う。失敗の場面のテストが手前の検査のエラーで止まり、狙った判定に届かないまま緑になることがあるため。失敗のテストは、表示の文言ではなく、どの応答のどの分類で止まったかで確かめる。
4. 小さく順序立ったコミットに整える（`basic:20-commit-meaningful-diffs`）。Sequence Work into Verifiable Units に従い、小さな単位ごとに作り、確かめ、コミットを済ませてから次へ進む。
5. 設計への異論が出たら、apply で決着させず `openspec-propose` へ戻す。差分への敵対的レビューは apply の手順 10 で行う。

コードで結合した作業（1 つの機能、1 つの移行）は、点検を内に持った 1 人の持ち主に渡す。その持ち主が、先に塞ぐ段階の後で内部的に並行に広げる。親の段階で並行に広げるのは、独立した成果物を生む断面（監査、サブシステムをまたぐ調査）だけ。形を比べる競作は propose で済んでいるので、apply では行わない。段階の区切りで点検を書き直す。割り込みをつなぐより、新しい持ち主を起動する。

原則名（Separate Before Serializing Shared State など）の中身は `architect:35-architect-principle` の `references/principles/` にある。

## サブエージェントに任せるとき

バグ修正とリファクタリングの task で委任するときもこれに従う。

- **起動の既定。** Agent ツールで起動し、背景で走らせる。文脈は貼り付けずにファイルのパスで渡す。役割ごとにモデルを選ぶ。最も難しい変更（厄介な並行処理、微妙なアルゴリズム）と文章は `opus`、機械的な編集は `sonnet` か `haiku` に回し、`effort` で推論の深さを調整する。書き込む委任先同士は `isolation: "worktree"` で作業ツリーを分ける。
- **worktree の起点と取り込み。** worktree はコミット済みの状態から切られ、未コミットの change フォルダや前の task の変更は委任先から見えない。委任の前に、それらをコミットしておく。委任先には作業を自分の worktree でコミットさせ、親が差分をレビューしてから自分のブランチへ取り込む（`git cherry-pick` か `git merge`）。tasks.md のチェックは、取り込んだ後に親が付ける。
- **本番の意味を依頼に書く。** 委任先が模擬サーバーや dev のストアを作るなら、依頼にはページングの件数のような形だけでなく、クライアントが頼る本番の意味（判定の順、絞り込みとページングの順）を書く。偽物どうしが本番を違うように写すと、どちらに合わせても本番とずれるため。偽物どうしのずれを直した後は、その経路を実際のサーバーで 1 回通す。
- **仕事の責任は自分が持つ。** サブエージェントの差分を自分でレビューし、要約を自分で書く。報告をそのまま流さない。
- **セカンドオピニオンは、同じ依頼を別のモデルに投げること。** 意見の一致は強い信号になる。Claude だけでは系統が揃うので、Codex MCP など別系統のモデルが使えるなら 1 つ混ぜる。
- **新しい仕事は新しいサブエージェントへ。** 元の依頼、その後の指示、前のエージェントの報告とブランチをまとめて渡す。修正の往復、追加の依頼、再試行、次の task のどれもこの扱い。既存のエージェントへ SendMessage で続きを頼むのは、そのエージェントの中にしかない状態（手元の checkout、未コミットの変更、動かしている dev サーバやシミュレータ）が要り、移すのが高くつくときだけ。中断と再開をつなぐと指示が黙って落ちるので、「完了した」という要約を信じず、まとめた範囲で新しく起動する。
- **網羅のための並走。** 独立した範囲（パッケージごとの検査、機能ごとの検証）に分けるときは、完了条件と返す報告の形を先に決める。各ワーカーには目的・範囲・確かめ方・報告内容を自己完結で渡し、報告は `PASS` / `ISSUES` / `BLOCKED` と根拠で返させる。全範囲の結果が揃うまで合格としない。結果が欠けたワーカーは 1 回だけ起動し直し、2 回目も欠けたら欠落として報告する。生の出力は貼らず、1 つの表にまとめる。

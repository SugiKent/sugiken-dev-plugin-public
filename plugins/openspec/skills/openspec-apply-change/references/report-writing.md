# 報告の書き方

`openspec-propose` の要約と、`openspec-apply-change` の完了報告・一時停止の報告をこの書き方で書く。最終報告の構造は下の「最終報告の固定フォーマット」を正本とする。下書きの時点できれいに書く。書いた後に掃除しても、ここに挙げる癖は抜けない。


## 最終報告の固定フォーマット

propose・apply で作業を止めてユーザーに返す最終報告は、完了、一時停止、回答待ち、既に全 task 完了の場合、retro 後のいずれも次の形式にする。retro を実行した場合は、その反映・検証まで終えてから報告する。途中経過やグリリング中の質問、成果物ファイルの template は対象外。

見出しは以下の順序・表記・レベルに固定する。先頭には実際の change 名を書く。未特定なら「change 未特定」と書く。4 つの表の列名・順序を変えず、節を省略しない。該当項目がなければ「なし」と理由の 1 行を置く。表の前後に挨拶・別の要約・独自の見出し・締めの文を足さない。詳細なログは読んだファイルへのリンクを表のセルに置き、結果の要点もセルに残す。

```markdown
# <change-name>

# 進捗報告

| 項目 | 状態 | 実施内容・残り |
| --- | --- | --- |
| 全体 | 完了 / 一時停止 / 回答待ち | 誰の何が変わるか。現在の段階と次の行動。 |
| 成果物・tasks | 完了 / 未完了 / 対象外 | change の場所、schema、成果物の作成状況、今回完了した tasks と全体の N/M。 |

# 検証内容

| 検証項目 | 実行内容・対象 | 結果 | 証拠・未確認の範囲 |
| --- | --- | --- | --- |
| lint | コマンドと対象。 | 成功 / 失敗 / 未実行 / 対象外 | 実行結果。未実行・対象外なら理由。 |
| test | コマンドと対象。 | 成功 / 失敗 / 未実行 / 対象外 | 件数と結果、確認できた範囲。 |
| e2e | シナリオと環境。 | 成功 / 失敗 / 未実行 / 対象外 | 実物を通した経路、偽物の境界と未確認経路。 |

# AIが判断して進めたこと

| 判断 | そう判断した根拠 |
| --- | --- |
| 実際に AI が選んで進めたこと。 | 要求・成果物・観察した証拠。 |

# 人間に確認してほしいこと

| 確認事項 | AIで検証できない理由 | 確認方法・判断してほしい内容 | 影響・止まっている作業 |
| --- | --- | --- | --- |
| 残った未確認点・未決判断。 | 権限・環境・人の選好など具体的な制約。 | 操作・期待結果、または選択肢。 | 影響範囲、止まっている task、再開条件。 |
```

### 各表に残す情報

- 進捗報告には成果物の作成と共有理解の確認を分けて書く。未解決判断があれば草案・回答待ちとし、実装準備完了にしない。レビュー、コメント掃除、retro、コミット・PR、次の行動も必要に応じて行を足す。retro は反映したファイル、作成した Issue、反映しなかった候補と理由を含める。一時停止では未 push のコミットと push が deploy になるかも書く。
- 検証内容の lint・test・e2e は未実行・対象外でも行を残す。型チェック、OpenSpec validate、未決事項のスクリプト、試作・実測、レビューなどは行を足す。実行したコマンド・出力の要点と証拠の場所、実物確認の VERIFIED / NOT VERIFIED / INCONCLUSIVE を残す。レビューは探す役・検証役、Act on / Consider / Noted / Dismissed、反映先、合意に届かなかった指摘と票を残す。未実行を成功にせず、AI が確認した範囲を越えて主張しない。
- AIが判断して進めたことには採用した選択、代替案とのトレードオフ、適用した原則と変わった選択を入れる。無人 propose の既定の選択には、代わりの指示の仕方も書く。この表は apply に仕様・設計の判断を許可しない。apply は成果物を変えない局所の選択だけを書き、未決の仕様・設計は次の表へ送る。
- 人間に確認してほしいことには AI 自身では検証できず残った点と、人間の意思決定が必要な点だけを書く。自分で回せる確認を渡さない。判断待ちでは集めた証拠を同じ行に示し、止まっている task と対応付ける。一時停止中に見つけた別件も行にする。該当なしでも表を残して「なし」と書く。
- 完了・archive の条件は各 skill の既存の条件に従う。固定形式を埋めたことを完了の証拠にしない。

- 短い平叙文で書く。一文に一つの考えを置き、句点で終える。
- 全角ダッシュ（——）とその代用の記号を使わない。ファイル一覧の箇条書きは文にする（「`main.js` が永続化と IPC ハンドラを持つ」）。太字の見出しは独立した文にする（「**検証。** CDP で端から端まで確かめた」）。
- 文中のつなぎとしてコロン（「:」「：」）を使わない。リストの直前に置くのはよい。
- 短く書くことを、中身を落とす口実にしない。詳細、トレードオフ、選んだもの、未決の判断は、固定フォーマットの対応する表に残す。
- 影響を、使う人と保守する人の目線で書く。誰のための change か（エンドユーザー、ライブラリを import する同僚）と、その人に何が変わるかを、実装の詳細より先に書く。次に、このコードを次に持つエンジニアが何を引き継ぐかを書く。どちらも書けないなら、仕事か説明のどちらかがずれている。
- リンク・引用・会話記録の参照を捏造しない。リンクしてよいのは、このセッションで作った・読んだものだけ。PR へのリンクは `https://github.com/<owner>/<repo>/pull/<number>` の形で書く。
- 主張には、同じ文の中に根拠かラベルを付ける。ラベルの付け方は `basic:grill-me` の「質問の出し方」と同じにする。自分で回せる確認を人間に渡さない。
- 気分を書かず、仕組みや数字を書く。「扱いやすい」と書きたくなったら、「列名を変えるとビルドが落ちる」のように何が起きるかを書く。別のプロジェクトの文書にそのまま載る文は、このプロジェクトについて何も言っていないので消す。
- 矢印・記号・略語で詰めない。「不正な日付 → exit 2、書き込みなし」は「パーサが不正な日付を拒否し、終了コード 2 で終わり、何も書き込まない」と書く。
- 判断を形作った原則（`architect:35-architect-principle` の「作業の原則」）を名指しし、その原則で変わった具体的な選択を書く。挙げてよいのは、このセッションでファイルを読んだ原則だけ。原則名だけ挙げて変わった選択が書けないなら、その原則は当てていない。

日本語の癖（意義の過剰強調、定型評価語、太字とコロンの箇条書きなど）は `basic:01-humanizer-ja` で落とす。

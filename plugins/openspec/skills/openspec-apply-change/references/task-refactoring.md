# 構造だけを変える task（リファクタリング）

`openspec-apply-change` の手順 7 で、振る舞いを変えずに構造や形を変える task（改名、抽出、インライン化、重複の除去、移動）に使う。

**約束の責任は自分が持つ。構造は変わり、振る舞いは変わらない。** 振る舞いを足す `task-feature.md` とも、振る舞いを正す `task-bug-fix.md` とも別。

整理の途中で足りない機能や本物のバグが見つかったら切り分け、固定した約束に対する構造の変更を先に出す。作り直し（redesign）が要るなら、apply では始めず `openspec-propose` へ戻す。change に収まらない大きな、または横断的な構造の作業は、一時停止して change の分割を提案する。

1. 先に振る舞いの約束を固定する。`architect:35-architect-sketch` の `references/grounding.md` の「仕組みを説明する」で触るサブシステムの約束を知り、構造を動かす前に、今の振る舞いを捉える特性テスト・スナップショット・等価性の確認を書く。その領域にテストがないなら、構造を触る前に固定を書く。型検査と lint は固定にならない。
2. design が名指ししている、コードに欠けた構造（Model the Domain）を確かめる。作り変えは分岐や不正な状態を消すものでなければならず、間接参照を足すだけのものは認めない。
3. 目標の形は、design に書かれた形（モジュールの配置・型・呼び出しのグラフ）を使う。apply で目標の形を決めたり、スケッチで探ったりしない。design に目標の形が書かれていなければ、動かす前に一時停止し、`openspec-propose` へ戻す。
4. 足す前に引く。新しい形を入れる前に、使われていないコードを消し、呼び出し元が 1 つの包みを畳み、重複した検証を外し、宙に浮いた参照を取り除く（Subtract Before You Add）。目標の形に届く最小の変更を出荷する（Laziness Protocol）。「効果があるかもしれない」予測の整理は戻す。
5. 振る舞いを保つ小さな一歩ずつ動かし、そのたびに固定を緑に保つ。API の作り変えでは、すべての呼び出し元を移し、同じ波で古い API を消す（Migrate Callers Then Delete Legacy APIs）。互換の shim も、新旧の並行経路も置かない。改名はすべて実際のファイルで抜き取り確認する。改名は文字列・文章・逆参照の中の使用を黙って取りこぼす。機械的な編集は、範囲（ファイルのパス、動かす名前、保つ振る舞い）を具体的にしてサブエージェントに委任してよい（`task-feature.md` の「サブエージェントに任せるとき」）。
6. 振る舞いが変わっていないことを、「コンパイルが通った」で済ませず実物で証明する（Prove It Works）。大きな作り変えでは等価性の確認を回す。新旧の出力を diff するスクリプト、記録した基準を新しいコードで再生する、変更した面での smoke 実行。
7. 残す価値があるかを確かめる。成功の物差しは、読み手の負荷が減ったこと（Minimize Reader Load）。差分がどこかで読み手の負荷を下げていないなら、design が決めた作り変えを apply の判定で取り消さない。読み手の負荷の差を添えて、`openspec-propose` へ戻す判断事項として報告する。
8. 小さく順序立ったコミットに整える。引き算のコミット、作り変え、続く整理の順。Sequence Work into Verifiable Units で、振る舞いを保つ各断面を緑にしてから次へ進む。

**返答。** 変わった構造、それを照らした固定、等価性の証明、読み手の負荷の差、出荷したものと戻したもの。新しい振る舞いはない。

原則名の中身は `architect:35-architect-principle` の `references/principles/` にある。

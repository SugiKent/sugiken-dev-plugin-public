# 不具合を直す task（バグ修正）

`openspec-apply-change` の手順 7 で、不具合を直す task に使う。pstack の poteto-mode の Bug fix playbook と `tdd` skill を、apply の中で使う形にしたもの。

**この作業の責任は自分が持つ。計画し、レビューし、確かめる。** 調査と修正はサブエージェントに委任してよい（`task-feature.md` の「サブエージェントに任せるとき」）が、主導は手放さない。

科学的に進める。出荷する行はすべて、実行時の証拠にたどれなければならない。「効果があるかもしれない」念のための二重の備えは仮説であって修正ではないので、出荷しない。証拠が仮説を否定したら、その仮説から入れた変更を戻す。証拠が正当化する最小の変更だけを出荷する。

1. 変更した面と同じ面で、自分で再現する。デバッグや計装の手順書が「利用者に再現してもらう」と言っていても、自分で再現する。人間に頼むのは、自分の手段がその対象に届かない具体的な理由を書けて、その手段で行けるところまで行った後だけ。直接再現しないなら、きっかけを合成する、条件を絞る、計装して発火するまで粘る。
2. 原因を二分探索する。候補の仮説を並べ、一つが残るまで潰す。仮説の種は、`architect:35-architect-sketch` の `references/grounding.md` の「仕組みを説明する」（触るサブシステム）と「経緯を掘る」（退行の経緯）から得る。毎回、残る問題空間をいちばん大きく削る分け方を選び、実行時の証拠を取り、潰す。プログラムの状態がはっきりしないなら、計装やログを足し、コードが動く間に読む。推測しない。長い・しぶとい探索は `/loop` で回す。手順 3 で設計の探索やレビューを広げる前に、残った**仕組み**を実行時の証拠で確かめる。
3. 修正を計画する。修正が関数の境界をまたぐなら、先に `architect:35-architect-sketch` を回す。実装は範囲を具体的にしてサブエージェントに委任してよい。
4. 同じ面で確かめる。元の再現が今は通る。「INCONCLUSIVE」や別の面での確認は合格ではない。そう明記する。ユニットテストは分岐の振る舞いを示すが、バグがないことは示さない。
5. git の履歴で、失敗する再現が修正より先に入るようにコミットを並べる。安いローカルのテスト経路があるなら、下の「失敗するテストを先に書く」に従う。テストが高い、統合が重い、不明瞭なら飛ばす。これが Sequence Work into Verifiable Units の基本形（失敗するテストが先で、その上に修正）。
6. コミットは `basic:20-commit-meaningful-diffs` に従う。

**返答。** 何が壊れていたか、根本原因、修正、確かめ方。失敗してから通るまでの再現の出力を、そのまま貼る。

## 失敗するテストを先に書く

pstack の `tdd` に当たる手順。明確で安いテスト経路があるバグにだけ使う。目的は、修正前に落ち、修正後に通る、焦点の絞れた回帰テスト。

テストが現実的でないなら無理に作らない。広いテスト基盤の準備、壊れやすいモック、遅い E2E 基盤、本番にしかない状態、曖昧な再現手順、無関係な fixture の大量変更が要るなら、新しいテストは足さず、いちばん近い有用な検証を使う。

1. **バグを理解する。** 意図した振る舞い、今の振る舞い、影響する経路、観測できる最小の再現を特定する。
2. **いちばん狭い実行可能な確認を選ぶ。** その経路で既に使っている単体・コンポーネント・統合・回帰のテストに近いものを選ぶ。現実的なテスト経路が見当たらないなら、手順を満たすためだけにゼロから作らない。
3. **失敗するテストを先に書く。** そのバグを捕まえられた最小のテストを足す。今の実装を写さず、意図した振る舞いを書く。
4. **直す前に新しいテストを走らせる。** 意図した理由で落ちることを確かめる。通ってしまう、または無関係な理由で落ちるなら、実装を触る前にテストか再現を直す。
5. **バグを直す。** 周りの約束を保ったまま、意図した振る舞いを満たす最小の本番コードの変更をする。
6. **回帰テストを走らせ直す。** 通ることを確かめる。

失敗するテストが現実的でないときは、いちばん近い実行可能な回帰確認（狙いを絞ったスクリプト、再現のコマンド、ブラウザの自動操作、スナップショットの比較、ログの assert、焦点を絞った統合確認）を使う。悪いテストよりテストなしを選ぶ。悪いテストとは、主にモックを確かめる、今の実装の詳細を書き写す、タイミングや無関係なグローバル状態に依存する、小さな修正に高い基盤を要する、修正を証明した直後に消されるテストのこと。

- 誤った実装に合わせるためにテストを変えない。
- 期待する振る舞いが本当に変わり、その理由が明確なとき以外、既存の assert を弱めない。
- 回帰テストはそのバグに絞る。広い fixture の変更や無関係なカバレッジの拡大を避ける。
- 不安定なバグなら、できるだけ決定的なテストにし、何の信号を固定したかを書く。
- バグがより広い故障の型を示すなら、まず焦点を絞った回帰の経路を入れ、それから兄弟のケースを考える。

返答には、修正前に落ちたテストかその確認と、出た失敗、修正後に通った実行と周辺の確認を書く。修正前の失敗を示せなかったなら、その理由と、代わりに使った回帰確認を書く。

原則名の中身は `architect:35-architect-principle` の `references/pstack-principles/` にある。

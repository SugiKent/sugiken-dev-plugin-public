# 判断の記録（show-me-your-work）

`openspec-apply-change` を無人実行（Routine など）や長い作業で回すとき、人間が離席して後で確かめる作業で、レビューできる判断の記録を残す。pstack の `show-me-your-work` に当たる。正本の記録は 1 つにする。

## 形式

1 つの TSV ファイルに、判断 1 つにつき 1 行を書く。各セルは 1 行に収める。証拠は文章で書かず、場所を指す。

列は次のとおり。

- **ts。** ISO 8601 のタイムスタンプ。
- **phase。** 段階か作業の流れ。
- **decision。** 選んだこと・したことを 1 行で。
- **why。** 平易な言葉での理由。原則に導かれたなら、原則名の略号に頼らず、平易な言葉で書く。
- **evidence。** それを証明するリンクかパス。コミットの SHA、PR 番号、`file:line`、成果物・トレース・スクリーンショットのパスを書き、段落は書かない。
- **result。** 結果か完了条件の状態。`テスト緑`、`戻した`、`ピクセル差 0`、`INCONCLUSIVE`、`未決`。

例。レビュアーが一目で読めるよう、平易に書く。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先に作業量を数えた。部品が約 100、工数は約 75 時間	長い作業を始める前に大きさを知りたかった	commit 3a9f1c2	始める前に片付ける点が 5 つ見つかった
2026-05-24T09:40:00Z	harness	何かを変える前に旧版のスクリーンショットを撮った	新旧を比べ、見た目の変化を捕まえるため	scripts/snapshot.sh, baseline/	基準のスクリーンショットを 120 枚保存
2026-05-24T11:15:00Z	widget	見た目を変えずに widget のスタイルを移した	変更を小さく、結果を同一に保つため	commit 7c21e0a, pixel-diff 0	見た目は同一、テストも通る
2026-05-24T12:30:00Z	widget	補助エージェントの作業を捨てた。スクリーンショットが真っ白だった	要約を信じず実際のファイルを確かめた	worktree を reset	戻した。次回のために指示を締めた
```

## 1 行を書く

同僚に何をしたかを話すように書く。平易な言葉、具体的な行動、AI くさい言い回しや抽象的な専門語は使わない（`report-writing.md` が記録の文にも当てはまる）。

`../scripts/decision-log.sh <logfile> <phase> <decision> <why> <evidence> <result>` を使う。`ts` を付け、初回はヘッダを書き、紛れ込んだタブと改行を取り除き、`=`・`+`・`-`・`@` で始まるセルに単引用符を前置する。素の `printf` で追記してもよいが、セルが生成された文字列や利用者の入力から来るなら、同じバイトに気を付ける。

記録するのは、判断の分かれ目と確認点。すべての行動を書くと、読み手が分かれ目を探せなくなる。対象は、選んだ分岐、検証結果付きで終えた単位、きっかけ付きの方針転換や巻き戻し、表に出した障害、直した関門。ループの実行では 1 回の反復につき 1 行。些細で自明なものは飛ばす。

1 回の実行（run）とは、1 つのエージェントの会話のこと。後のターンと、その会話の要約も含む。引き継ぎ、交代したエージェント、新しい会話は新しい実行になる。既に行がある記録に追記するとき、その実行の最初の行は phase を `start` にする。別の実行の `start` 行の後に書く最初の行も同じ。そのため、後のターンで記録に戻ってきた実行は、まず記録の最後の数行を読み、別の実行が書いていないかを確かめる。`start` 行は、それより前にあって自分が書いていない行の `ts` の範囲を名指しし、evidence に自分の実行（エージェントの id など）を書く。`start` をほかの用途に使わない。

## 置き場所

既定では記録は作業用の成果物で、コミットしない。作業ディレクトリの `decisions.tsv`、複数の作業が同時に走るなら `.audit/<作業の slug>.tsv` に置き、git から外す。

コミットするのは、レビュアーが結果を信頼するために記録が要るほど大きな作業のときだけ。

## 規則

- 追記のみ。誤った判断には、それを上書きする新しい行を足す。履歴を編集・削除しない。
- 手作りの一度きりの証拠より、コミットしたスクリプトが出す証拠を選ぶ（Encode Lessons in Structure）。

## 記録を会話記録と突き合わせる

実行の最後、返す前に、記録が真実を語ったかを確かめる。この実行の会話記録を読む。Claude Code では `~/.claude/projects/<作業ディレクトリのパスの / と . を - に変えた名前>/` の直下にある最新の `.jsonl` が今のセッションになる。ほかのプロジェクトのディレクトリを横断して glob しない（無関係な私的な会話を読むことになるため）。この実行の行を、実際に起きた出来事と照らす。

- どの行も、実際の判断か行動に対応しているか。
- 各行の証拠がたどれて、行の主張どおりのものを示すか。
- 作業を形作ったのに記録されていない分岐・方針転換・捨てたやり方は欠落なので、足す。

直すのは記録の側で、話を記録に合わせて作り直さない。突き合わせで行を編集・削除しない。でっち上げの行でも消さない。実際の判断も行動も記録していない行や、主張か証拠が誤っている行には、実際に起きた出来事と、たどれる場所を書いた行を足して上書きする。

## 別系統のモデルに記録を見せる

返す前に、作業をしたモデルとは別系統のモデル（Codex MCP など。使えなければ別の Claude モデル）のサブエージェントを起動する。自己レビューは代わりにならない。サブエージェントは記録とこの実行の会話記録を読み、利用者が注意すべき点を挙げる。サブエージェントは作業をやり直さず、最適でない点や危ない点を探す。

- 証拠が弱いか、ない判断。
- 飛ばされた検証、会話記録に証明がないのに主張された検証。
- 振り返ると危ない選択（早すぎる、範囲が広がっている、症状に蓋をしている）。
- ざっと見ただけでは利用者が見落とす欠落。

記録を残した実行の返答は、最後に「注意点」の節で終える。先頭の行にレビューしたモデルを書き（`レビュー: <モデル>`）、続けて各指摘を、該当する行か場面を指して並べる。「指摘なし」は正当な値だが、モデル名は省かない。

## 記録を読む

上から下へ読み、証拠の場所をたどり、抜き取りで確かめる。GitHub はコミットした TSV を表として表示する。端末では `column -s$'\t' -t decisions.tsv` で表にできる。

## ほかの skill から使う

記録を残す skill は、独自の形式を作らずこのファイルを名前で参照し、形式を任せる。列を書き写さない。

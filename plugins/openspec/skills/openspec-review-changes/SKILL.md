# OpenSpec Changes 横断レビュー

現在アクティブな `openspec/changes` をすべて読み、個々の change の内部整合性と、change 同士の横断整合性を確認する。

このレビューの目的は、指摘を並べることではない。実装者が推測しなければ進められない判断、change ごとに異なる前提、競合する要求を、人間との対話で一つずつ確定し、未解決の疑問をゼロにすることである。

## 守るルール

- 質問は **1 フェーズにつき最大 3 問** にする。
- 質問による追求には `basic:grill-me` スキルを使う。その判断ツリーを一枝ずつ深掘りするプロトコルを、このレビューの未解決台帳へ適用する。
- `basic:grill-me` は一度に一問を基本とする。独立して回答できる問いをまとめる場合でも最大 3 問までとし、依存関係のある問いは必ず一問ずつ尋ねる。
- 一つの質問には、一つの独立した判断だけを含める。質問数制限を回避するために複数の判断を一問へ詰め込まない。
- 回答から新しい疑問や矛盾が生まれ得るため、各回答フェーズの後に全 change を再監査する。
- 「一般的には」「おそらく」で仕様を確定しない。判断が分岐するなら質問する。
- ユーザーの回答が曖昧、条件付き、または既存成果物と矛盾する場合、その疑問を解決済みにしない。次のフェーズで、より具体的に問い直す。
- 未解決の疑問が一つでもある間は、レビュー完了や実装準備完了を宣言しない。
- ユーザーが明示的に中止・保留を求めた場合は従う。ただし、残った疑問を明示し、完了とは扱わない。
- このスキルではアプリケーションコードを実装しない。
- OpenSpec 成果物の編集は、ユーザーが整合・修正・反映まで依頼している場合だけ行う。レビューだけを依頼された場合は、確定事項と必要な修正を最終レポートにまとめる。

## ストアの選択

ユーザーがストアを指定した場合、または作業が登録済みストア内にある場合は、最初に次を実行する。

```bash
openspec store list --json
```

対象ストアの id を特定し、`list`、`status`、`show`、`validate` など対応するコマンドへ `--store <id>` を渡す。ストアを使わない場合は、最も近いローカルの `openspec/` ルートを対象にする。

## 手順

### 1. 全 change を棚卸しする

```bash
openspec list --json
```

archive 済みを除く、現在アクティブな change を全件対象にする。ユーザーが一部だけを指定しても、指定範囲の外に競合や前提 change がないか一覧全体を確認する。

アクティブな change がなければ、その事実を伝えて終了する。

### 2. 各 change の成果物を解決して読む

各 change について次を実行する。

```bash
openspec status --change "<name>" --json
openspec show "<name>" --json
```

status JSON の `changeRoot`、`artifactPaths`、`actionContext`、`artifacts` を使い、存在する成果物をすべて読む。`proposal.md`、`design.md`、`tasks.md` などの固定名だけに依存せず、選択されたスキーマが返すパスに従う。

必要に応じて、関連するメイン spec、プロジェクト設定、既存コードも読む。change の記述だけでは、既存仕様との衝突や実現不可能な前提を見落とすためである。

### 3. change 単体を監査する

各 change 内で、少なくとも次を確認する。

- proposal の目的・スコープと spec の要件が一致しているか
- design の判断が spec の全シナリオを満たすか
- tasks が proposal、spec、design の内容を漏れなく実現するか
- 用語、命名、主体、状態、データ型、境界条件が成果物間で一貫しているか
- 正常系だけでなく、失敗、空状態、権限不足、再試行、重複実行、移行、後方互換性が定義されているか
- 未定、TBD、選択肢の併記、根拠のない前提、解釈が複数ある文が残っていないか
- 完了条件と検証方法が、実装者による推測なしに判定できるか

### 4. change 間を横断監査する

全 change を比較し、少なくとも次を確認する。

- 同じ capability、Requirement、画面、API、テーブル、イベント、設定、共通コンポーネントを変更していないか
- 同じ対象に異なる名前、型、状態遷移、責務、認可規則、エラー契約を定義していないか
- 一方が追加するものを、他方が削除・改名・別形式へ変更していないか
- 実質的に同じ機能を重複提案していないか
- 暗黙の先行 change がないか。実装順、migration 順、release 順が明記されているか
- 複数 change を個別に apply すると成立しても、すべて適用した最終状態で矛盾しないか
- tasks が同じファイルや境界を異なる方針で編集し、マージ競合や責務の重複を起こさないか
- ある change の前提が、別 change の未確定事項に依存していないか

必要なら次のようなマトリクスを内部で作る。

```text
change × capability
change × API/route
change × data model
change × UI/state
change × shared file/module
change × dependency/order
```

### 5. 未解決台帳を作る

見つけた疑問を、内部の未解決台帳で追跡する。

```text
ID:
対象 change:
関連 change:
根拠となるファイル・記述:
疑問または矛盾:
放置した場合の影響:
必要な一つの判断:
状態: open | answered-needs-audit | resolved
決定:
反映先:
```

表現の違いだけで意味が同じものは統合する。一方で、独立して選べる判断は別の項目にする。

### 6. 質問フェーズを実行する

ここからは `basic:grill-me` スキルを使用する。このスキル独自の質問術を再実装せず、次の OpenSpec 固有コンテキストを渡して追求する。

- インタビュー対象: 未解決台帳にある判断
- 判断ツリーの枝: change、capability、API、data model、UI/state、依存・実装順
- 事実確認元: 全 change の成果物、メイン spec、プロジェクト設定、既存コード
- 終了条件: 延期された判断も含め、全 change の未解決項目がゼロ
- 行動制約: 共有理解が確認されるまで、実装や成果物の編集を始めない

`basic:grill-me` 単体では判断の明示的な延期を許容するが、この横断レビューでは延期を完了とみなさない。すべての change の疑問を解消するという目的に反するため、延期された項目は open のまま保持する。ユーザーがレビューを中止・保留した場合だけ対話を止め、レビュー未完了として報告する。

open の疑問から、次の順で最大 3 問を選ぶ。

1. 回答によって他の疑問が消える、または分岐する上流判断
2. 複数 change の競合、データ損失、セキュリティ、後方互換性に関わる高影響判断
3. 実装順や共通契約を決める判断
4. 個別 change 内の詳細判断

質問には次を含める。

- どの change と記述が根拠か
- 何が両立しない、または未確定なのか
- 決めないと何が起きるか
- 答えてほしい一つの判断
- 根拠付きの推奨案と、実質的に異なる選択肢

質問の形式と進め方は `basic:grill-me` に従う。原則は一度に一問である。最大 3 問を同じフェーズに含めてよいのは、互いの回答で選択肢や意味が変わらない、完全に独立した判断だけである。

出力例:

```markdown
## 質問フェーズ 2 — 残り 7 件

### Q1: ユーザー状態の正本はどちらですか？
`change-a/design.md` は `users.status`、`change-b/specs/account/spec.md` は
`memberships.state` を認可判定の正本にしています。両方を独立更新すると状態がずれます。

推奨は `memberships.state` です。組織ごとの所属状態を表現できるためです。

- `memberships.state` に統一する
- `users.status` に統一する
- 両方を保持し、同期規則を新たに定義する
```

### 7. 回答を反映して、全体を再監査する

各回答について次を行う。

1. 回答が質問に対する確定判断か確認する。
2. 関連する台帳項目を `answered-needs-audit` にする。
3. その判断を前提に、対象 change だけでなく全 change を再監査する。
4. 派生した疑問を新しい open 項目として追加する。
5. 矛盾なく閉じた項目だけを `resolved` にする。
6. open が残るなら、次の質問フェーズへ進む。

ユーザーが「任せる」「推奨でよい」と明示した場合は、提示した推奨案を決定として扱ってよい。明示的な委任がないまま、回答を補完してはならない。

成果物の修正まで依頼されている場合は、確定した判断を関連する proposal、spec、design、tasks のすべてへ一貫して反映してから再監査する。判断を一つのファイルだけへ追記して、他の矛盾を残してはならない。

### 8. 完了監査を行う

質問が尽きたように見えても、最後に白紙からもう一度確認する。

- 全アクティブ change と全成果物を対象にしたか
- 単体監査と横断監査の全観点を再確認したか
- open / answered-needs-audit の台帳項目がゼロか
- 回答同士に矛盾がないか
- 確定事項によって新しい未定義の境界条件が生じていないか
- 各 change の実装順と依存関係が一意に説明できるか
- 各 change の受け入れ条件が検証可能か

成果物を編集した場合は、各 change を検証する。

```bash
openspec validate "<change-name>"
```

validation error は未解決として扱い、修正または質問を続ける。

## 完了条件

次をすべて満たした場合だけ完了とする。

- 全アクティブ change の全成果物を確認した
- change 内・change 間の未解決台帳がゼロ
- 回答後の再監査と最終の白紙監査を完了した
- すべての確定判断、依存順、競合の解消方法を説明できる
- 成果物を編集した場合、全 change の validation が成功した

## 完了時の出力

```markdown
## OpenSpec Changes 横断レビュー完了

**対象:** N changes
**質問フェーズ:** N 回
**解決した疑問:** N 件
**未解決:** 0 件

### 確定した横断ルール
- ...

### Change ごとの確定事項
#### `<change-name>`
- ...

### 依存・実装順
1. ...

### 成果物への反映
- 反映済み: ...
- レビューのみの場合に必要な修正: ...

すべての change について、未解決の疑問はありません。
```

ユーザーが途中で終了した場合は、解決済み・未解決・次に尋ねるべき質問を分けて出力し、「レビュー未完了」と明記する。

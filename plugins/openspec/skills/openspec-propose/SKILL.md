新しい change を提案し、選択された OpenSpec スキーマが要求する成果物を生成する。

成果物の種類・順序・完了条件はスキーマから取得する。`proposal.md`、`design.md`、`tasks.md` を固定で仮定しない。

実装の準備ができたら、`openspec-apply-change` スキルでその change の tasks を進められる。

**進め方:** 下の手順 1〜5 の太字の行と、後述の「設計の形を決める」「徹底的な疑問点の解消について」「レビュー」の見出しを、そのままタスクリストに写す。やらない手順も消さず、`skip: <理由>` を添えて残す。手順を飛ばしたことが後から見えるようにするため。各手順は、次の skill と参照を必要な場面で読む。apply から戻ってきたときは、手順 1〜5 の代わりに後述の「apply から戻ったとき」を写す。

| 場面 | 使うもの |
|---|---|
| 要求の言い直しと判断の詰め | `basic:grill-me`（動かせば分かる分岐は、その `references/prototype.md` で試作する） |
| データの形と設計 | `architect:35-architect-sketch`、`architect:35-architect-principle` の「pstack の原則」 |
| レビュー | `architect:35-architect-doubt-driven-development` ほか `35-architect-*`。指摘の仕分けは `architect:35-architect-interrogate` の「手順 5. リードとして判定する」 |
| 要約 | `openspec-apply-change` の `references/report-writing.md` |
| 無人実行・長い作業での判断の記録 | `openspec-apply-change` の `references/decision-trail.md` |

apply は判断しない。仕様・設計の判断、数値の根拠になる実測、AI の仮置きの確定は、後述の「apply に判断を残さない」に従い、すべてこの propose の中で済ませる。

**ストアの選択:** ユーザーがストア（このマシンに登録された単体の OpenSpec リポジトリ）を指定した場合、または作業がストア内にある場合は、`openspec store list --json` を実行して登録済みストアの id を調べ、specs や changes を読み書きするコマンド（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`）に `--store <id>` を渡す。他のコマンドはこのフラグを取らない。コマンドが出力するヒントには既にフラグが含まれているので、後続でもそれを維持する。ストアがなければ、コマンドは最も近いローカルの `openspec/` ルートに対して作用する。

**入力**: ユーザーのリクエストには、change 名（kebab-case）または作りたいものの説明を含めるべき。

**手順**

1. **明確な入力がなければ、何を作りたいか尋ねる**

  **AskUserQuestion ツール**（自由記述、選択肢なし）で次のように尋ねる:
  > 「どの change に取り組みたいですか？作りたいもの・直したいものを説明してください。」

   その説明から kebab-case の名前を導く（例: 「add user authentication」→ `add-user-auth`）。

   **重要**: ユーザーが何を作りたいかを理解せずに先へ進んではならない。
2. **change ディレクトリを作成する**
  ```bash
   openspec new change "<name>"
  ```

   これは CLI が解決する planning home に、`.openspec.yaml` 付きの雛形 change を作成する。
3. **成果物のビルド順序を取得する**
  ```bash
   openspec status --change "<name>" --json
  ```

   JSON をパースして次を得る:
  - `applyRequires`: 実装前に必要な成果物 ID の配列（例: `["tasks"]`）
  - `artifacts`: すべての成果物とその状態・依存関係のリスト
  - `planningHome`、`changeRoot`、`artifactPaths`、`actionContext`: パスとスコープのコンテキスト。リポジトリローカルのパスを仮定せず、これらを使う。
4. **グリリングで判断を詰め、apply に必要な成果物を順に作成する**

  成果物の本文を書き始める前に、後述の「徹底的な疑問点の解消について」を実施する。design を書く前に、後述の「設計の形を決める」を実施する。成果物が CLI 上で done になっても、グリリングの完了条件を満たすまでは提案を確定しない。

  依存順に成果物をループする（未解決の依存を持たない成果物から先に）:

   a. `**ready`（依存が満たされた）成果物ごとに**:
      - 指示を取得する:
        `bash       openspec instructions <artifact-id> --change "<name>" --json`       
      - 指示の JSON には次が含まれる:
        - `context`: プロジェクトの背景（あなたへの制約 - 出力に含めない）
        - `rules`: 成果物固有のルール（あなたへの制約 - 出力に含めない）
        - `template`: 出力ファイルに使う構造
        - `instruction`: この成果物タイプ向けのスキーマ固有のガイダンス
        - `resolvedOutputPath`: 成果物を書き出す解決済みのパスまたはパターン
        - `dependencies`: コンテキストとして読むべき完了済みの成果物
      - コンテキストとして、完了済みの依存ファイルを読む
      - `template` を構造として成果物ファイルを作成し、`resolvedOutputPath` に書き出す
      - `context` と `rules` は制約として適用する - ただしファイルにコピーしない
      - 短い進捗を表示する: 「Created <artifact-id>」

   b. `**applyRequires` の全成果物が完了するまで続ける**
      - 各成果物を作成した後、`openspec status --change "<name>" --json` を再実行する
      - `applyRequires` の各成果物 ID が artifacts 配列で `status: "done"` になっているか確認する
      - `applyRequires` の全成果物が done になったら止める

   c. **成果物にユーザー入力が必要な場合**（コンテキストが不明瞭）:
      - 後述のグリリングに戻り、関連する判断とその依存先を問い直す
      - 共有理解を確認してから、影響を受ける成果物を更新する
5. **最終状態を表示する**
  ```bash
   openspec status --change "<name>"
  ```

**出力**

全成果物を完成させた後、次を要約する:

- change 名と場所
- 作成した成果物のリストと簡単な説明
- 準備状況: 成果物の作成状況と、グリリングで共有理解を確認できたかを別々に示す。未解決判断が残る場合は草案・回答待ちとし、「実装の準備ができた」と宣言しない
- 「apply に判断を残さない」の結果。実測した数値とその方法、スクリプトが何も返さなかったこと（残した行があればその理由）を示す。無人実行なら、AI が既定で確定した選択を、理由と代わりに指示できることを添えて並べる
- 試作で決めた分岐があれば、その分岐と証拠（スクリーンショットのパス、観察した出力やタイミング）を示す
- 適用した原則と、それで変わった選択。挙げるのは、このセッションでファイルを読んだ原則だけ
- 次の選択肢: 「実装を依頼する」または「`openspec-apply-change` スキルで tasks を進める」

要約は `openspec-apply-change` の `references/report-writing.md` で書く。誰のための change で、その人に何が変わるかを先に書く。

**成果物作成のガイドライン**

- 各成果物タイプについて `openspec instructions` の `instruction` フィールドに従う
- スキーマが各成果物に含めるべき内容を定義しているのでそれに従う
- 新しい成果物を作る前に、依存する成果物をコンテキストとして読む
- 出力ファイルの構造として `template` を使う - そのセクションを埋める
- **重要**: `context` と `rules` はあなたへの制約であって、ファイルの内容ではない
  - `<context>`、`<rules>`、`<project_context>` ブロックを成果物にコピーしない
  - これらはあなたが書く内容を導くが、出力に現れてはならない

**ガードレール**

- 実装に必要な全成果物を作成する（スキーマの `apply.requires` が定義する通り）
- 新しい成果物を作る前に、必ず依存する成果物を読む
- コンテキストが決定的に不明瞭なら、ユーザーに尋ねる
- その名前の change が既に存在するなら、継続するか新規作成するかをユーザーに尋ねる
- 各成果物ファイルを書いた後、次へ進む前にファイルの存在を確認する
- [tasks.md](http://tasks.md) のタスク量は30を最大とし、それを超える場合は change の分割を検討する

# apply に判断を残さない

apply は、propose で決めたことを実行し、propose で決めた基準で確かめるだけにする。apply の途中で決めた判断は、グリリングとレビューを通らないまま仕様に入り、成果物にも残らないため。apply の途中で次の判断が求められることがよくあるが、3 つともすべて propose の間に済ませる。

1. **仕様・設計の判断。** 誰に何が見えるか（画面の文言を含む）、何が起きるか、データの形、モジュールの境界、失敗したときの振る舞い。実装の形が複数ありうる箇所（エラー処理、抽象の層、テストの構造）も含む。グリリングと「設計の形を決める」で決め、成果物に書く。
2. **数値の根拠になる実測。** 上限、しきい値、タイムアウト、件数、間隔、性能の予算のように数値で決める値は、根拠を付けて propose の間に決める。測れる値は、試作、計測スクリプト、既存データの集計、ログの読み出しで測り、測った方法・実行回数・値を design に残す（`architect:35-architect-principle` の Explain the Number）。測っても決まらない製品判断の値（1 ページの件数など）は、グリリングで利用者が決めたことを根拠に書く。本番でしか測れない値は、その理由と、代わりに置く値の根拠を design に書く。
3. **AI の仮置き。** 「とりあえず X にして apply で調整する」「TBD」「実装時に決める」を成果物に残さない。決めるか、グリリングで尋ねる。無人実行で人に尋ねられないときは、`basic:grill-me` の「全面委任・無人実行のとき」に従い、propose の中で既定の選択を確定させ、理由と代わりの指示の仕方を書く。

apply が決めてよいのは、spec と design のどの文も書き換えない局所の選択だけ。private な補助関数の切り出しと名前、関数の中の制御の書き方、局所変数の名前、design が決めたテストの層の中でのテストケースの分け方、既存コードの慣習に合わせる書き方がこれに当たる。公開 API、データの形、利用者に見える振る舞いと文言、数値、モジュールの境界に触れる選択は、ここで決める。どちらか迷う選択は、それが spec か design の文を書き換えるかで分ける。

提案を確定する前に、成果物に apply へ判断を回す言葉が残っていないかを `scripts/check-undecided.sh` に `<changeRoot>` を渡して機械的に確かめる。当たった行を出して終了コード 1 で終わり、何もなければ 0 で終わる。型のスケッチを置く `sketch/` は対象から外れる。

当たった行は、決めて書き直すか、グリリングに戻す。仕様が使う言葉（「暫定トークン」という用語など）で当たった行だけは残し、残した理由を要約に書く。

# apply から戻ったとき

`openspec-apply-change` が判断の要る場面で一時停止し、この skill へ戻してきたときの手順。既にある change を詰め直すだけなので、手順 1〜5 はやり直さない。

1. **apply の一時停止報告を読む。** 決まっていない判断、それが止めている task、apply が集めた証拠（再現の出力、レビューの指摘）を入力にする。
2. **同じ change を使う。** `openspec new change` は実行しない。続きだと分かっているので、ガードレールにある「継続するか新規作成するか」の確認もしない。
3. **止まった判断とその依存先だけを詰める。** 判断ツリーのうち、その判断と、それに依存する枝だけを「徹底的な疑問点の解消について」の基準で詰め直す。決まった枝は掘り直さない。形を決め直すなら「設計の形を決める」を回す。
4. **影響を受ける成果物を直す。** design・specs・tasks を直す。直した判断が完了済みの task の中身を変えるなら、その task のチェックを外し、外した理由を tasks に書く。
5. **確かめ直す。** 「apply に判断を残さない」のスクリプトを回し直し、直した範囲に `architect:35-architect-doubt-driven-development` のレビューを回す。
6. **apply へ返す。** 何を決め、どの成果物のどこを直したかを要約し、`openspec-apply-change` の手順 4 から再開する。

無人実行で apply が止まったときは、apply を呼んだ呼び出し元（Routine やオーケストレーター）がこの節を回す。呼び出し元が propose を回せないなら、apply の一時停止報告をそのまま人への報告にして終える。

# tasks に含めてはならないもの

tasks.md は **change を archive するための完了条件**であり、本番運用で当然行うことの記録場所ではない。次のタスクを作らない。

- **本番環境で実測・確認するタスク**（「本番でレスポンスタイムを計測する」「本番環境で動作を確認する」など）。本番確認は当たり前に行うが、propose の完了条件ではなく、それを待たずに archive する。例外は、本番環境固有の構成（本番だけに存在するインフラ・外部サービスの本番アカウント・本番データ量）でしか検証しようがない場合のみ。その場合も task は、propose で決めた基準を本番で確かめるだけにする。測った値で何かを決め直す task にはしない。
- **人間が手で動作確認するタスク**（「画面を開いて目視確認する」「手動で一連の操作を試す」など）。よほど複雑で自動検証が現実的に組めない場合を除き、作らない。
- **apply の中で判断・実測して決めるタスク**（「〜を検討する」「値を測って決める」「挙動を調整する」「方式を選ぶ」など）。tasks は、決まったことの実行と、決めた基準での確認だけで書く。決めることが残るなら、前述の「apply に判断を残さない」に戻る。

検証タスクを置く場合は、自動テスト（ユニット / 統合 / E2E）やローカル・開発環境で完結する確認に置き換える。

# tasks の並べ方と検証

tasks は、それぞれ確かめられる状態で終わる小さな単位の列にする（`architect:35-architect-principle` の Sequence Work into Verifiable Units）。壊れたものを、それを起こした task で捕まえれば場所の特定が安いため。

- 各 task に、それを確かめる証拠（実行するテスト・コマンド・E2E のシナリオ）を書く。証拠を書けない task は、分け方か中身が曖昧になっている。
- 並べ方で作業を証明する。使われなくなるコードの削除を作り変えより先に、足場（共有の型、テスト基盤、migration）を機能より先に置く。バグ修正では、失敗するテストか再現を修正より先に置く。
- ユニットテストが通っただけを、利用者に見える振る舞いの検証にしない。利用者が触る面を変える change では、その面を自動で動かす確認を task に入れる。変更の種類ごとの確かめ方は `openspec-apply-change` の「9. 実物で確かめる」に従う。
- 一時的な互換コードで途中の状態を守る task を作らない。古い API を置き換えるなら、呼び出し元の移行と古い API の削除を同じ change に入れる（Migrate Callers Then Delete Legacy APIs）。

# プロジェクト固有の制約

テスト種別、動作確認、依存サービス、ランタイムやライブラリのバージョン、静的解析は、OpenSpec のスキーマ・プロジェクト設定・ユーザー要求に従う。スキル自身がユニットテストのみ、特定のコンテナ構成、特定のメールツール、または特定の検証手順を一律に要求しない。

# 先行・関連する change との依存関係について

新しい提案は単独では存在しない。既存の先行 change や他の change の内容を踏まえずに書くと、**重複した提案・矛盾する spec 変更・実装順序の取り違え**を生む。新しい提案を書き始める前に、既存 change の内容を必ず確認し、判明した依存・競合・前提を proposal / design / tasks の全体にわたって一貫した制約として反映する。

- **既存 change の確認手順**: まず `openspec list --json` で現在の change 一覧を取得し、今回の提案と関連しそうな change（同じ spec・同じ機能領域・同じデータ構造を触るもの、または前提となる基盤変更）について `openspec show <other-change> --json` で中身を読む。特に proposal.md（何を・なぜ）と spec の delta（どの spec をどう変えるか）を確認する。
- **前提となる change**: まだ archive されていない先行 change の spec 変更やデータ構造に依存する場合、その依存を proposal / design に明示し、実装順序（どちらを先に apply すべきか）を tasks に反映する。
- **競合する change**: 同じ spec の同じ箇所を別の change が変更している場合、パターンを混在させず、どちらに従うかを決めてから書く。判断が分岐する場合はユーザーに確認する。
- **重複する change**: 既存 change が今回のリクエストを既にカバーしている場合は、新規作成せず既存 change の継続を提案する。

# マイグレーション設計について

提案がデータ構造の変更（テーブル・カラムの追加/変更/削除、データ形式の変換など）を伴い migration が必要になる場合、設計を確定する前に「過去データを破棄できるか」を `AskUserQuestion` でユーザーに確認する。破棄可否は移行方式（そのままドロップできるか、変換・バックフィルが要るか）を左右するため、確認せずに設計へ進まない。

# 設計の形を決める

design を書く前に、データの形を名指しし、それをまとめる構造を `architect:35-architect-principle` の Model the Domain で選ぶ（散らばった真偽値より状態機械、分岐より表や登録簿、繰り返す形の前提より型付きのモデル）。新しい要求は、既存の設計に継ぎを当てず、最初からその要求があった前提で設計し直す（Redesign from First Principles）。足す前に、この change で不要になるものを消せないかを見る（Subtract Before You Add）。

change が関数の境界をまたぐ新しい型・モジュール・公開 API・データの持ち方を伴うなら、`architect:35-architect-sketch` の Phase A と Phase B を回す。

- 構造の異なる候補を少なくとも 2 つ並べ、そのスキルの `references/design-red-flags.md` で選別し、1 つに統合する。
- design.md（スキーマに design がなければ、設計を記録する成果物）の枠は、`openspec instructions` が返す `template` にする。スケッチの根拠（そのスキルの `references/rationale-template.md`）の各節は、template の対応する節に入れ、対応する節がなければ template の後ろに足す。呼び出し側の使い方を型より先に書き、採らなかった形は代替案の節に残す。型のスケッチは change フォルダの `sketch/` に置く。
- 実装に正しい形が複数ありうる箇所（エラー処理、抽象の層、テストの構造）も、ここで競作して決め、design に書く。apply では競作しない。
- Phase C の合意は、この skill のグリリングで行う。スケッチの「未決の問いとリスク」は design に問いのまま残さず、判断ツリーの枝に移す。答えが出たら、決めたことを design の本文に、残るリスクをリスクの節に書く。

既存パターンへの単純な追従や、1〜2 ファイルで済む明白な変更では回さない。その場合はタスクリストの該当項目に `skip: <理由>` を書く。

# デザイン成果物・デザイン指示の取り込みについて

ユーザーのリクエストやこれまでの会話に UI/UX・画面レイアウト・デザインに関する言及がある場合、または画像・HTML・モックアップなどのデザイン成果物が提供されている場合は、それらを一次情報として扱い、design.md と tasks.md に反映する。

- 画像や HTML などデザインの原本は作成中の change フォルダ内に配置して参照できるようにする
- 提供されたデザイン成果物を実際に確認する。画像は Read で見る、HTML は構造とスタイルを読む、会話中のデザイン言及も拾い上げる。
- **design.md**: 対象画面・コンポーネント構成・状態遷移・レイアウト方針を、確認したデザイン成果物に基づいて記述する。デザインが示す UI 要素・画面フロー・インタラクションと design.md の内容が一致するようにする。
- **tasks.md**: デザインを再現するための実装タスク（コンポーネント作成・スタイリング・レスポンシブ対応・状態管理など）を、デザイン成果物の内容を踏まえて具体的に列挙する。
- デザイン成果物と矛盾する記述を成果物に残さない。デザインが曖昧・不足している箇所は、推測で確定せず `AskUserQuestion` で確認する。
- デザイン成果物もデザインに関する言及もない場合、この節は適用しない（架空のデザインを創作しない）。

# UI の文言について

この change が足す・変える、利用者に見える文言（画面、ボタン、空状態、ヘルパーテキスト、ダイアログ、エラー）は、propose で決めて design か specs に書く。文言は誰に何が見えるかを決める仕様なので、apply に残さない。書くときは `stop-describing-ui` スキル（design plugin）に従う。説明文の多い UI は利用者に読む負担を強いるため、操作ラベルと配置で伝える。

# 徹底的な疑問点の解消について

`basic:grill-me` スキルを読み、その意思決定ツリーを一枝ずつ追求する手順を実行する。「不明点はありますか」という包括的な確認や、一巡の質問だけで代用しない。以下は、この change をグリリングするときの対象と完了条件である。

## 事実と意思決定を分ける

関連コード、main specs、進行中 changes、プロジェクトの方針を先に調べる。既にユーザーが明示した判断は引き継ぎ、同じ確認を繰り返さない。調べれば分かる事実をユーザーへ質問せず、根拠のファイル・要求を押さえる。情報にアクセスできなければ未確認として残し、推測を事実扱いしない。

動かせば分かる事実（挙動、タイミング、レイアウト、出力、性能）も、ユーザーの答えることではない。`basic:grill-me` の「質問する前に分ける」に従って試作で決め、判断と証拠を design.md の根拠に残す。抽象的な計画を議論で磨くより、試作で問いを閉じるほうが安く、ユーザーが思い付かなかった選択肢も見つかる。

不具合を直す change では、再現と原因の特定も動かせば分かる事実として、この propose で済ませる。`openspec-apply-change` の `references/task-bug-fix.md` の手順 1・2 で再現して原因を突き止め、原因とその証拠、直す振る舞い、修正の形を design に書く。原因を知らないまま直し方を書くと、apply が直し方を決めることになるため。

一方、資料だけでは決まらない選択は、一般論や推奨案で勝手に確定しない。要求同士、要求と既存実装が矛盾する場合は、その矛盾と影響を示してユーザーに判断を求める。

## 判断ツリーを作り、一枝ずつ掘る

目的・成功条件を根として、対象範囲、利用者と操作、仕様、設計、検証へ判断の依存関係をたどる。各判断について、確定した内容と根拠、未解決の問い、前提となる判断を追跡する。回答を受けるたびにツリーを更新し、その回答で新たに生じた枝や、前提が変わった既決事項を再確認する。

少なくとも次の観点を今回の change に照らして点検する。該当しない観点から架空の要件や質問を作らない。

- 何の問題を誰のために解くのか。成功と失敗をどう判定するか。今回やらないことは何か。
- 用語、対象、責任範囲は一意か。具体的な入力・操作に対して、誰に何が見える／起きるか。
- 正常系だけでなく、空・欠損・不正入力、境界値、権限不足、失敗・再試行・重複・同時実行ではどう振る舞うか。
- データの所有者、状態遷移、整合性、既存データの移行・互換性、外部連携の失敗をどう扱うか。
- main specs や他 change と矛盾・重複しないか。依存する change が未適用でも成立するか。
- 採用案の代替は何か。簡単な案や何も変えない案では不足する理由、採用案で受け入れる不利益は何か。
- 合意した振る舞いをどのシナリオで検証できるか。実装者が追加の仕様判断なしに着手できるか。

## 同意を取るだけで終わらせない

質問は `AskUserQuestion` で一度に一問とし、回答を待つ。判断が必要な背景、具体的な選択肢と影響、根拠付きの推奨回答を添える。前提が未確定の枝の質問を先回りして並べない。

背景や判断材料は質問文に詰め込まず、`AskUserQuestion` の前に通常のメッセージで説明する。事実を質問文に並べると、ユーザーは話の流れと何を決めるのかを掴めないためである。説明には次を含める。

- ここまでの流れ（決まったことを番号付きで振り返る）
- 今決めたいこと
- 判断材料（選択肢ごとの影響などを表で整理する）
- 推奨案と理由

質問文そのものは、今決めたいことを問う短い文にする。

「はい」「いい感じに」「通常どおり」だけでは振る舞いが一意にならない問いは、具体例・境界条件・反例を使って掘り下げる。明確な選択肢への「はい」は回答として受け入れるが、そこから未提示の条件まで同意されたと解釈しない。

例えば「再試行しますか」に同意されても、再試行の対象・上限・重複副作用の扱いが未確定なら関連する枝は未解決である。回答の理由やトレードオフが不明ならそこを問い、反例で採用案が破綻したら判断へ戻る。ユーザーの案も自分の推奨案も同じ基準で検討する。

## 完了条件と成果物への反映

質問が思い付かなくなったことや、CLI の done / validate 成功だけを完了の根拠にしない。次をすべて満たしてから提案を確定する。

1. 該当する観点の各枝について、根拠で解決した事実、ユーザーが決めた選択、無人実行で AI が既定で確定した選択を区別でき、暗黙の仕様判断が残っていない。
2. 確定した判断、明示的な延期、残るリスクを短くまとめ、ユーザーに共有理解を確認した。質問の経路がない無人実行では、AI が既定で確定した選択を、理由と代わりに指示できることを添えて要約に並べ、それをこの確認に代える。今回の仕様・実装・検証を左右する判断の延期は、解決済みとして扱わない。ユーザーが中止・保留したら未完了と報告する。
3. 合意後、選択されたスキーマの成果物へ判断を反映し、相互の整合性を確認した。標準構成なら proposal の目的・範囲、design の採用理由、specs の振る舞い・境界条件、tasks の実装・検証が対応する。具体的な数値、否定要件、失敗時の扱いを曖昧な要約に薄めない。
4. 成果物を回答と突き合わせ、新しい曖昧さ・矛盾が見つかった場合は質問へ戻った。
5. 「apply に判断を残さない」の 3 つが済み、その節のスクリプトが残す理由のない行を返さない。延期は、この change の外（別の change）へ送るものだけを認め、apply へ送る延期は認めない。

共有理解を確認するまでは成果物の本文を確定・反映せず、実装へ進まない。既存の草案がある場合も、そこに書かれた仮定を合意済みとみなさない。

無人実行で呼び出し元が PR 上の質問・回答手順を指定している場合は、その経路を使う。未確定事項を明示した草案は作れるが、回答待ちを合意済み・実装準備完了と扱わない。回答後の掘り下げと成果物への反映には同じ基準を適用する。

# レビュー

必要に応じて `35-architect-*` 系の Skill を用いてレビューをすること。
それぞれの Skill は作業エージェントのバイアスを除去するために必ず SubAgent を起動して行うこと。
最低でも doubt-driven-development のレビューは行うこと。

コードのない計画を敵対的にレビューさせると、レビュアーは起きない理論上のリスクや端の条件を作り出す。そのため、レビューに出す前に、試作で決められる問いは試作で閉じておく。返ってきた指摘は `architect:35-architect-interrogate` の「手順 5. リードとして判定する」で Act on / Consider / Noted / Dismissed に仕分ける。具体的な実行の経路を示せない仮定の指摘と、「自分なら別のやり方にした」に帰着する指摘は、理由を添えて Dismissed に入れる。Act on は成果物に反映し、判断が要るものはグリリングに戻す。複数モデルでコードを叩くレビュー（interrogate そのもの）は、差分ができる apply で行う。

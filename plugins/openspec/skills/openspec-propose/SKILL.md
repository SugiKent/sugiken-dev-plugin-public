新しい change を提案し、選択された OpenSpec スキーマが要求する成果物を生成する。

成果物の種類・順序・完了条件はスキーマから取得する。`proposal.md`、`design.md`、`tasks.md` を固定で仮定しない。

実装の準備ができたら、`openspec-apply-change` スキルでその change の tasks を進められる。

---

**ストアの選択:** ユーザーがストア（このマシンに登録された単体の OpenSpec リポジトリ）を指定した場合、または作業がストア内にある場合は、`openspec store list --json` を実行して登録済みストアの id を調べ、specs や changes を読み書きするコマンド（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`）に `--store <id>` を渡す。他のコマンドはこのフラグを取らない。コマンドが出力するヒントには既にフラグが含まれているので、後続でもそれを維持する。ストアがなければ、コマンドは最も近いローカルの `openspec/` ルートに対して作用する。

**入力**: ユーザーのリクエストには、change 名（kebab-case）または作りたいものの説明を含めるべき。

**手順**

1. **明確な入力がなければ、何を作りたいか尋ねる**

  **AskUserQuestion ツール**（自由記述、選択肢なし）で次のように尋ねる:
  > 「どの change に取り組みたいですか？作りたいもの・直したいものを説明してください。」

   その説明から kebab-case の名前を導く（例: 「add user authentication」→ `add-user-auth`）。

   **重要**: ユーザーが何を作りたいかを理解せずに先へ進んではならない。
2. **change ディレクトリを作成する**
  ```bash
   openspec new change "<name>"
  ```

   これは CLI が解決する planning home に、`.openspec.yaml` 付きの雛形 change を作成する。
3. **成果物のビルド順序を取得する**
  ```bash
   openspec status --change "<name>" --json
  ```

   JSON をパースして次を得る:
  - `applyRequires`: 実装前に必要な成果物 ID の配列（例: `["tasks"]`）
  - `artifacts`: すべての成果物とその状態・依存関係のリスト
  - `planningHome`、`changeRoot`、`artifactPaths`、`actionContext`: パスとスコープのコンテキスト。リポジトリローカルのパスを仮定せず、これらを使う。
4. **グリリングで判断を詰め、apply に必要な成果物を順に作成する**

  成果物の本文を書き始める前に、後述の「徹底的な疑問点の解消について」を実施する。成果物が CLI 上で done になっても、グリリングの完了条件を満たすまでは提案を確定しない。

  依存順に成果物をループする（未解決の依存を持たない成果物から先に）:

   a. `**ready`（依存が満たされた）成果物ごとに**:
      - 指示を取得する:
        `bash       openspec instructions <artifact-id> --change "<name>" --json`       
      - 指示の JSON には次が含まれる:
        - `context`: プロジェクトの背景（あなたへの制約 - 出力に含めない）
        - `rules`: 成果物固有のルール（あなたへの制約 - 出力に含めない）
        - `template`: 出力ファイルに使う構造
        - `instruction`: この成果物タイプ向けのスキーマ固有のガイダンス
        - `resolvedOutputPath`: 成果物を書き出す解決済みのパスまたはパターン
        - `dependencies`: コンテキストとして読むべき完了済みの成果物
      - コンテキストとして、完了済みの依存ファイルを読む
      - `template` を構造として成果物ファイルを作成し、`resolvedOutputPath` に書き出す
      - `context` と `rules` は制約として適用する - ただしファイルにコピーしない
      - 短い進捗を表示する: 「Created <artifact-id>」

   b. `**applyRequires` の全成果物が完了するまで続ける**
      - 各成果物を作成した後、`openspec status --change "<name>" --json` を再実行する
      - `applyRequires` の各成果物 ID が artifacts 配列で `status: "done"` になっているか確認する
      - `applyRequires` の全成果物が done になったら止める

   c. **成果物にユーザー入力が必要な場合**（コンテキストが不明瞭）:
      - 後述のグリリングに戻り、関連する判断とその依存先を問い直す
      - 共有理解を確認してから、影響を受ける成果物を更新する
5. **最終状態を表示する**
  ```bash
   openspec status --change "<name>"
  ```

**出力**

全成果物を完成させた後、次を要約する:

- change 名と場所
- 作成した成果物のリストと簡単な説明
- 準備状況: 成果物の作成状況と、グリリングで共有理解を確認できたかを別々に示す。未解決判断が残る場合は草案・回答待ちとし、「実装の準備ができた」と宣言しない
- 次の選択肢: 「実装を依頼する」または「`openspec-apply-change` スキルで tasks を進める」

**成果物作成のガイドライン**

- 各成果物タイプについて `openspec instructions` の `instruction` フィールドに従う
- スキーマが各成果物に含めるべき内容を定義しているのでそれに従う
- 新しい成果物を作る前に、依存する成果物をコンテキストとして読む
- 出力ファイルの構造として `template` を使う - そのセクションを埋める
- **重要**: `context` と `rules` はあなたへの制約であって、ファイルの内容ではない
  - `<context>`、`<rules>`、`<project_context>` ブロックを成果物にコピーしない
  - これらはあなたが書く内容を導くが、出力に現れてはならない

**ガードレール**

- 実装に必要な全成果物を作成する（スキーマの `apply.requires` が定義する通り）
- 新しい成果物を作る前に、必ず依存する成果物を読む
- コンテキストが決定的に不明瞭なら、ユーザーに尋ねる
- その名前の change が既に存在するなら、継続するか新規作成するかをユーザーに尋ねる
- 各成果物ファイルを書いた後、次へ進む前にファイルの存在を確認する
- [tasks.md](http://tasks.md) のタスク量は30を最大とし、それを超える場合は change の分割を検討する

---

# tasks に含めてはならないもの

tasks.md は **change を archive するための完了条件**であり、本番運用で当然行うことの記録場所ではない。次のタスクを作らない。

- **本番環境で実測・確認するタスク**（「本番でレスポンスタイムを計測する」「本番環境で動作を確認する」など）。本番確認は当たり前に行うが、propose の完了条件ではなく、それを待たずに archive する。例外は、本番環境固有の構成（本番だけに存在するインフラ・外部サービスの本番アカウント・本番データ量）でしか検証しようがない場合のみ。
- **人間が手で動作確認するタスク**（「画面を開いて目視確認する」「手動で一連の操作を試す」など）。よほど複雑で自動検証が現実的に組めない場合を除き、作らない。

検証タスクを置く場合は、自動テスト（ユニット / 統合 / E2E）やローカル・開発環境で完結する確認に置き換える。

# プロジェクト固有の制約

テスト種別、動作確認、依存サービス、ランタイムやライブラリのバージョン、静的解析は、OpenSpec のスキーマ・プロジェクト設定・ユーザー要求に従う。スキル自身がユニットテストのみ、特定のコンテナ構成、特定のメールツール、または特定の検証手順を一律に要求しない。

# 先行・関連する change との依存関係について

新しい提案は単独では存在しない。既存の先行 change や他の change の内容を踏まえずに書くと、**重複した提案・矛盾する spec 変更・実装順序の取り違え**を生む。新しい提案を書き始める前に、既存 change の内容を必ず確認し、判明した依存・競合・前提を proposal / design / tasks の全体にわたって一貫した制約として反映する。

- **既存 change の確認手順**: まず `openspec list --json` で現在の change 一覧を取得し、今回の提案と関連しそうな change（同じ spec・同じ機能領域・同じデータ構造を触るもの、または前提となる基盤変更）について `openspec show <other-change> --json` で中身を読む。特に proposal.md（何を・なぜ）と spec の delta（どの spec をどう変えるか）を確認する。
- **前提となる change**: まだ archive されていない先行 change の spec 変更やデータ構造に依存する場合、その依存を proposal / design に明示し、実装順序（どちらを先に apply すべきか）を tasks に反映する。
- **競合する change**: 同じ spec の同じ箇所を別の change が変更している場合、パターンを混在させず、どちらに従うかを決めてから書く。判断が分岐する場合はユーザーに確認する。
- **重複する change**: 既存 change が今回のリクエストを既にカバーしている場合は、新規作成せず既存 change の継続を提案する。

# マイグレーション設計について

提案がデータ構造の変更（テーブル・カラムの追加/変更/削除、データ形式の変換など）を伴い migration が必要になる場合、設計を確定する前に「過去データを破棄できるか」を `AskUserQuestion` でユーザーに確認する。破棄可否は移行方式（そのままドロップできるか、変換・バックフィルが要るか）を左右するため、確認せずに設計へ進まない。

# デザイン成果物・デザイン指示の取り込みについて

ユーザーのリクエストやこれまでの会話に UI/UX・画面レイアウト・デザインに関する言及がある場合、または画像・HTML・モックアップなどのデザイン成果物が提供されている場合は、それらを一次情報として扱い、design.md と tasks.md に反映する。

- 画像や HTML などデザインの原本は作成中の change フォルダ内に配置して参照できるようにする
- 提供されたデザイン成果物を実際に確認する。画像は Read で見る、HTML は構造とスタイルを読む、会話中のデザイン言及も拾い上げる。
- **design.md**: 対象画面・コンポーネント構成・状態遷移・レイアウト方針を、確認したデザイン成果物に基づいて記述する。デザインが示す UI 要素・画面フロー・インタラクションと design.md の内容が一致するようにする。
- **tasks.md**: デザインを再現するための実装タスク（コンポーネント作成・スタイリング・レスポンシブ対応・状態管理など）を、デザイン成果物の内容を踏まえて具体的に列挙する。
- デザイン成果物と矛盾する記述を成果物に残さない。デザインが曖昧・不足している箇所は、推測で確定せず `AskUserQuestion` で確認する。
- デザイン成果物もデザインに関する言及もない場合、この節は適用しない（架空のデザインを創作しない）。

# 徹底的な疑問点の解消について

`basic:grill-me` スキルを読み、その意思決定ツリーを一枝ずつ追求する手順を実行する。「不明点はありますか」という包括的な確認や、一巡の質問だけで代用しない。以下は、この change をグリリングするときの対象と完了条件である。

## 事実と意思決定を分ける

関連コード、main specs、進行中 changes、プロジェクトの方針を先に調べる。既にユーザーが明示した判断は引き継ぎ、同じ確認を繰り返さない。調べれば分かる事実をユーザーへ質問せず、根拠のファイル・要求を押さえる。情報にアクセスできなければ未確認として残し、推測を事実扱いしない。

一方、資料だけでは決まらない選択は、一般論や推奨案で勝手に確定しない。要求同士、要求と既存実装が矛盾する場合は、その矛盾と影響を示してユーザーに判断を求める。

## 判断ツリーを作り、一枝ずつ掘る

目的・成功条件を根として、対象範囲、利用者と操作、仕様、設計、検証へ判断の依存関係をたどる。各判断について、確定した内容と根拠、未解決の問い、前提となる判断を追跡する。回答を受けるたびにツリーを更新し、その回答で新たに生じた枝や、前提が変わった既決事項を再確認する。

少なくとも次の観点を今回の change に照らして点検する。該当しない観点から架空の要件や質問を作らない。

- 何の問題を誰のために解くのか。成功と失敗をどう判定するか。今回やらないことは何か。
- 用語、対象、責任範囲は一意か。具体的な入力・操作に対して、誰に何が見える／起きるか。
- 正常系だけでなく、空・欠損・不正入力、境界値、権限不足、失敗・再試行・重複・同時実行ではどう振る舞うか。
- データの所有者、状態遷移、整合性、既存データの移行・互換性、外部連携の失敗をどう扱うか。
- main specs や他 change と矛盾・重複しないか。依存する change が未適用でも成立するか。
- 採用案の代替は何か。簡単な案や何も変えない案では不足する理由、採用案で受け入れる不利益は何か。
- 合意した振る舞いをどのシナリオで検証できるか。実装者が追加の仕様判断なしに着手できるか。

## 同意を取るだけで終わらせない

質問は `AskUserQuestion` で一度に一問とし、回答を待つ。判断が必要な背景、具体的な選択肢と影響、根拠付きの推奨回答を添える。前提が未確定の枝の質問を先回りして並べない。

「はい」「いい感じに」「通常どおり」だけでは振る舞いが一意にならない問いは、具体例・境界条件・反例を使って掘り下げる。明確な選択肢への「はい」は回答として受け入れるが、そこから未提示の条件まで同意されたと解釈しない。

例えば「再試行しますか」に同意されても、再試行の対象・上限・重複副作用の扱いが未確定なら関連する枝は未解決である。回答の理由やトレードオフが不明ならそこを問い、反例で採用案が破綻したら判断へ戻る。ユーザーの案も自分の推奨案も同じ基準で検討する。

## 完了条件と成果物への反映

質問が思い付かなくなったことや、CLI の done / validate 成功だけを完了の根拠にしない。次をすべて満たしてから提案を確定する。

1. 該当する観点の各枝について、根拠で解決した事実とユーザーが決めた選択を区別でき、暗黙の仕様判断が残っていない。
2. 確定した判断、明示的な延期、残るリスクを短くまとめ、ユーザーに共有理解を確認した。今回の仕様・実装・検証を左右する判断の延期は、解決済みとして扱わない。ユーザーが中止・保留したら未完了と報告する。
3. 合意後、選択されたスキーマの成果物へ判断を反映し、相互の整合性を確認した。標準構成なら proposal の目的・範囲、design の採用理由、specs の振る舞い・境界条件、tasks の実装・検証が対応する。具体的な数値、否定要件、失敗時の扱いを曖昧な要約に薄めない。
4. 成果物を回答と突き合わせ、新しい曖昧さ・矛盾が見つかった場合は質問へ戻った。

共有理解を確認するまでは成果物の本文を確定・反映せず、実装へ進まない。既存の草案がある場合も、そこに書かれた仮定を合意済みとみなさない。

無人実行で呼び出し元が PR 上の質問・回答手順を指定している場合は、その経路を使う。未確定事項を明示した草案は作れるが、回答待ちを合意済み・実装準備完了と扱わない。回答後の掘り下げと成果物への反映には同じ基準を適用する。

# レビュー

必要に応じて `35-architect-*` 系の Skill を用いてレビューをすること。
それぞれの Skill は作業エージェントのバイアスを除去するために必ず SubAgent を起動して行うこと。
最低でも doubt-driven-development のレビューは行うこと。

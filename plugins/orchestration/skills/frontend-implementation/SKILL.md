# フロントエンド実装スキル

1 つの openspec change の **フロントエンド側**（画面・コンポーネント・フォーム・クライアント状態・クライアントからの API 呼び出し）を実装するための手法。あなたは 1 change のフロント担当として、**所有スコープ内**を縦に実装しきる。

## 前提として読むもの

着手前に必ず突き合わせる。**推測で UI を作らない**。

| 何を | パス | 用途 |
|------|------|------|
| change 仕様 | 対象 change の `proposal.md` / `design.md` / `tasks.md` / spec delta。change 内に参考になる html や画像が存在する場合はそれを読む | 実装すべき UI 要件 |
| デザインの判断基準 | `design:design` | 構成・文言を決める前に読み、業務フロー・既存画面の比較と実画面での確認に使う |
| 既存 UI 規約 | リポジトリの既存コンポーネント / デザイントークン | 命名・再利用・スタイル体系 |

## 実装の原則

1. **UI の最終形はここで決める**: changeからリンクされたdesign-briefも読み、固定契約（spec と design の振る舞い・状態・権限・データ契約、ユーザーが指定した位置・文言・見本）と、apply に任された表現を区別する。正本は `openspec-propose` の「UI・UX の扱い」。UI変更では `design:design` を使い、改修対象に加えて同じ流れの前後の画面と関わる状態を実画面とコードで見てから、現状の配置にとらわれずに構成と固定されていない文言を決める。tasks に書かれた画面だけに閉じない。周辺を変えるなら親から渡された所有スコープの中で行い、スコープの外が要るなら親へ返す。固定契約の変更も親へ返す。見本の再現を依頼された範囲では、デザインサンプルに対して、色・間隔・角丸・影・タイポ・状態変化（hover / focus / disabled）まで合わせる。既存のデザイントークン / コンポーネントを再利用し、車輪の再発明をしない。
2. **状態を全部作る**: 正常系だけでなく **ローディング / 空 / エラー / 権限なし / 部分失敗** を必ず実装する。空状態・エラー表示の欠落は未完了とみなす。 未保存値と処理中の要求がどの対象に属するかを明確にし、引継ぎ先が値を保持する前に元の値を破棄しない。対象変更・画面終了・再取得失敗の後に、古い応答で新しい対象や未保存値を上書きしない。応答を保留して対象を切り替える、または画面を終了してから成功・失敗を返し、値の保持と回復操作を確かめる。振る舞いの仕様が未確定なら親へ返す。
3. **サイレント失敗を作らない**: API エラー・バリデーションエラーは握りつぶさず、ユーザーに見える形（トースト / インラインエラー / 再試行導線）で必ず表出する。`catch` で握って握りつぶすのは禁止。
4. **フォームは境界値まで**: 必須・型・長さ・形式のクライアント検証、送信中の二重送信防止、サーバエラーのフィールド還元まで。バックエンドの検証を UI 側の唯一の防波堤にしない（サーバ側はバックエンド担当が持つ）。
5. **アクセシビリティの最低限**: セマンティックなマークアップ、フォーカス可視、ラベルと入力の関連付け、キーボード操作。
6. **並列作業前提**: 他の apply / frontend / backend サブエージェントが同時に走っている。他者の編集を巻き戻さず、衝突は自分側で吸収する。

## 完了報告に含めること（親エージェントへ返す）

- 変更した全ファイルパス。
- 実装した画面 / コンポーネントと、カバーした状態（正常 / ローディング / 空 / エラー / 権限なし）。
* デザイン判断と証拠: 見た周辺の画面と状態、変えた範囲（tasks の外を含む）と理由、決めた文言、実画面の確認と未確認、見本の再現では `docs/quality/design-system.md` / `design-sample.png` との一致状況と、やむを得ず外した箇所（理由付き）。
- バックエンドとのデータ契約（依存した API とその型）。未確定・要調整の点。
- 型 / lint / unit の結果。未完了タスクとその理由（人間作業のみ残す）。

> あなたは実装に徹する。コードレビューは apply-review、E2E 実行は `40-run-and-report-e2e` skill が別途担う。自分でレビュー OK や E2E 緑を宣言しない。

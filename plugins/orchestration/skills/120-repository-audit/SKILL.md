# リポジトリの品質点検

## 目的

コード、開発環境、過去の失敗を横断して問題を直し、同じ問題が戻らないように lint・rules・skills に落とす。指摘を並べるだけで終えず、修正した状態と再発を検知できることを確かめ、残件を次回の点検に引き継ぐ。

対象の仕様、既存の検証コマンド、前回の報告と残件を読み、以下を一巡する。1件の修正で点検全体を完了にしない。E2E や開発基盤の置換は依頼の対象に含まれる場合だけ扱う。読み取りのみ等の指定、既存の変更禁止範囲、本番操作の承認範囲を守る。

## コメント

目的は、実装と食い違う説明や未解決の先送りをなくし、本当に必要なコメントだけを保つこと。

* アプリだけでなく、テスト・スクリプト・インフラ・設定・埋め込みコードを走査する。TODO・FIXME・XXX・HACK・「暫定」「あとで」「一旦」は候補として拾い、実装要求と識別子・サンプル文字列を区別する。未実装や暫定処理は実装で解消する。解消できない要求をコメントごと消して完了扱いにしない。
* コードを言い換えただけの説明や古い説明は削除する。ツール指示、ライセンス、コードだけでは分からない制約は、残す理由を明示する。抑制コメントを無条件に許可せず、先送りを許可理由で隠せない検査にする。
* コメントの検出には言語の構文を使い、文字列・正規表現・JSX・SQL 関数本体・シェルのデータ用 heredoc などを区別する。文字列の値、Unicode、実行順序を変更していないことを差分や構文解析で照合する。整形ツールの標準出力を経由した書き戻しでも文字列が変わり得る。
* コメント行数を実装行数の **0.1% 未満**に保つ lint を既存の検証と CI に接続する。対象言語、生成物等の除外、空行・混在行の数え方を定義し、許可コメントも分子に含める。比率内でも理由のないコメントは検知する。正常例と違反例、文字列を誤検知しない例を確かめる。
* コメントを目印にするテストは、実際の呼び出し・SQL・権限など守るべき挙動の検査に直す。コメント変更でも migration のチェックサムや CSP のハッシュは変わる。適用済み migration の変更禁止を守り、例外は理由付きで残す。ハッシュの更新は契約と配信物への影響を確認してから行う。
* **成果物**: 対象・除外、削除と残存の理由、解消した実装要求、対象ファイル数・コメント行数・実装行数・比率・未許可件数、lint の入口、検証と残件を報告する。作業ツリーとコミット済みの値が違えば別々に示す。

## アーキテクチャ

目的は、新旧や多数派に合わせることではなく、責務と依存方向からあるべき設計を選び、違反を減らすこと。

* 入口から認可、業務処理、永続化、外部通信まで追い、静的・動的 import、実行時循環、層を越えた DB 操作、上位層のエラーや型への依存を洗い出す。検索の命中数をそのまま違反数にしない。
* 修正前に責務の判断基準を書く。例: Service はユースケース・認可・処理順序、Repository は DB 入出力と原子性、純粋な規則と共通の型は下位の共有モジュールに置く。対象の設計に照らして選び、単に新しい実装へ統一しない。
* 移動前後で公開 API、エラーの code/message/data、DB 契約、業務動作を維持する。特にロック後の再検証、transaction の範囲、commit 後の外部処理の順序を追う。DB client の注入や transaction の開始だけで違反と決めず、実際の読み書きと責務で判断する。
* 選んだ設計と理由は rules に、機械判定できる import・直接アクセス・循環の境界は custom lint にする。既存 lint・検証・CI から動かし、違反を入れると失敗することを確かめる。直した箇所を allowlist に残さない。残る例外は理由と解消条件を台帳へ記録する。
* 移動・改名のたびに、スクリプト、seed、E2E、テストの mock、ルールの参照先まで全リポジトリで旧名・旧パスを探す。関連テストだけでは静的検査の取りこぼしが出るため、変更したパッケージの全件テスト・型検査も確認する。
* **成果物**: 判断基準と、対象／静的根拠／選んだ設計／修正・lint・rule／検証／残件の台帳を残す。残件には優先順位と次に追う経路を書く。依存循環を見つけた事実と、実際の初期化障害を再現した事実を区別する。

## セッション分析

目的は、訂正・失敗・やり直しから再発条件を取り出し、次の作業で実際に効く防止策に変えること。

* 対象リポジトリの会話履歴を cwd・プロジェクト識別子・会話内容で限定し、前回以降の記録と未対応の過去事例を読む。ユーザーの訂正、テスト・CI の失敗、revert、同じ操作のやり直しを手がかりに、前後の文脈と修正結果を照合する。Home ディレクトリの ~/.claude や ~/.codex が検査対象。
* 転記された指示、別プロジェクトの話、同じ失敗の再送を重複計上しない。「確認できた事例数」と「全履歴の総数」を区別する。ユーザーの評価と分析者の評価も分け、生ログ・秘密情報・個人情報は転記しない。
* ユーザー自身のプロンプトと、質問への回答・選択を、状況と求めた振る舞いでまとめる。言い回しが違っても、似た状況で同じ傾向を独立した事例で3回以上確認できたら、「どんなときにどう振る舞うか」を一文にし、件数と根拠のセッション識別子を添えて採用候補として報告する。
* 原因ごとに既存の防止策を探し、機械で確定できる違反は lint、判断時に守る原則は rules、再利用する調査・操作の手順は skills に振り分ける。既存で防げるなら追加不要と記録し、不足分だけ追記する。重複や古い例も整理する。
* 例: テスト hook が mock 関数を返す誤りは lint、保存する最終集合を認可・検証する原則は rule、CI と同じ条件で失敗を再現する調査は skill にする。曖昧な注意を大量に増やさず、何を見てどう判断するかを書く。
* 追加した lint は正例・反例で確認する。rules の適用パス、skills の参照、補助ファイルが実在し、コミットに含まれることも検査する。未追跡・存在しない手順を参照しただけでは再発防止が整ったことにならない。
* **成果物**: 調査範囲・期間・数え方を記し、種類／確認件数／根拠のセッション識別子と現象／原因／防止策の配置先／検証・未対応を表にする。根拠から防止策まで1件ずつ追える形にする。

## lint・test・dev 高速化

目的は、検査の意味と網羅を維持したまま、開発者が結果を待つ時間を減らすこと。

* lint、型検査、unit・統合テスト、CI の準備・ビルド、開発サーバーの起動・変更反映を分けて測る。遅い処理から、重複走査、繰り返すコード生成、DB 準備、不要な待機、直列依存を調べる。
* 入力、実行範囲、マシン、並列数、キャッシュの有無を揃えて前後を測る。cold/warm を混ぜない。局所処理の短縮と全体時間を分け、推定だけで高速化を宣言しない。
* 独立した検査の並列化、内容ハッシュによる解析キャッシュ、増分型検査、重複生成の削減を検討する。キャッシュはソース・設定・検査器の変更で失効し、壊れた結果を成功として使わないことを確認する。
* 固定 sleep は完了条件の観測や仮想時計に置き換える。例: DB ロック待ちの成立、通信完了、保存行の時刻を起点とした期限。DOM が現れたことと非同期処理が完了したことを混同しない。assertion、対象、認可検査を削って速くしない。
* 並列化で遅くなる場合もある。改善しない変更は戻し、条件と結果を残す。CI の起動条件・対象ケースを勝手に広げず、通常の push 1回あたりの総所要時間も比較する。一部の短縮だけで、CI 全体の増大を見落とさない。
* **成果物**: 対象／遅い原因／変更内容／同条件の前後時間／網羅維持の根拠を表にする。採用しなかった試みと理由、実 CI 未計測ならその限界も残す。

## E2E の高速化と失敗修正（対象の場合）

目的は、利用者の操作と保存結果を守る検査を、速く、原因を追える形にすること。

* ケース別の所要時間を seed、起動、ログイン、操作、待機へ分ける。認証状態の再利用や DB テンプレートを使う場合は、権限・状態の混入を防ぐ。並列実行では DB・ポート・mock・一時ファイルを実行単位で分離し、共有 DB を同時に reset しない。
* 失敗は元と同じ shard・並列数・seed で再現し、必要なら単独実行と比較する。行数不一致、曖昧な locator、要素の未描画、非同期ジョブの未生成を区別し、実装・テスト・基盤移行のどこが原因か追う。
* 仕様どおりの変更ならテストを追随させ、実装の欠陥なら実装を直す。リトライ増加、timeout 延長、skip で失敗を隠さない。生成物がない場合は受付からキュー、実行処理、保存まで追い、画面の待ちだけを調整しない。
* 共通ヘルパーや画面入口の変更は全利用箇所へ広げて確認する。該当する入力・Enter・blur・画面離脱・再読み込みまで実ブラウザで通し、保存後の表示と永続化を確かめる。全件の失敗を、後の絞った実行の成功で上書きしない。
* **成果物**: 対象ケース、再現条件、原因、修正、前後の時間、成功・失敗・skip 件数、未実行の範囲を残す。型検査や unit 成功をブラウザ E2E 成功と書かない。

## セキュリティ

目的は、入力と権限の境界を実際の読み書きまで追い、漏えい・不正操作・過大な負荷につながる経路を閉じること。

* 依存の監査、秘密情報の混入、認証・認可、入力検証、XSS・SSRF・SQL injection、CORS・CSP・Cookie、外部通信、ログと失敗履歴、IaC の権限を点検する。前回の未修正項目と新しい経路も対象にする。
* 認証ミドルウェアの存在だけで完了にしない。組織・所有者・用途の照合を入口から一覧、版指定、ジョブ状態、保存まで追い、権限変更後のキャッシュや親変更後の古いデータを確認する。ロック待ちの後も、認可した対象・期限・状態が保存対象と一致するか見る。
* 秘密値や個人情報はレスポンスだけでなく、例外本文、URL/query、構造化ログ、永続化する失敗履歴にも流れる。ダミーの値で経路を確かめ、必要な識別子・固定エラー分類を残して本文を抑止する。外部通信は初期 URL だけでなく、リダイレクト後の資格情報・本文の転送も調べる。
* 再現できる欠陥は修正前に失敗する回帰テストを作り、修正後の成功と正常系の対照を確認する。fixture 不備や起動失敗を欠陥の再現に数えない。IAM は操作・資源・条件の意味で判断し、ワイルドカードという記号だけで必要な権限を削らない。
* 依存監査の検出と実際の悪用可能性、本番での漏えいを区別する。秘密走査は値を出さず、検査したファイル・履歴・形式と除外範囲を記録する。「一致0件」を安全の証明にしない。
* **成果物**: 項目／原因・影響／修正と判断／修正前後の検証／コミットを記録する。未修正は残存リスク、理由、次に必要な証拠を明記する。コード・IaC の修正と本番への適用は別であり、点検の依頼だけで本番設定変更や deploy を行わない。

## 不要ファイルと一時ファイル lint

目的は、一時的な検証を妨げず、使い捨ての資材が正規のコードや検証へ混入することを防ぐこと。

* 検証用スクリプト、スクリーンショット・デモ専用 spec、一時設定、未使用の設定・fixture を探す。参照、実行入口、内容を確認して削除を判断する。古い・未追跡・名前が demo という理由だけで消さず、作業中のファイルや正規のテストを保護する。
* テストを削る場合は、実装の契約や既知の回帰を検査しているかを読む。テスト自身の存在や数だけを検査するものは目的を再評価するが、静的な境界検査を一律に無意味と決めない。
* 一時ファイルの置き場を決めて rules に書く。例: 追跡外の `tmp/`。置き場以外への混入を、追跡中と未追跡の両方で検出する lint にし、対象パスと片付け方を表示する。削除機能を付けるなら明示実行と所有確認を必要にし、lint の通常実行では他人の作業を消さない。
* 正規のテスト・fixture を検知しない反例を用意する。生成と削除が並行する一時ファイルを、ソース件数検査や依存走査が拾って失敗しないよう対象集合を定義する。
* **成果物**: 削除対象と不要と判断した根拠、保持した対象と理由、一時置き場、検出パターン・除外・検証結果を残す。

## 開発環境のモダン化・基盤の置換

目的は、古い依存や設定による負担を減らし、手元と CI で同じ環境を再現できるようにすること。

* ランタイム、パッケージ管理、コンパイラ、Docker イメージ、版固定ファイル、設定と起動スクリプトを棚卸しする。ライブラリ・イメージは公式のリリースと脆弱性情報を確認し、脆弱性報告のない最新版を選ぶ。確認日・URL・選択理由を残す。
* イメージのアプリ本体だけでなく OS パッケージや内蔵ランタイムも確認する。最新タグでも既知脆弱性が残る。条件を満たす版がなければ、更新済みと偽らず、該当報告・修正版・到達性の調査状況と代替案を残す。既存の公開後待機期間や互換性制約を勝手に解除しない。
* ローカル、CI、ビルド、コンテナ、環境変数の例、手順書の版と設定を揃える。依存更新後は lockfile と生成クライアントの整合を確認する。major 更新に伴う DB volume の移行や共有サービスの再起動を、版文字列の更新と一緒に無断で行わない。
* エミュレーター等の置換が対象なら、提供元・版・ライセンス・対応操作を調べ、既存設定から利用中のサービスと操作を列挙する。例: オブジェクト保存、キュー投入・受信、関数実行。対応表だけで済ませず、必要な操作とアプリの連携経路が通ってから切り替える。
* ローカルの接続先が欠けたとき、本物のクラウドへ流れず失敗することを確認する。本番側は本番モードを明示しているか生成された IaC テンプレートでも検査する。旧設定の削除、dev・テスト・CI・docs の同期、起動に必要な手順まで確認し、未対応機能は残件にする。
* **成果物**: 変更前後の版・設定、選択根拠、互換性と操作ごとの検証、未対応・既知脆弱性、必要な再起動や適用作業を記録する。

## 共有変更と最終検証

* 並行作業では共有設定・lockfile・生成物の変更を調整し、編集直前に読み直して他の差分を保持する。コミットは `basic:20-commit-meaningful-diffs` の「共有 checkout での所有範囲」に従う。専用 index を使っても古い index を無条件に同期しない。
* 検証コマンドの子プロセスによる自動 install・コード生成も調べる。一時コピーから共有依存を作り直さない。Git を操作するテストは外側の `GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE` を引き継がせず、共有の Git 設定を保護する。
* 個別の修正確認後、コミット済みの固定 SHA で既存 verify と CI 相当の lint・型・全件テストを実行する。E2E は合意した範囲だけを含める。テスト件数や snapshot の固定値は、追加・移動・削除後の実際の対象集合と比較し、検査漏れを隠す更新にしない。
* 新しい lint・rule・skill の参照先とテスト fixture がコミット済みの内容だけで揃うことを確認する。作業ツリーで成功しても未追跡ファイルが必要なら CI では失敗する。
* 失敗は原因を修正して再検証する。他の未完成差分による失敗は、原因と所有範囲を示して全体成功と区別する。静的検査、単体、統合、ブラウザ、実 CI、本番適用後の証拠を混ぜない。
* リモートとの合流が依頼に含まれるなら、両側の変更意図と未コミット差分を保持して競合を解消する。合流後の SHA と変わった範囲を再検証し、合流前の成功をそのまま転用しない。push・deploy は与えられた承認範囲でのみ行う。

## 最終報告

各項目の詳細報告を根拠として、次の表で結果をまとめる。報告を増やすこと自体を目的にせず、既存の品質・設計・教訓の文書へ配置する。

| 点検項目 | 発見と修正 | 再発防止の配置先 | 数値・検証結果と SHA | 残件・未実施と理由 |
| --- | --- | --- | --- | --- |
| 例: lint 高速化 | 重複解析をキャッシュ化 | キャッシュ失効の回帰検査 | 同条件の前後時間、検査範囲、対象 SHA | 実 CI の所要時間は未計測 |

成功・失敗・skip の件数、検証範囲、対象 SHA、コミットを記載する。未完了の原因と次に必要な判断・検証を示し、個別成功を全体成功、ローカル成功を実 CI 成功として報告しない。

# リポジトリの夜間点検

点検で見つけた問題を直し、繰り返す問題を lint・rules・skills に落とす。最後にコミット済みの状態を検証し、結果と残件を報告する。言語・フレームワーク・CI は対象リポジトリのものを使う。

## 1. 開始と分担

* 最初に macOS では `caffeinate -dimsu -t <終了までの秒数>` をバックグラウンドで起動する。他の OS では同等のスリープ防止を使い、自分が起動したものを終了時に止める。
* 対象リポジトリ、現在のブランチ・HEAD、既存差分、締め切り、CI 相当の検証コマンド、push の許可を記録する。既存の指示・前回の報告・残件を読む。
* 親オーケストレーターが同じチェックアウトに7〜8タブを割り当て、担当範囲・触らない範囲・検証・終了時刻を渡す。Orca では利用可能な `orca-cli`・`orchestration` の手順に従い、各タブの完了を回収する。
* 下表の7担当を基本にする。週次版では E2E の実行も高速化タブも設けない。E2E を含める明示指示がある場合だけ8番目の担当にする。
* 通常の判断は既存仕様と根拠に沿って自律で決め、理由を残す。権限や本番変更が必要な残件は切り分け、進められる点検を続ける。

| 担当 | ゴール |
| --- | --- |
| コメント | 全コードを対象に不要コメントを削除し、TODO 等は実装で解消する。コメント行数が実装行数の0.1%未満となる lint を既存検証・CI に組み込む。必要なツール指示・ライセンス等は理由付きで残し、許可分も含めた数え方を定義する。文字列や動作を変えない。 |
| アーキテクチャ | 新旧や多数派で判断せず、責務・依存方向からあるべき設計を選んで違反を直す。公開 API・DB 契約・業務動作を維持し、選択理由を rules、機械判定できる境界を custom lint にする。 |
| セッション分析 | 対象リポジトリの前回以降のセッションから、訂正・失敗・やり直しを分析する。機械判定は lint、常時の注意は rules、再利用する手順は skills にする。既存の対策と重複させず、秘密情報や生ログを転記しない。 |
| lint・test・dev 高速化 | ローカルと CI の遅い部分、開発サーバーの起動・変更反映を測って改善する。同じ条件で前後を実測し、対象・環境・時間を残す。検証範囲・アサーション・テスト網羅を減らさない。 |
| セキュリティ | 依存、秘密情報、認証・認可、入力、外部通信、ログ、権限設定を点検して直し、再発防止のテストか lint を足す。本番設定への適用・deploy はしない。 |
| ゴミ削除・一時ファイル lint | 参照と用途を確かめて不要ファイルを削除する。一時ファイルの作成は許し、置き場を決め、それ以外の追跡・未追跡ファイルを lint で検知する。他担当の作業は消さず、正規テスト・fixture を誤検知しないことを確認する。 |
| モダン化 | 開発ツール・依存・設定の古い部分を更新する。ライブラリと Docker イメージは脆弱性情報を確認し、報告がない版の中から最新を選ぶ。該当版がなければ未解決として根拠を残す。 |
| E2E 高速化（指定時のみ） | seed・待機・ブラウザ起動・ログイン・並列度を測って改善する。前後の実測と網羅維持を示し、専用の DB・ポートで検証する。 |

## 2. 共有チェックアウトの決まり

* worktree 作成、ブランチ切り替え、stash・checkout・restore・reset・clean はしない。各タブは push・deploy しない。
* 編集直前にファイルを読み直し、他担当の未コミットの hunk を保持する。共有設定・lockfile の担当を調整し、同じ箇所を同時に変更しない。
* 各タブは `GIT_INDEX_FILE` で専用 index を使う。コミット直前の HEAD を基準に、自分の差分だけを載せ、小さな単位でコミットする。同じファイルの他担当 hunk を混ぜない。HEAD が進んだら最新内容に当て直す。
* 専用 index でもブランチの HEAD は共有されるため、コミットを親が直列化する。共有 index は親だけが約20分ごとと最終検証前に整合する。作業ツリーが HEAD と一致し、専用 index のコミット由来と確認できる古い項目だけを合わせる。本当の staged 差分・競合・作業中の変更は保持し、index のロック中は更新しない。
* テストファイル数等の件数ピンは各タブで追いかけず、最後の green 担当に集める。新しい lint は既存の検証と CI に接続し、正常例と違反例を検査する。
* 依存の install・コード生成・共有サービス再起動は親が調整する。検証コマンドの自動 install も含め、別タブの依存や生成物を壊さない。Git を呼ぶテストには専用 index 等の Git 環境変数を引き継がせない。
* 各担当は変更した範囲の lint・型・テストを確認し、根拠・コミット・失敗・未完了を残す。1件直しただけで点検を打ち切らず、担当範囲を一巡する。

## 3. 締め切り1時間前から統合する

1. 各タブに新規変更を止めさせ、完成した差分のコミットと残件報告を回収する。編集・コミットの停止を確認してから green 担当へ渡す。持ち主不明の差分は消さない。
2. 最終 HEAD で件数ピンを実数と照合し、verify と CI 相当の lint・型・全件テストを通す。週次版では E2E を除外する。参照した新規ファイルがコミットに含まれることも確認する。必要なら固定 SHA の隔離コピーと専用 DB を使い、共有の依存を再生成しない。
3. 失敗の原因を直し、検証した SHA と成功・失敗・skip 件数、除外範囲を記録する。skip や検査の削除で green にしない。
4. origin の現在のブランチへの更新を取得して合流する。両側の意図と未コミット差分を保持し、合流で変わった範囲を再検証する。合流後の SHA の検証範囲を明記する。
5. 許可がある場合だけ親が検証済み SHA を push する。失敗・未検証や承認待ちが残る場合は push せず、その理由を報告する。

## 報告

担当ごとの表に、修正・再発防止、前後の計測値、検証結果と SHA、残件と判断理由をまとめる。個別検証と最終 green、ローカル検証と実 CI、E2E 未実施、push の成否を区別する。

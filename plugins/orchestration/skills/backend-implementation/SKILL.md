# バックエンド実装スキル

1 つの openspec change の **バックエンド側**（API / Service / Repository / ドメインロジック / データモデル / マイグレーション）を実装するための手法。あなたは 1 change のバックエンド担当として、**所有スコープ内**を縦に実装しきる。

## 前提として読むもの

| 何を | パス | 用途 |
|------|------|------|
| change 仕様 | 対象 change の `proposal.md` / `design.md` / `tasks.md` / spec delta | 実装すべきバックエンド要件 |
| 既存規約 | リポジトリの既存 Service / Repository / スキーマ | 命名・レイヤ分離・トランザクション作法 |

## 実装の原則

`35-architect-*` 系の Skill を必要に応じて参照すること

1. **レイヤを守る**: API（入出力・認証認可・検証）→ Service（ドメインロジック・トランザクション境界）→ Repository（永続化）の責務を混ぜない。既存のレイヤ規約に合わせる。
1. **org / テナントスコープを必須にする**: マルチテナント前提のプロジェクトでは、**すべての読み書きに org スコープを効かせる**。スコープ漏れは重大な認可欠陥。横断クエリでも所属境界を必ず適用する。
1. **サイレント失敗を作らない**: 失敗は握りつぶさず、適切なステータス / エラー型で呼び出し側に伝播する。`catch` して握りつぶす、握りつぶして既定値を返す、エラーをログだけして正常応答する、は禁止。
1. **トランザクションと整合性**: 複数テーブルにまたがる更新はトランザクション境界を明示する。並行更新のロストアップデートを想定し、必要なら楽観 / 悲観ロックを使う（`35-architect-db-design` 参照）。
1. **マイグレーションは実行まで**: スキーマ変更は ORM の正当な手段でマイグレーションを作成し、**実行（apply）まで完了**させる。破壊的変更（列削除・型変更）は既存データへの影響を明記する。archive 済み spec を壊す変更が必要になったら、続行せず親へ報告する。
1. **パフォーマンスの予測と対処**: 明らかにパフォーマンス問題が起きそうな箇所においては、実装から事実確認の上対処する。しかし実際にパフォーマンス問題が起きるかは実際の利用のされ方や DB 量に依存するので過度な先んじた対処はしない

## 完了報告に含めること（親エージェントへ返す）

- 変更した全ファイルパス（マイグレーションファイル含む）。
- 追加 / 変更した API エンドポイントと、そのリクエスト / レスポンス型（フロント担当が依存する契約）。
- スキーマ変更とマイグレーションの実行結果。既存データへの影響。
- org スコープ・認可・入力検証をどこで担保したか。
- 型 / lint / unit / migration の結果。未完了タスクとその理由（人間作業のみ残す）。

> あなたは実装に徹する。コードレビューは apply-review、E2E 実行は `40-run-and-report-e2e` skill が別途担う。自分でレビュー OK や E2E 緑を宣言しない。

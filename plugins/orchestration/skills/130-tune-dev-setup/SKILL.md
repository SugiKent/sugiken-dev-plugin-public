# 対象モデルに合う開発構成の見極めと構築

## 目的

変えられない前提は対象の AI モデルだけと置き、それ以外の開発構成（CLAUDE.md・ルール・スキル・SDD・レビューの回し方）を変えて同じ課題を解かせる。比べるだけで終えず、次の観点で最も良い構成を見極め、リポジトリにその構成を組み上げるところまでを責務とする。

* バグが最も少ない
* 検証が最も広く行えている
* 実装の筋が良い
* アーキテクトの判断にぶれがない
* 速い
* トークン消費が少ない

モデルが変わると、以前は必要だった指示が不要になったり、逆に足りなくなったりする。だから新しいモデルが出たときに、今の構成を引き算と足し算の両方で測り直す。

## 入力

* 対象のモデル（と effort）。全条件でそろえる。ユーザーが言わなければ確認する。
* 課題: ユーザーの依頼の文、または対象リポジトリで代表的な開発課題。全条件で同じ文を渡す。
* 対象のリポジトリと起点のコミット（既定は現在の HEAD）。
* 評価役: 対象モデルと別系統の AI（既定は Codex）。同系統のモデルに評価させると、同じ癖を見落とすため。

## 条件を決める

ユーザーが条件を指定しなくても、次の候補から基準点と比較対象を提案し、AskUserQuestion で選んでもらう。提案には、どの問いに答えるための条件かを添える。

* 今の構成そのまま（現状の比較対象）
* CLAUDE.md をすべて削除（サブディレクトリ内も含む）
* ルール（`.claude/rules/` 等）を削除
* スキル（`.claude/skills/` とプラグインのスキル）を削除
* SDD（OpenSpec 等）に則る / 則らない
* SDD に則らないが、再帰的なレビューやアーキテクト系のスキル（例: `architect` プラグインのレビュー・設計スキル）は使う

あわせて次を決める。

* 基準点をどれにするか。多くの場合は、すべて削った最小構成か、今の構成のどちらか。
* 基準点に特定のルールやスキルを足した worktree も起動するか。足し算の候補は、引き算で差が出た要素から選ぶ。
* ユーザー単位の設定（グローバルの CLAUDE.md、導入済みのプラグイン、MCP）も条件に含めるか。含めないと、リポジトリから削っても効き続け、差が見えなくなる。外すなら条件ごとに設定ディレクトリを分ける。

## 進め方

1. 条件ごとに、同じ起点から worktree とブランチ（`exp/<課題>-<条件>`）を作り、その中だけで削除や追加を行う。削ったものを履歴から読めないように、必要なら親の無いコミットを作る。元のブランチと履歴は書き換えない。
2. 条件ごとに別のセッションを同じモデル・effort で立てる。Orca があればタブに分ける。どのセッションにも、課題の文、その条件のやり方、共通の決まり（その worktree の中だけで作業する、専用の DB・ポートを使う、ブランチを切り替えない、push・deploy・外部への送信をしない、終えたらそのブランチにコミットする）を渡す。条件ではない指示は全条件で同じにする。
3. 各セッションの JSONL の場所を記録する（Claude Code なら `<CLAUDE_CONFIG_DIR>/projects/<worktree のパスの / を - にしたもの>/`。サブエージェントの記録はその下）。
4. 全条件のセッションがコミットしたら、評価役を読み取り専用で起動して評価させる（Codex なら `codex exec -s read-only`）。依頼には、課題の文、条件ごとの構成の差、worktree・ブランチ・成果のコミット・JSONL のパス、評価の出力先を書く。
5. 評価をもとに推奨構成を決め、ユーザーに結果と推奨を渡す。共有の形を求められたら HTML のアーティファクトなどにする。
6. ユーザーが承認したら、推奨構成を対象リポジトリに組み上げる（不要になった CLAUDE.md・ルール・スキルを削る、効いたものを残す・足す）。差が小さく判断できない要素は、削らず次回の比較に回す。

## 評価で必ず出させること

* 結論（3 行以内）と推奨構成。推測と事実を分ける。
* 目的の 6 観点ごとの条件の順位と根拠。
* 数値の比較: 経過時間、ツール呼び出し、トークン（キャッシュ読み出しを分ける）、失敗とやり直し、ユーザーへの質問、コミット数、差分の行数、足したテストの数。
* 課題の要件ごとの正しさと、条件の間の見落としの対照表。バグの疑いはファイル:行と根拠を付ける。
* 設計判断の比較: 条件ごとにどこで何を決めたか、その判断が途中で揺れたか。
* SubAgent とレビューの動き（誰が、いつ、何を見て、指摘をどう扱ったか）。
* 差を生んだ原因が条件そのものか、それに伴って変わった別の要因（レビュー回数、テストの範囲等）か。1 回の試行では偶然の差もあるため、差が小さいものはそう明記する。

## 注意

* 「worktree を使わない」決まりがあるリポジトリでも、このスキルを使うときだけは例外として worktree を作る。実験のブランチは push しない。
* 片付け（worktree・ブランチ・DB・コンテナ・条件用の設定ディレクトリの削除）は、ユーザーが評価を読んで許可した後に行う。

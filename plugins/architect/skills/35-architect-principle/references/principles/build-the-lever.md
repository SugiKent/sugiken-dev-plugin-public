# Build the Lever（てこを作る）

この原則は、一括作業に限らず、自明でない作業すべて（編集、移行、分析、検査）に当てる。手で作業せず、作業をする・証明する道具（codemod、スクリプト、生成器、サブエージェントが従う skill）を作る。道具は、レビュアーが再実行できる成果物になる。

codemod・生成器・スクリプトは毎回同じやり方で作業し、何度でもただで再実行できる。道具はレビュアーが読んで再実行し、作業を確かめられる 1 つの成果物になる。手作業の変更を確かめ直す方法は、やり直すことしかない。決定的なスクリプトは「信じて」を「これを実行して」に変える。

既定でてこを作る。作らないのは、一目で分かる明白な編集が 2、3 個だけの自明な作業のときだけ。

- 最初の 1 単位は手でやって手順を覚え、それから道具を作る。その単位で道具を再実行し、手作業の結果と diff を取って証明する。何度実行しても安全にする。
- 編集には codemod かスクリプト、繰り返しのファイルには生成器、分析には SQLite に落として問い合わせる処理、検証には再実行できる検査を使う。
- 決定的なてこは、並行作業に勝つ。道具が全単位を 1 回で処理できるなら、自分で実行する。スクリプトが処理できる作業を、サブエージェントを並べて手作業させない。
- サブエージェントに作業を配るときは、てこを全員が読む skill として書く。手順、検証の約束、触ってはいけない範囲を 1 つの成果物にまとめる。サブエージェントが黙って約束を書き換えられないよう、その書き込み範囲の外に置く。
- この原則を当てると、ファイルが 1 つできる。原則を挙げたのに差分に codemod・スクリプト・生成器・委任用の skill がないなら、当てていない。
- 作業がセッションより長生きするなら、てこをコミットする。

てこを作るかどうかは、繰り返しの多さより、作業が自明かどうかで決める。一度きりの作業でも、てこがあって初めて作業を確かめられるなら、てこを作る価値がある。[Laziness Protocol](laziness-protocol.md) に従い、作業をする・証明する最小のスクリプトを作る。フレームワークは作らない。

[Encode Lessons in Structure](encode-lessons-in-structure.md) とは別物。あちらは繰り返す指示を長持ちするガードレールにする。こちらは目の前の作業の処理量とレビューのしやすさのため。検証そのものをスクリプトにする話は [Prove It Works](prove-it-works.md) を見る。

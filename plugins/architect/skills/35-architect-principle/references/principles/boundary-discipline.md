# Boundary Discipline（境界の規律）

検証・エラー処理・フレームワークのアダプタをつなぐときに当てる。ガードはシステムの境界（CLI、設定、ネットワーク、外部 API）に集め、内部の型は信頼し、業務ロジックは純粋な関数に置く。

検証・型の絞り込み・エラー処理はシステムの境界に置く。内部のコードは無条件に信頼する。業務ロジックは純粋な関数に住む。外殻は薄く、機械的にする。

**理由。** 散らばった検証はうるさく、重複し、安全だという錯覚を生む。ロジックをフレームワークの配線から出しておけば、フレームワークなしでテストできる。

**やり方。**

- **境界では**（CLI 引数、設定ファイル、外部 API、ネットワークのプロトコル）、検証し、エラーを返し、防御的に扱う。
- **システムの内側では**、型の付いたデータを使い、エラーを伝え、検証し直さない。型を信頼する。
- **境界をまたぐときは**、ドメインの概念を出し、境界の内部表現は外に出さない。汎用の仕組みは内側に、特定の方針は端に置く。

**当てどころ。**

検証とエラー処理。

- 設定は、パースする時点（境界）で検証する。業務ロジックの中で検証すると、同じ検査が使う場所ごとに散らばる。
- 生のデータは境界でドメインの型にパースする。
- 通信・保存・フレームワーク・ワイヤ形式の型を、公開する表面から再 export しない。
- 境界で検証済みなら、呼び出しの奥で nil の検査を重ねない。

コードの配置。

- 業務ロジックは、フレームワークに依存しない純粋な関数に置く。
- パース関数は、生のバイトから型付きの状態への純粋な変換にする。
- プロンプトの組み立ては、構造化された状態を入れて文字列を出す。
- 採点や評価は、状態から結果への純粋な変換にする。

**確かめ方。**

- 「このデータは今まさにシステムの境界をまたいでいるか」。またいでいないなら、その検証は重複している。
- 「これは外殻が呼ぶだけの純粋な関数にできるか」。できるなら切り出す。

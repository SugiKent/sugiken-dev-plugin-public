# Separate Before Serializing Shared State（直列化の前に共有をなくす）

並行に動く主体が、同じファイル・ブランチ・キー・状態オブジェクトへ書き込みうるときに当てる。まず共有をなくす。1 つの共有された書き込み先が本当の不変条件であるときだけ、構造で直列化する。

並行に動く主体が書き換え可能な状態を共有しうるなら、まず「本当に同じ書き換え可能なオブジェクトが要るか」を問う。要らないなら共有をなくす。共有が本物なら、直列化を構造で強制する（ロックファイル、順番に進む段階、排他的な所有）。指示や慣習は並行制御にならない。

**理由。** 共有状態への並行な書き込みは競合状態を生む。競合状態はたまにしか起きず、再現しにくく、デバッグが高くつく。

**やり方。**

1. **書き換え可能な共有状態を特定する**（両者が読み書きするファイル、両者が push するブランチ、両者が定義して使う API）。
2. **既定では、共有された書き込み先をなくす。** 「この主体たちは 1 つの正本のオブジェクトが要るのか、それとも独立した事実を出しているだけか」を問う。主体ごとに専用のファイル・キー・ブランチ・状態ディレクトリを持たせ、読む側・報告する側の境界でだけ合わせる。2 つのワーカーが 1 つの `state.json` にそれぞれの `lastX` フィールドを書くのは、まだ共有された書き換えになる。`indexer-state.json` と `metrics-state.json` に分ければ共有ではない。
3. **1 つの共有された書き込み先が本当の不変条件であるときだけ、アクセスを構造で直列化する**（ロックファイル、順番に進む段階、書き手を 1 つにした actor、atomic な compare-and-swap）。「ロックが要る」は確かめるべき設計の臭いとして扱い、既定の答えにしない。

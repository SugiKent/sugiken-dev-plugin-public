# コードレビューと品質

## 役割

このスキルは、指定された対象の品質とリスクを評価し、根拠のある指摘と改善案を返す。

レビューをいつ行うか、誰が実施するか、マージ・コミット・リリースを進めるかは規定しない。利用者から与えられた範囲と目的に従う。

## 評価軸

### 正確性

- 仕様・契約・期待する振る舞いと一致するか
- 空値、境界値、失敗経路、並行実行で破綻しないか
- テストが実装詳細でなく振る舞いを検証しているか

### 可読性とシンプルさ

- 名前、責務、制御フローが理解しやすいか
- 投機的な抽象化、不要な分岐、死んだコードがないか
- 同じ形の分岐が繰り返され、モデルや境界の不足を示していないか

### アーキテクチャ

- モジュール境界、依存方向、責務の置き場所が妥当か
- 機能固有のロジックが共有モジュールへ漏れていないか
- 抽象化が増やす概念よりも、削減する複雑さが大きいか

構造上のトレードオフは `35-architect-principle` を参照する。

### セキュリティ

- 信頼できない入力が境界で検証されるか
- 認証・認可・シークレット・外部通信の扱いが適切か
- インジェクション、XSS、SSRF、情報漏えいにつながる経路がないか

必要に応じて `35-architect-security` を参照する。

### パフォーマンス

- N+1、無制限取得、無制限ループ、不要な再計算がないか
- データ量やホットパスに対する上限・ページネーションがあるか

必要に応じて `references/performance-checklist.md` を参照する。

## 指摘の書き方

重要なものから順に、対象箇所・問題・影響・推奨する変更を示す。

| 接頭辞 | 意味 |
|---|---|
| **Critical:** | データ損失、脆弱性、重大な機能破壊につながる |
| **Required:** | 要件や契約を満たすために修正が必要 |
| **Optional:** | 品質・保守性を上げる提案 |
| **Nit:** | 任意の軽微な改善 |
| **FYI:** | 判断材料となる情報 |

構造的な問題には、単に「複雑」と言うのではなく、分岐の集約、責務の移動、境界の明示、不要な抽象の削除など、具体的な再構成を提案する。

## 出力

```markdown
## レビュー結果

### 前提・対象範囲
- …

### 指摘
- **Required:** `path:line` — 問題、影響、推奨変更

### 未確認事項
- …

### 総評
- …
```

テスト、ビルド、手動確認などの実施状況が不明な場合は、合否を推測せず未確認事項として記載する。

# コードレビューと品質

## 役割

このスキルは、指定された対象の品質とリスクを評価し、根拠のある指摘と改善案を返す。

レビューをいつ行うか、誰が実施するか、マージ・コミット・リリースを進めるかは規定しない。利用者から与えられた範囲と目的に従う。

## 評価軸

### 正確性

- 仕様・契約・期待する振る舞いと一致するか
- 空値、境界値、失敗経路、並行実行で破綻しないか
- テストが実装詳細でなく振る舞いを検証しているか

### 根本原因か症状か

- 修正が実際の問題を直しているか、ガード・再試行・キャスト・握りつぶしで症状に蓋をしていないか
- 回避策がなぜ要るのか。本来の修正は別のモジュールの約束の側にないか
- 「X をしないで」というコメントや覚えておくべき慣習で済ませていないか。型・lint・実行時の検査で誤りを不可能にできないか

レビュアーは、変更したファイルの外にある呼び出し元・呼び出し先・型の定義まで読んでから判断する。観点の詳細は `35-architect-interrogate` の `references/rubric.md`「根本原因か症状か」を参照する。

### 可読性とシンプルさ

- 名前、責務、制御フローが理解しやすいか
- 投機的な抽象化、不要な分岐、死んだコードがないか
- 同じ形の分岐が繰り返され、モデルや境界の不足を示していないか
- 振る舞いを保ったまま分岐・補助関数・層をまるごと消せる組み替え（コード柔道の一手）を見逃していないか
- 複雑さが成し遂げることに見合っているか。呼び出し箇所が 1 つの抽象、まだない場合のための設定、移行が終わった互換経路が残っていないか

承認の基準は `35-architect-interrogate` の `references/code-quality-lens.md`「承認の基準」に従う。振る舞いが正しそうだというだけで承認しない。

### アーキテクチャ

- モジュール境界、依存方向、責務の置き場所が妥当か
- 機能固有のロジックが共有モジュールへ漏れていないか
- 抽象化が増やす概念よりも、削減する複雑さが大きいか

構造上のトレードオフは `35-architect-principle` を参照する。

### 検証

- テストが、利用者が観測できる振る舞いを確かめているか。実装の詳細に縛られていないか
- バグ修正に、そのバグを捕まえるテストか再現の確認があるか
- 確かめているのは実物の出力や値か。ファイルの更新時刻、キャッシュした状態、委任先の自己申告は、本物が壊れていても正常に見えるので証拠にならない

### セキュリティ

- 信頼できない入力が境界で検証されるか
- 認証・認可・シークレット・外部通信の扱いが適切か
- インジェクション、XSS、SSRF、情報漏えいにつながる経路がないか

必要に応じて `35-architect-security` を参照する。

### パフォーマンス

- N+1、無制限取得、無制限ループ、不要な再計算がないか
- データ量やホットパスに対する上限・ページネーションがあるか

必要に応じて `references/performance-checklist.md` を参照する。

## 指摘の書き方

重要なものから順に、対象箇所・問題・影響・推奨する変更を示す。

| 接頭辞 | 意味 |
|---|---|
| **Critical:** | データ損失、脆弱性、重大な機能破壊につながる |
| **Required:** | 要件や契約を満たすために修正が必要 |
| **Optional:** | 品質・保守性を上げる提案 |
| **Nit:** | 任意の軽微な改善 |
| **FYI:** | 判断材料となる情報 |

構造的な問題を指摘するときは、分岐の集約、責務の移動、境界の明示、不要な抽象の削除など、具体的な再構成を提案する。「複雑」の一言だけでは、作者は何を直せばよいか分からない。

バグの可能性は、実行の経路をたどって示す。「null になりうる」と書くだけで終えず、null にする呼び出しの連鎖を示す。上流で検証済み、または型が防いでいるなら指摘にしない。「自分なら別のやり方にした」に帰着する好みは、今のやり方の具体的な問題を示せない限り指摘にしない。何も見つからなければ「指摘なし」と書く。空のレビューは正当な結果である。

複数のレビュアー・複数のモデルの指摘をまとめるときは、`35-architect-interrogate` の手順 4・5 で統合し、Act on / Consider / Noted / Dismissed に仕分ける。

## 出力

```markdown
## レビュー結果

### 前提・対象範囲
- …

### 指摘
- **Required:** `path:line` — 問題、影響、推奨変更

### 未確認事項
- …

### 総評
- …
```

テスト、ビルド、手動確認などの実施状況が不明な場合は、合否を推測せず未確認事項として記載する。

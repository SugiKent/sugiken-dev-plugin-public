# 重大バグ検出レビュー

## 役割

対象の変更を精査し、レビューをすり抜けた**重大な正確性の問題だけ**を報告する。品質全般の多軸レビューではない。網羅性より、確度と影響度を優先する。

多軸（可読性・アーキテクチャ・パフォーマンスを含む）のレビューが必要なら `35-architect-code-review` を使う。

## レビュー対象の決め方

- コンテキストに PR がある場合はその PR の変更内容
- PR がない場合は直近の diff（作業ツリー、または対象ブランチとベースの差分）から総合的に判定する

## 手順

1. **既報告バグの台帳 `docs/quality/critical-bug-review/reported-bugs.md` を確認する**（後述「重複報告の防止」）
2. 変更の全体像と、影響を受ける処理経路を把握する
3. 重大度の高い候補を洗い出す
4. 各候補について、呼び出し元・呼び出し先・保存先・エラーハンドリングまで経路を追跡し、確信度の基準を満たすか検証する
5. 基準を満たしたものだけを、重大度順に報告する
6. 台帳 `docs/quality/critical-bug-review/reported-bugs.md` を更新する

## 報告対象

以下のような深刻な影響を引き起こす問題に限定する。

- データ消失・データ破損
- アプリケーションや重要機能のクラッシュ
- 認可・権限・認証の回避
- 重大な情報漏えい
- 主要なユーザーフローを広範囲に壊す不具合
- 書き込みの取りこぼしにつながる競合状態
- 無限ループ、枯渇、重大なリソースリーク
- 意図しないデータ切り詰めや不可逆な変換

## レビュー方針

- 影響範囲が大きい振る舞いの変更を優先する
- 差分だけをパターンマッチで判断せず、処理経路全体を追跡する
- API、DB 更新、認可判定、非同期処理、キュー、キャッシュ、外部連携、例外処理、リトライ処理は重点的に確認する
- 具体的な再現シナリオを構築できる問題だけを報告する

**原則として報告しないもの**（ノイズは、本当に重大な指摘の価値を下げる）:

- スタイルや可読性だけの問題
- 軽微な UX 劣化
- 実害が不明確な理論上の懸念
- 現実的なトリガーを説明できない問題
- 重大な影響につながらない境界ケース

## 確信度の基準

不具合として指摘するには、次の 4 つをすべて満たす必要がある。

1. 具体的な入力・状態・操作手順など、現実的な発生条件を説明できる
2. その条件で実際にどのコードパスを通り、何が壊れるかを説明できる
3. 影響がデータ消失、クラッシュ、セキュリティ問題、または重大なユーザー影響に該当する
4. 対象の変更によって新たに発生した、または悪化した問題である

確信が十分でない場合は、重大バグとして断定しない。懸念点と、確信を得るために確認すべき事項を簡潔に示す。

## 重複報告の防止

docs の扱いは [[01-docs-management]] に従い、既報告バグの台帳は `docs/quality/critical-bug-review/reported-bugs.md` に置く。

レビュー開始前にこのファイルを確認する。見つからない場合は空として扱い、記録が必要になった時点で `docs/quality/critical-bug-review/` ごと作成する。

このファイルには、過去のレビューで報告済みの不具合が 1 行ごとに記録されている。

```
- <不具合の概要（該当箇所と根本原因）> | <PR URL> | <status: open | rejected> | <記録日 YYYY-MM-DD>
```

記録済みの不具合と一致する場合は、対応する PR の状態を確認し、次のとおり扱う。

| PR の状態 | 対応 |
|---|---|
| オープン中 | 再報告しない。レビュー結果に「既存の修正 PR がレビュー待ち」であることと URL を記載する |
| マージ済み | 解消済みとして台帳から該当エントリを削除する |
| マージされずクローズ | エントリは残し、status を `rejected` に更新する。関連コードが大きく変更されていない限り再報告しない |
| 別の変更で既に解消 | 台帳から該当エントリを削除する |
| `rejected` かつ記録日から 30 日超 | 削除する。コードの変化を踏まえ、新しい問題として改めて評価できるようにするため |

台帳には、オープン中または `rejected` の PR に対応する不具合だけを保持する。レビュー履歴、調査メモ、スキャン結果は記録しない。

台帳は継続更新する正本なので、冒頭に `最終更新: YYYY-MM-DD-HHmm` を置き、更新のたびに書き換える。各エントリの記録日が変更履歴を兼ねるため、末尾の変更履歴は残さない。

## 出力

レビューコメント、コードコメント、PR に関する記述はすべて日本語で書く。

重大な不具合を発見した場合は、重大度順に次の形式で出力する。

```markdown
### <タイトル: 問題の要約>

- **重大度**: Critical | High
- **該当箇所**: ファイル名 / 関数名 / 行番号または該当コード
- **影響**: 何が壊れるか、誰に影響するか
- **根本原因**: なぜその不具合が発生するか
- **再現シナリオ**: 問題が起きる具体的な条件と手順
- **推奨修正**: 最小限で安全な修正方針
```

既報告の不具合に該当するものがあった場合は、末尾に次を添える。

```markdown
### 既知の不具合（報告済み）

- <概要> — 修正 PR がレビュー待ち: <PR URL>
```

不具合が見つからなかった場合は、次のように短く報告する。

> 重大な正確性・セキュリティ・データ整合性の問題は確認できませんでした。

指摘は簡潔で具体的に書き、推測を事実のように扱わない。

# Interrogate（複数モデルの敵対的レビュー）

設定したモデルごとにレビュアーを 1 つ起動し、コードの変更を敵対的にレビューさせる。敵対的な信号は、モデルの多様性から生まれる。モデルごとに盲点が違うので、同じモデルに役柄を割り当てても同じ所を見落とす。成果物は統合した判定で、変更は自動で適用しない。pstack の `interrogate` を Claude Code に合わせて日本語化した。

抽象的な計画にこのレビューを当てない。コードのない計画を敵対的にレビューさせると、レビュアーは起きない理論上のリスクや端の条件を作り出す。計画の問いは試作で決め、作ったものをレビューする。設計の前提を疑うなら `35-architect-doubt-driven-development` を使う。

## 手順 1. 範囲を決める

レビューするものを文脈から特定する。

- 利用者が特定のファイルや差分を指したなら、それを使う。
- 機能ブランチにいるなら、`git diff main...HEAD`（または適切なベースブランチ）で変更一式を取る。
- 利用者の発言が直近の作業を指すなら、関係するファイルを集める。

差分かファイルの中身を、レビュアーがコードを理解するのに要る周辺のファイルと一緒にまとめる。

## 手順 2. 意図を述べる

レビュアーを起動する前に、利用者の発言、コミットメッセージ、PR の説明（あれば）、コードから、意図を 1 段落ではっきり述べる。SDD の change では proposal・specs・design・tasks が意図の正本になる。意図に自信がなければ、進める前に利用者に尋ねる。

## 手順 3. レビュアーを起動する

すべてのレビュアーを 1 つの発言で起動し、レビュアー A、B… とラベルを付ける。既定は 2 つ。

| レビュアー | 既定 |
|---|---|
| A | `architect:architect-interrogate-reviewer` を `model: "opus"` で起動する |
| B | Codex MCP（`sandbox: read-only`、`approval-policy: never`）。使えなければ `architect:architect-interrogate-reviewer` を `model: "sonnet"` で起動し、系統の多様性が下がったことを判定に記す |

すべてのレビュアーに、`references/reviewer-prompt.md` の同じ雛形を埋めて渡す。埋めるのは、述べた意図、差分かファイルの中身、`references/rubric.md` の観点、`references/code-quality-lens.md` のコード品質の目。Codex は plugin のファイルを読めない場合があるので、観点と目の本文を依頼文へ貼る。推論の深さ（`effort`）は仕事に合わせて選ぶ。

起動したレビュアーが失敗したら、残りで続け、脱落を判定に記す。レビュアーがファイルを変えていないことを、終わった後に `git status` で確かめる。

## 手順 4. 統合する

結果が返るにつれ、1 つの全体像を組む。全レビュアーの指摘を読み、違う言い方で同じ問題を述べている指摘をまとめ、どのモデルがそれを挙げたかを記す。2 つ以上のモデルが独立に挙げた指摘は、いちばん強い信号になる。1 つのモデルだけの指摘も読むが、相応に重みを下げる。意見の食い違いを記す。あるモデルが指摘し、別のモデルが明示的に逆を言うなら、それは判定の文脈になる。

## 手順 5. リードとして判定する

あなたはリードレビュアーで、実利を取る上級エンジニアとして判断する。指摘を数えて並べるだけの集計係になると、うるさい指摘と本物の問題を同じ重さで扱ってしまう。`references/lead-judgment.md` を読む。すべての指摘を 4 つのどれかに入れ、挙げたモデルと 1 行の理由を添える。

- **Act on。** 実際の目標に照らして、正確性・セキュリティ・保守性を損なう本物の問題。本物の PR ならマージを止める。
- **Consider。** 正当だが、今それに手を付けるコストを上回るか確信がないもの。利用者に見てもらう価値がある。
- **Noted。** 技術的には正しいが、行動に移せないもの。文脈次第、早すぎる最適化、今の段階では影響が小さい。
- **Dismissed。** 誤り、重箱の隅、文脈の欠落。短い理由を添える。

変更は適用しない。呼び出し元（SDD の apply など）が Act on を直す。

## 出力

```markdown
### 意図
> <手順 2 の意図の段落>

### レビュアー
- レビュアー <ラベル> は <モデル> で、指摘は <N> 件（1 レビュアー 1 行）

### Act on
<各項目に、内容、挙げたモデル、なぜ重要か>

### Consider
<各項目に、内容、挙げたモデル、トレードオフ>

### Noted
<短い一覧>

### Dismissed
<各項目に短い理由>

### 一致の地図
<モデル同士が一致した点と分かれた点、その形が何を語るか>
```

# Interrogate（複数モデルの敵対的レビュー）

設定したモデルごとにレビュアーを 1 つ起動し、コードの変更を敵対的にレビューさせる。敵対的な信号は、モデルの多様性から生まれる。モデルごとに盲点が違うので、同じモデルに役柄を割り当てても同じ所を見落とす。成果物は統合した判定で、変更は自動で適用しない。

抽象的な計画にこのレビューを当てない。コードのない計画を敵対的にレビューさせると、レビュアーは起きない理論上のリスクや端の条件を作り出す。計画の問いは試作で決め、作ったものをレビューする。設計の前提を疑うなら `35-architect-doubt-driven-development` を使う。

## 手順 1. 範囲を決める

レビューするものを文脈から特定する。

- 利用者が特定のファイルや差分を指したなら、それを使う。
- 機能ブランチにいるなら、`git diff main...HEAD`（または適切なベースブランチ）で変更一式を取る。
- 利用者の発言が直近の作業を指すなら、関係するファイルを集める。

差分かファイルの中身を、レビュアーがコードを理解するのに要る周辺のファイルと一緒にまとめる。差分だけを見るレビュアーは、変更がシステムに合うか、他を壊していないかを判断できない。そのため、呼び出し元・呼び出し先・同じ状態や設定を共有するモジュールの場所も渡し、レビュアーにはリポジトリ全体を読める状態で起動する。

変更を作ったエージェントが実行したテスト・ビルド・画面確認などがあれば、そのコマンドと出力を「実行の証拠」としてまとめる。「完了した」「通った」という宣言は証拠に入れない。証拠が無ければ、無いことを書く。

## 手順 2. 意図を述べる

レビュアーを起動する前に、利用者の発言、コミットメッセージ、PR の説明（あれば）、コードから、意図を 1 段落ではっきり述べる。SDD の change では proposal・specs・design・tasks が意図の正本になる。意図には、変更が何のためにあるか（change の目的）を含める。レビュアーは目的に照らして、問題を解決しているか、システムに合うか、他を壊していないかを確かめるため。意図には目標（誰の何を変えるか）だけを書き、目標を達成する手段（回避策とその理由）は書かない。レビュアーは意図を疑わないので、手段を意図に入れると、手段を生んだ根本原因が指摘されなくなる。手段は、疑ってよいレビュー対象として差分か design の側で渡す。意図に自信がなければ、進める前に利用者に尋ねる。

## 手順 3. レビュアーを起動する

すべてのレビュアーを 1 つの発言で起動し、レビュアー A、B… とラベルを付ける。既定は 2 つ。レビュアーは変更を作った会話を持たない新しいコンテキストで起動する。作った側の思い込みを引き継がずに差分を読ませるため。

| レビュアー | 既定 |
|---|---|
| A | `architect:architect-interrogate-reviewer` を `model: "opus"` で起動する |
| B | Codex プラグインの `codex:codex-rescue` サブエージェント。依頼文で、ファイルを編集せず指摘だけを返すよう伝える。使えなければ `architect:architect-interrogate-reviewer` を `model: "sonnet"` で起動し、系統の多様性が下がったことを判定に記す |

すべてのレビュアーに、`references/reviewer-prompt.md` の同じ雛形を埋めて渡す。埋めるのは、述べた意図、差分かファイルの中身、手順 1 の実行の証拠、`references/rubric.md` の観点、`references/code-quality-lens.md` のコード品質の目。Codex は plugin のファイルを読めない場合があるので、観点と目の本文を依頼文へ貼る。推論の深さ（`effort`）は仕事に合わせて選ぶ。

起動したレビュアーが失敗したら、残りで続け、脱落を判定に記す。レビュアーがファイルを変えていないことを、終わった後に `git status` で確かめる。

## 手順 4. 統合し、検証する

結果が返るにつれ、1 つの全体像を組む。全レビュアーの指摘を読み、違う言い方で同じ問題を述べている指摘をまとめ、どのモデルがそれを挙げたかを記す。2 つ以上のモデルが独立に挙げた指摘は、いちばん強い信号になる。1 つのモデルだけの指摘も読むが、相応に重みを下げる。意見の食い違いを記す。あるモデルが指摘し、別のモデルが明示的に逆を言うなら、それは判定の文脈になる。

統合した指摘のうち重大度が `重大` と `中` のものを、探したレビュアーとは別の検証役に確かめさせる。敵対的なレビュアーは筋の通った偽の指摘も書くので、探す役と確かめる役を分け、合意の取れた指摘だけを報告に載せる。`Nit` は検証に回さず、手順 5 でリードが Noted か Dismissed に入れる。

* 検証役は 3 つを 1 つの発言で起動する。`architect:architect-interrogate-verifier` を 2 つ（`model: "opus"`）と、別系統のモデル 1 つ（手順 3 のレビュアー B と同じ選び方）。どれも新しいコンテキストで起動し、探したレビュアーの推論は渡さない。
* 各検証役に、`references/verifier-prompt.md` を埋めて渡す。埋めるのは、意図、差分、実行の証拠、検証する指摘の一覧（場所・指摘・根拠）。
* 検証役は指摘ごとに `成立` / `不成立` / `判断できない` を返し、根拠の強さを段階で示す。段階は `35-architect-doubt-driven-development` の「確かさの段階」を、読むだけの役に合わせて依頼文に写したもの。段階 2（行を指した）に届かない `成立` は `判断できない` として数える。
* 3 つのうち 2 つ以上が `成立` とした指摘だけを、手順 5 の Act on と Consider の候補にする。2 つ以上が `不成立` とした指摘は Dismissed に入れ、検証役の反証を理由にする。どちらにも届かない指摘は「合意に届かなかった指摘」に残し、直す対象にはしない。セキュリティ・データ損失の指摘で合意に届かなかったものも同じ扱いにするが、利用者が見落とさないよう、その節の先頭に置く。
* 検証役が失敗したら、残りの過半数で判定し、脱落を判定に記す。残りが 1 つなら合意は取れないので、すべてを「合意に届かなかった指摘」に入れる。終わった後に `git status` でファイルが変わっていないことを確かめる。
* `重大` と `中` の指摘が 0 件なら、検証役は起動しない。

## 手順 5. リードとして判定する

あなたはリードレビュアーで、実利を取る上級エンジニアとして判断する。仕分けるのは、手順 4 で合意の取れた指摘と `Nit` だけ。合意の取れた指摘も、lead-judgment の原則で Consider や Noted に下げてよい。指摘を数えて並べるだけの集計係になると、うるさい指摘と本物の問題を同じ重さで扱ってしまう。`references/lead-judgment.md` を読む。それらを 4 つのどれかに入れ、挙げたモデルと 1 行の理由を添える。

- **Act on。** 実際の目標に照らして、正確性・セキュリティ・保守性を損なう本物の問題。本物の PR ならマージを止める。
- **Consider。** 正当だが、今それに手を付けるコストを上回るか確信がないもの。利用者に見てもらう価値がある。
- **Noted。** 技術的には正しいが、行動に移せないもの。文脈次第、早すぎる最適化、今の段階では影響が小さい。
- **Dismissed。** 誤り、重箱の隅、文脈の欠落。短い理由を添える。

変更は適用しない。呼び出し元（SDD の apply など）が Act on を直す。

## 出力

```markdown
### 意図
> <手順 2 の意図の段落>

### レビュアー
- レビュアー <ラベル> は <モデル> で、指摘は <N> 件（1 レビュアー 1 行）
- 検証役は <モデルの一覧> で、検証した指摘は <N> 件、合意の取れた指摘は <N> 件

### Act on
<各項目に、内容、挙げたモデル、なぜ重要か>

### Consider
<各項目に、内容、挙げたモデル、トレードオフ>

### Noted
<短い一覧>

### Dismissed
<各項目に短い理由。検証で退けたものは、反証した検証役と反証>

### 合意に届かなかった指摘
<各項目に、内容、検証の票（成立 / 不成立 / 判断できない の数）。セキュリティ・データ損失を先頭に置く>

### 一致の地図
<モデル同士が一致した点と分かれた点、その形が何を語るか>
```

# リードの判定の枠組み

## 仕分けの原則

### 重箱の隅の引力

レビュアー、特に敵対的なレビュアーは、レビューを埋めようとする。重大な問題が見つからないと、nit を膨らませて埋める。あるレビュアーの指摘がすべて nit とスタイルの好みなら、コードはおそらく問題ない。そう言う。

### 仮定か実際か

「ここに null を渡されたら」が指摘になるのは、呼び出し元が実際に null を渡せるときだけ。呼び出し箇所をたどる。上流で入力が検証されている、または型システムが防いでいるなら退ける。差分だけを見るレビュアーには呼び出しの連鎖全体が見えないことがある。あなたには見える。

### 早すぎる抽象の勧め

レビュアーは、関数の切り出し、インターフェースの追加、抽象の作成をよく勧める。このコードは 2 つ目の変わり方をする必要があるか。ないなら、その抽象は早すぎる。動く単純なインラインのコードは、今の範囲には大げさなきれいな抽象に勝つ。

### 「自分なら別のやり方にした」

コードレビューでいちばん多い偽陽性。「別のやり方が好み」に帰着する指摘は、今のやり方の具体的な問題をレビュアーが示さない限り、バグでも設計の欠陥でもなく、行動に移せない。退け、理由を言う。

### 文脈の欠落の兆し

レビュアーが文脈を理解していなかったことを示す指摘に気を付ける。

- 作者が書いていない・変えていないコードの変更を勧める。
- コードベースのほかの部分と一貫したパターンを指摘する（レビュアーがそれを知らないだけ）。
- あなたが知っている制約とぶつかるやり方を勧める。

これらは限られた情報で働くレビュアーの正直な間違いなので、穏やかに退ける。

## レビュアーが正しいとき

居心地が悪いという理由で指摘を退けない。敵対的レビューの要点は、自分が見逃すものを捕まえることにある。指摘が注意に値する兆し。

- 複数のモデルが独立に同じ問題を挙げる（合意の信号）。
- 指摘が、具体的な実行の経路を示している。
- 指摘が、あなたのコードの頭の中のモデルの穴を明らかにする。
- 指摘を読んで「…確かにそうだ」と思う。

セキュリティの指摘と正確性のバグは、1 つのモデルからでも退ける前に特に慎重に吟味する。

## 外部レビューの指摘

PR に付いたレビュー bot やセキュリティレビューの指摘も、上の原則で仕分ける。既定で無視するのでも、すべてをコード変更として扱うのでもない。各スレッドを、手を動かす前に分類する。

- **直す。** 正確性・セキュリティ・プライバシー・データ損失・認証・課金・migration・冪等性・競合状態・出荷済みの振る舞いの問題として、もっともらしい指摘。それを持つ最も下の PR で直し、コミットを添えて返信する。
- **退ける。** 指摘の懸念が、今のコードと文脈からコード変更を要しないと証明できる。短い理由を返信する。
- **尋ねる。** 新しい種類の指摘、重大度が高い、セキュリティ・プライバシー・データに関わる、曖昧。推測せず利用者に尋ねる。

迷ったら尋ねる。うるさいコード品質の指摘を飛ばすのは安いが、本物のデータやセキュリティのバグを飛ばすのは安くない。次は、以前の PR で似たものを退けたことがあっても、自動では飛ばさない。

- セキュリティ、プライバシー、認証、課金、データの保持、権限の境界を扱う指摘。
- 重大度の高い指摘。
- migration、スキーマ、冪等性、並行性、システムをまたぐ振る舞いの指摘。
- 提案された修正が小さく、製品の意図を変えずに明らかにリスクを下げる指摘。

指摘が、PR の中の文書やテストの食い違いのように、コマンド 1 つで確かめられる主張なら、分類の前にそのコマンドを実行する。結果が赤ならそのまま証拠になり、緑なら退ける返信の具体的な反証になる。

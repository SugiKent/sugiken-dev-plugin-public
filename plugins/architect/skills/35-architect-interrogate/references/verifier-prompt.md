# 検証役への依頼文の雛形

手順 4 で、各検証役への依頼文を、この雛形の差し込み口を埋めて作る。どの検証役にも同じ文を渡す。

---

あなたはコードレビューの指摘を検証する役です。別のレビュアーが挙げた指摘が本当に成り立つかを、コードを読んで確かめてください。指摘を増やす役ではありません。新しい問題に気づいても、一覧の最後に 1 行で書くだけにしてください。

ファイルの編集・作成・削除、整形、テストの実行、git の書き込み操作はしないでください。

## 意図

> {INTENT}

## レビュー対象のコード

{DIFF_OR_FILES}

リポジトリ全体を読めます。指摘が言う実行の経路を、呼び出し元・呼び出し先・型・設定までたどってください。

## 実行の証拠

{EVIDENCE}

## 検証する指摘

{FINDINGS}

## 判定のしかた

指摘ごとに、次のどれかを付けてください。

* `成立`: 指摘が言う悪い結果に届く実行の経路が、実際のコードにある。
* `不成立`: その経路は届かない。上流の検証、型、呼び出し元の制約、既存のテストなど、届かない理由をコードで示せる。
* `判断できない`: コードを読んでも決められない。何が分かれば決まるかを書く。

根拠には、どこまで確かめたかを次の段階で書いてください。

1. そう言っただけ。
2. 実在する `file:line` を指した。
3. 失敗の流れを一歩ずつたどった。
4. 誤っていれば落ちる小さなスクリプトかテストで動かした（読むだけの役なので、通常はここまで届かない）。

段階 1 の `成立` は `判断できない` として扱われます。筋の通った指摘の文章は、真偽にかかわらず正しく読めます。判定は、コードが指摘のとおりになっているかだけで決めてください。

## 出力

```
### 指摘 <番号>: <短い題>
**判定**: 成立 / 不成立 / 判断できない
**段階**: <1〜4>
**根拠**: <file:line と、たどった経路または届かない理由>
```

最後に `成立: N件 / 不成立: N件 / 判断できない: N件` を書いてください。

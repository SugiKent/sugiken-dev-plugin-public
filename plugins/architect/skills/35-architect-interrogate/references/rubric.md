# レビューの観点

当てはまる観点でレビューする。すべての変更にすべての観点が当てはまるわけではない。

## 正確性

コードは、意図が言うことを実際にしているか。

- 端の条件。空の入力、nil や undefined、境界値、並行アクセスをどう扱うか。
- エラー処理。エラーは捕まえられているか、伝えられているか、黙って握りつぶされていないか。
- off-by-one、型の強制変換、整数のオーバーフロー、文字列のエンコーディングの誤りがないか。
- 状態の管理。競合状態、古いクロージャ、宙に浮いた参照。
- 正常系と異常系の両方が動くか。
- 冪等性。この操作が 2 回動いたら、前回の実行が途中でクラッシュしていたら何が起きるか。答えが「残された状態による」なら、突き合わせの手順が欠けている。
- 並行性。複数の主体が同じ書き換え可能な状態（ファイル、ブランチ、共有データ）に触れうるなら、アクセスは構造（ロック、順番に進む段階、排他的な所有）で直列化されているか。それとも守られない慣習に頼っているか。

バグの可能性を見つけたら、実行の経路をたどる。「これは nil になりうる」と指摘するだけで終えず、nil にする呼び出しの連鎖を示す。

## 根本原因か症状か

コードは実際の問題を直しているか、症状に蓋をしているか。

この問いに答えるには、変更したファイルの外を見る必要があることが多い。周辺のコード（呼び出し元、呼び出し先、型の定義、兄弟のモジュール）を読み、変更が置かれているアーキテクチャを理解する。使える道具（Read、Grep、Glob）で呼び出しの連鎖をたどり、型を読み、コードがなぜあるのかを理解してから、変更が正しい層を扱っているかを判断する。

- より深い不変条件の違反を覆い隠すガード節。
- 壊れた約束を隠す再試行のロジック。
- モデル化の誤りを黙らせる型のキャスト。
- 回避策。なぜ要るのか。まともな修正はどんな形か。
- モジュール A の修正が、本当はモジュール B の約束の修正であるべき。
- 構造で済むところに指示を置いている。修正が「X をしないで」というコメントや、誰かが覚えておくべき慣習なら、誤りを不可能にする型の制約、lint のルール、実行時の検査にできないかを問う。

## 構造の健全性

コードは、属するシステムにうまく収まっているか。

- 境界の規律。検証はシステムの境界にあるか、業務ロジックに散らばっているか。データはシステムに入る場所で一度検証し、内側では信頼する。
- 抽象の水準。高い水準の調整と低い水準の詳細が混ざっていないか。
- 結合。この変更は、将来の変更を難しくする依存を持ち込んでいないか。
- データモデルの適合。データ構造は実際のアクセスパターンに合っているか。
- 後付けか組み込みか。新しい要求が最初から分かっていたら、コードはこの形だったか。それとも既存の設計に継ぎを当てたように見えるか。
- 古い二重経路。新しい API を入れながら古い API を生かしていないか。外部の利用者がいないなら、同じ波で呼び出し元を移し、古い経路を消す。恒久化する互換の層を残さない。

抽象がないことを理由に単純なコードを減点しない。早すぎる抽象は重複より悪い。

## 検証

読んで、このコードが動くと分かるか。

- テストはあるか。振る舞いを確かめているか、実装の詳細を確かめているか。
- 退行を捕まえる assert や不変条件はあるか。
- バグ修正なら、そのバグのテストはあるか。
- 統合の境界に触れるなら、経路全体がテストされているか。
- 実物を確かめているか。実際の値を読む代わりに、ファイルの更新時刻やキャッシュした状態で生存を確かめているなら、検証の穴になる。
- 委任した作業や非同期の作業では、実際の出力の成果物を確かめているか、自己申告や要約を信じているか。

## 複雑さの予算

複雑さは、コードが成し遂げることに見合っているか。

- 正確さも明快さも失わずに、もっと単純にできるコード。
- 呼び出し箇所が 1 つだけの抽象。
- まだ存在しない場合のための設定やパラメータ化。
- 死んだコード、使っていない import、名残りの引数。
- 作り込みすぎ。今の呼び出し元がない「念のため」のコード経路。
- もう要らない移行期の安定のために生かしている古い互換経路。移行が終わったなら足場を消す。
- 利用者の体験は、その複雑さを正当化するか。機能・操作・選択肢のどれも、ある理由を持たなければならない。半端な機能は、ない機能より悪い。

間違いでない限り、単純なほうがよい。

## セキュリティ

セキュリティの指摘ごとに、入力の経路をコードの中でたどって示す。

- 利用者の入力が、無害化されずに危険な行き先（SQL、shell、eval、innerHTML）へ流れる。
- 新しいエンドポイントの認証・認可の穴。
- コード、ログ、エラーメッセージの中のシークレット。
- セキュリティ上重要な経路に TOCTOU（検査した時点と使う時点のずれ）がないか。

詳しい観点は `35-architect-security` と、このリポジトリの `35-architect-code-review` の評価軸を参照する。

# コード品質の目

各レビュアーは、観点に加えてこのコード品質の目を当てる。実装の質、保守性、抽象の質、コードベースの健康に焦点を当てた厳しい基準。

何よりも、コードの構造に野心的であること。局所的な整理を見つけるだけで終えない。振る舞いを保ったまま、実装を劇的に単純・小さく・直接的・簡潔にする組み替え（「コード柔道」の一手）を積極的に探す。

## 中心の依頼

この基準から始める。

> 現在のブランチの変更について、深いコード品質の監査を行ってください。
> 振る舞いに影響を与えずにコード品質を意味のある形で上げるよう、変更の構造と実装を考え直してください。
> 抽象、モジュール性を改善し、スパゲッティコードを減らし、簡潔さと読みやすさを上げてください。
> 野心的に。コードベースの一部を組み替えて実装を改善する明確な道があるなら、それを推してください。
> とても徹底して、厳密に。二度測って一度で切ってください。

## 観点

各観点は一度だけ述べる。当てはまるものを当てる。

0. **構造の単純化に野心的であること。** 「もう少しきれいにできる」で止まらない。分岐・補助関数・モード・条件・層をまるごと消す捉え直しを探す。コード柔道の一手はたいていあると考える。既存のアーキテクチャをもっとうまく使い、変更を劇的に単純にする手のこと。複雑さを並べ替えずに消せるなら、強く推す。
1. **1000 行未満のファイルを 1000 行超えへ押し上げる PR は、とても強い理由がない限り認めない。** 強い臭いとして扱う。補助関数・部分コンポーネント・モジュールの切り出しを選ぶ。差分がこの線を越えるなら、先に分解すべきでないかを問う。見逃すのは、結果のファイルが明らかに整理されたままで、説得力のある構造上の理由があるときだけ。
2. **既存のコードにスパゲッティを育てない。** 無関係な流れに差し込んだ、新しい場当たりの条件・散らばった特別扱い・一度きりの分岐を疑う。「妙な場所にある妙な if 文」は設計の問題として扱う。スタイルの nit として流すと、次の変更が同じ流れにもう 1 本の分岐を足す。既存の経路を絡ませず、専用の補助関数・状態機械・モジュールへロジックを押し出すほうを選ぶ。
3. **動くコードでも、設計をきれいにするほうへ寄せる。** 振る舞いを保ったまま構造が意味のある形できれいになるなら、きれいなほうを推す。同じ複雑さをあちこちへ広げるリファクタリングより、動く部品を取り除く単純化を選ぶ。
4. **ハックや魔法より、直接的で退屈で保守できるコードを選ぶ。** 脆い・場当たりの・「魔法」の振る舞いは問題として扱う。単純なデータの形の前提を隠す汎用の仕組みを疑う。明快さを買わずに間接参照を足す、薄い抽象・恒等の包み・素通しの補助関数を指摘する。
5. **保守性に関わるなら、型と境界のきれいさを押す。** もっと明快な型の境界がありうるのに、不要な optional、`unknown`、`any`、キャストだらけのコードがあれば問う。ばらばらの形の場当たりのオブジェクトより、明示的な型付きのモデルを選ぶ。不明瞭な不変条件に黙った fallback で蓋をしている分岐があれば、境界を明示すべきでないかを問う。
6. **ロジックは正しい層に置き、既存の補助を再利用する。** 機能のロジックが共有の経路へ漏れている、実装の詳細が API を通して漏れているなら指摘する。一度きりの自作より、既存の正規のユーティリティを選ぶ。ずれを常態化させず、正しいパッケージ・サービス・モジュールへコードを押し出す。
7. **構造がきれいになるのが明らかなら、不要な直列の調整と非 atomic な更新を設計の臭いとして扱う。** 独立した作業が理由なく直列になっているなら、並行にすべきでないかを問う。関係する更新が状態を半端に残しうるなら、より atomic な構造を推す。細かい最適化にこだわりすぎないが、コードを脆くする避けられる調整の複雑さは指摘する。

## 出力の優先順位

構造上のコード品質の退行と、見逃した単純化を先に。次にスパゲッティと分岐の複雑さ。次に境界・型・ファイルの大きさの懸念。その後に小さなモジュール性と読みやすさの問題。

## 承認の基準

振る舞いが正しそうだというだけで承認しない。作者が正当化できない限り、次を止める理由として扱う。コード柔道の一手で消せる付随的な複雑さを多く残している。1000 行未満のファイルを 1000 行超えにする。既存の流れを絡ませる場当たりの分岐を足す。機能の検査を共有コードに散らす。不要な抽象・包み・キャストだらけの約束を足す。明確な正規の置き場があるのに、既存の補助を重複させる、またはロジックを誤った層に置く。これらに当たらなければ、行動に移せる明示的なフィードバックを残し、よりきれいな分解を推す。

## レビューの口調

直接的に、真剣に、品質に厳しく。無礼にはしないが、大きな保守性の問題を穏やかな提案に薄めない。コードがコードベースを汚しているなら、そう言う。実装が明らかな劇的単純化を見逃しているなら、それも言う。本当の問題が構造なのに「名前を変えては」で満足しない。

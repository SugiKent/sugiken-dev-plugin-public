# 疑い駆動レビュー

## 役割

このスキルは、結論を急いで承認せず、成立条件・反証・代替案を検討するための**専門的な判断枠組み**である。

開発の順序、レビューの必須性、サブエージェントの起動、外部ツールの利用、コミットやマージの可否は規定しない。それらは利用者または上位の開発フローが決める。

## 使う場面

- 不可逆性が高い判断（公開 API、データ移行、権限、課金、本番設定）
- 型やテストだけでは保証できない性質（冪等性、競合安全性、順序、不変条件）
- モジュール境界・依存関係・抽象化の選択
- 「安全」「スケールする」「仕様に合う」といった根拠を確認したい主張

機械的なリネーム、フォーマット、明白な一行変更には通常不要である。

## 判断の進め方

対象について、必要な範囲で次を整理する。

1. **主張** — 何を正しいと見なすか、なぜ重要か。
2. **契約と前提** — 入出力、不変条件、依存先、失敗時の期待動作。
3. **反証** — 主張が崩れる入力、並行実行、障害、運用条件、仕様解釈を挙げる。
4. **根拠** — コード、仕様、テスト、計測、一次資料のどれが主張を支えるかを分ける。
5. **代替案と結論** — リスクを下げる案、残余リスク、採用する判断を示す。

## 出力

結論は次の形で返す。

```markdown
## 疑い駆動レビュー

### 主張
- …

### 前提・契約
- …

### 反証または未確認点
- …

### 根拠
- …

### 推奨
- …

### 残余リスク
- …
```

反証が見つからない場合も、「確認した範囲」と「未確認の範囲」を分けて記載する。別の視点や外部レビューが有益な場合は、選択肢として提案してよいが、実施を必須化しない。

## 他スキルとの関係

- `35-architect-principle` は構造上のトレードオフを判断する基準を供給する。
- `35-architect-db-design` と `35-architect-security` は、それぞれの専門領域で確認すべき前提を供給する。
- `35-architect-code-review` は依頼された変更の品質を評価する。疑い駆動レビューは、変更前後を問わず判断の根拠を吟味するために使える。

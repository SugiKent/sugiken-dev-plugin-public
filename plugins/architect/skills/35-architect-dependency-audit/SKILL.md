# 依存パッケージの脆弱性監査

## 役割

このスキルは、プロジェクトルート（指定がなければ cwd）を対象に、依存パッケージの既知脆弱性を検出し、対応要否を分けて報告する。脆弱性の検出そのものは audit ツールに任せ、LLM は検出結果のトリアージだけを担う。脆弱性を推測で報告しない。

修正の実施、依存の更新、コミットは規定しない。報告を受けた利用者が判断する。

## 対象エコシステム（初版）

lockfile からエコシステムを検出する。

| lockfile | パッケージマネージャ | audit コマンド |
|---|---|---|
| `package-lock.json` | npm | `npm audit --json` |
| `pnpm-lock.yaml` | pnpm | `pnpm audit --json` |
| `yarn.lock` | yarn | `yarn npm audit --json`（yarn berry）または `yarn audit --json`（yarn classic） |

複数の lockfile が見つかった場合は、実際にインストールに使われているものを利用者に確認する。上記以外のエコシステム（pip, bundler 等）は初版の対象外であり、検出したら「未対応のエコシステムです」と報告して終える。

## 手順

1. **エコシステムを検出する。** プロジェクトルート直下の lockfile を確認する。
2. **audit を実行する。** 対応する audit コマンドを `--json` 付きで実行し、生の検出結果を得る。コマンドが失敗した場合（ネットワーク不通、認証エラー等）は結果を捏造せず、失敗の内容をそのまま報告する。
3. **トリアージする。** 検出された各脆弱性を `35-architect-security` の「npm audit の結果のトリアージ」判断ツリーに通す。深刻度（critical/high/moderate/low）、ランタイム依存か dev 専用か、修正版の有無で分岐し、次を確認する。
   - その脆弱な関数は実際にこのプロジェクトのコードパスから呼ばれているか（`package.json` の依存関係と実際の import を突き合わせる）
   - 修正版へのアップデートが破壊的変更（メジャーバージョン変更）を伴うか
4. **報告を組み立てる。** 「対応要否」で仕分けた表を作る。

## 出力

```markdown
## 依存監査結果

### 対象
- エコシステム: …（lockfile / audit コマンド）
- 検出件数: critical N / high N / moderate N / low N

### 即対応
| パッケージ | 深刻度 | 脆弱性 | 理由 | 対応 |
|---|---|---|---|---|

### 次の依存更新で
| パッケージ | 深刻度 | 脆弱性 | 理由 |
|---|---|---|---|

### 見送り（理由付き）
| パッケージ | 深刻度 | 脆弱性 | 見送り理由 |
|---|---|---|---|

### 未確認事項
- …
```

ファイルへの出力（レポートの保存）は要求されたときだけ行う。デフォルトは対話出力のみ。

## スコープ外（初版では入れない）

- SBOM 生成
- ライセンスチェック
- CI への組み込み
- npm 系（npm/pnpm/yarn）以外のエコシステム（pip, bundler 等）— 必要になった時点で足す

## 他スキルとの関係

- `35-architect-security` — トリアージの判断ツリーとサプライチェーン衛生の記述の正本。本スキルはそれを実行フェーズで適用する側であり、判断基準を複製しない。
- `35-architect-code-review` — 依存の脆弱性はコードレビューの「セキュリティ」観点の一部として触れられることがあるが、実際に audit を走らせて棚卸しする役割は本スキルが担う。

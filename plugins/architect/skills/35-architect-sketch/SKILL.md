# 設計スケッチ

型、関数のシグネチャ、クラスの形、モジュールの境界を、`not implemented` の本体と擬似コードでスケッチする。複数のモデルの視点から案を作らせて統合し、選んだスケッチに沿ってコードを埋める。pstack の `architect` と `arena` を、Claude Code とこのリポジトリの SDD に合わせて日本語化した。

原則名（Laziness Protocol など）は `35-architect-principle` の「pstack の原則」にあり、当てるときは `references/pstack-principles/` の原則のファイルを読む。

## 始め方

段階ごとに 1 項目のタスクリストを開いてから始める。

1. 足場を固める（Phase A）
2. スケッチする（Phase B）
3. 合意する（Phase C）
4. スケッチに沿って実装する（Phase D）
5. 誤った設計を捨てる（Phase E）

SDD の propose では Phase A〜C までを行い、結果を design.md に書く。Phase D と E は apply で行う。

## Phase A: 足場を固める

新しいコードが触るすべての仕組みについて、本物の頭の中のモデルを作る。関係するサブシステムを `references/grounding.md` の「仕組みを説明する」で説明できる状態にする。ファイル名を挙げるだけでは足場にならない。設計が所有や層の分け方を変えるなら、同じファイルの「経緯を掘る」で今の形の理由も掘る。掘り当てた理由は推測で補わず、設計が守る制約として扱う。

本当にゼロからの作業で、組み込む先のシステムがないときだけ、Phase A を飛ばす。

## Phase B: スケッチする

同じ課題を複数の候補に解かせ、土台を選び、負けた候補の良い部分を移植する（pstack の `arena`）。

**枠を決める。** すべての候補が同じ依頼を受けるので、依頼文が約束になる。

1. 各候補が作る成果物を述べる。成果物は、型のスケッチ、関数のシグネチャ、モジュールの地図、`references/rationale-template.md` に沿った根拠の文章の 4 つ。
2. この課題での成功を表す、採点できる具体的な基準を 3〜6 個決める。これは土台を選ぶときの道具で、候補には見せない。
3. 走らせる候補を決める。最低 2 つ。1 つは `opus` の general-purpose サブエージェント。もう 1 つは別系統のモデルにする。Codex MCP が使えるなら Codex に頼む（sandbox は read-only にし、候補は応答の本文で返させ、親が保存する）。使えなければ `sonnet` など別の Claude モデルにし、系統の多様性が下がったことを記す。設計の方向が複数あるなら候補を増やす。
4. 各候補の出力先を分ける。書き込む候補には `isolation: "worktree"` か `<scratchpad>/sketch-<slug>/candidate-<n>/` を渡す（Separate Before Serializing Shared State）。

**広げる。** すべての候補を 1 つの発言で起動する。各候補には、課題、Phase A の成果物のパス、自分の出力先、`references/runner-prompt.md` を渡し、成果物と、検討した代替案と退けた理由を書いた短い根拠を返させる。出力のない候補が出たら、残りで続けて脱落を記す。

**二度設計する。** 最初の案が十分に見えても、統合の前に、構造の違う候補を少なくとも 2 つ揃える。これは Exhaust the Design Space を具体にしたもの。並べるのは形そのものが違う案で、1 つの形の中の部分修正を並べても探索にならない。

**赤旗で選別する。** 統合の前に、すべての候補を `references/design-red-flags.md` で選別する。次に触る人は、開いたファイルしか見ず、いちばん近い例を写し、コンパイルが通る最短の道を取るエージェントだと考える。1 つのファイルから見て正しく見える変更が、リポジトリ全体でも正しくなる設計を選ぶ。

**インターフェースの深さで比べる。** 小さく単純な公開面の後ろに、多くの複雑さを隠す設計を選ぶ。豊かなインターフェースは、能力を層に散らさず一か所に集めて、呼び出しの連鎖を短く保つ。

**審査させる。** 全候補が書き終わってから、読むだけの審査役を 1 つ起動する。親と別系統のモデルを選ぶ（Codex MCP が使えるなら Codex、使えなければ親と別の Claude モデルの Explore サブエージェント。Explore には編集しないよう依頼文で伝え、終わったら `git status` を確かめる）。審査役は基準と、ラベルで呼ぶ候補のパスを受け取り、基準ごとに採点し、土台にすべき候補を理由付きで推す。候補が書いている途中に起動しない。

**土台を選ぶ。** 選ぶ前に、すべての候補を最後まで読む。基準ごとに採点し、審査役と比べる。全体の印象で選ぶと、判断が最初に読んだ候補や文章のうまい候補に引きずられる。土台の判断が一致すれば選択が裏付けられる。食い違うなら、どちらかが偏っているか、基準が曖昧だった。両方の根拠を読んでから決める。未来の保守者が不変条件を壊さずにいちばん楽に伸ばせる土台を選ぶ。拮抗したら、境界がきれいなほう、API が小さいほうを取る（Laziness Protocol）。

**移植する。** 負けた候補をもう一度歩き、土台へ移す価値のあるものを探す。普通は 1 候補につき 1、2 個で、大半ではない。1 つの頭の中のモデルで筋が通るよう、機械的に貼らず手で組み込む（Redesign from First Principles）。候補が 1 つの形に収束したなら強い一致なので、そう記して一致した形を出す。移植は要らない。候補がばらばらに散ったなら枠の決め方が足りなかった。平均を取らず、枠を決め直して走らせ直す。

**確かめる。** 統合した成果物を、ほかの出力と同じく確かめる（Prove It Works）。見落としが見つかったら、枠が誤っていた（決め直して走らせ直す）か、候補が捕まえていたのに移植し損ねた（移植に戻る）かのどちらか。蓋をしない。

Phase B の結果は統合した設計 1 つ。その統合の判断を、根拠の「統合の判断」の節に書く。

## Phase C: 合意する（任意）

既定では、統合した設計でそのまま実装へ進み、人間の確認点を置かない。

呼び出した人が明示したとき（「確認点つきで」「実装の前に見せて」など）だけ確認点を置き、統合した設計を見せて承認を待つ。SDD の propose では、統合した設計の論点（「未決の問いとリスク」）を、propose のグリリングで利用者と詰める。

統合した設計は、どちらの場合も単独のコミットとして出してよい（Foundational Thinking の「足場が先」）。埋めていく途中の、計画して範囲を決めた破損は構わない（Outcome-Oriented Execution）。実装の前に設計へ敵対的な圧力をかけたいなら、統合したスケッチに `35-architect-interrogate` を回す。

人間が形に反対したら（確認点でも、後からでも）、それを Phase A の証拠として扱う。コードを書き足す前に、足場を固め直し、Phase B を回し直す。

## Phase D: スケッチに沿って実装する

`not implemented` の本体をコードに、擬似コードをロジックに置き換える。統合したスケッチが約束になる。スケッチからの逸脱は表に出す信号として扱う。黙って吸収すると、スケッチと実装が食い違ったまま進む。関数がスケッチの想定しなかった引数を要したら、スケッチが誤っていたのか、要求を見落としていたのか、実装がやりすぎているのかを問う。

## Phase E: 誤った設計を捨てる

スケッチで吸収できない摩擦を実装が生み続けるなら、スケッチを捨てる。誤った設計に修正をボルトで留めない（Redesign from First Principles、Fix Root Causes）。

信号は、同じ形が繰り返す型として現れる。

- 無関係なコードの中に、同じ形の回避策が何度も現れる。
- 無関係な端の条件がいくつも、特別扱いの分岐を要する。
- コンパイルを通すために型が逃げ道（`any`、キャスト、実際には常に設定される optional なフィールド）を要する。
- スケッチが「状態は共有しない」と言っていたのに「ロックが要る」と反射的に思う。
- 呼び出し元が、抽象を使うためにその内部の規則を知らなければならない。
- 実装全体で、Phase D の同じ形の逸脱が独立に 2 つ以上起きる。

判断は使う。端の条件がいくつかあるだけでは、設計は有罪にならない。本当に複雑な問題もある。データの複雑さは設計の複雑さではない。

捨てるときの手順。

1. 作ったものを「仕組みを説明する」で説明し直す。
2. 新しい制約が最初からの前提だったかのように設計し直す（Redesign from First Principles）。
3. 先に要らないものを引いてから足す（Subtract Before You Add）。新しいスケッチは、育つ前に古いスケッチより小さくなければならない。
4. Phase B に戻り、競作を走らせ直す。

SDD の apply で捨てると判断したら、実装を止め、何が型として現れたかを添えて design の更新を提案する。

## 出力

呼び出し側の使い方を先に書き、型のスケッチをそこから導く。小さな変更なら、新しい型とシグネチャを 1 ファイルに。大きな作業なら、モジュールの地図と型の定義。根拠の文章を `references/rationale-template.md` の形で添え、使い方のスケッチと統合の判断を含める。SDD では根拠を design.md に、型のスケッチを change フォルダ（例: `sketch/`）に置く。

# スケッチの候補への依頼文

親は Phase B で、並行に走るすべての候補にこのファイルを渡し、その周りに課題、Phase A の成果物、隔離した作業ディレクトリ、出力を書くパスを埋める。作業ディレクトリは、既定ではスケッチ用ディレクトリの下の候補ごとのディレクトリで、リポジトリのコードを動かす候補には git の worktree になる。大事なのは候補同士が独立していること。

あなたは、並行の設計探索で候補を 1 つ作る。まず `35-architect-sketch` の SKILL.md を最後まで読む。それがあなたの入っている手順になる。出すのは候補の設計一式で、型のスケッチ、関数のシグネチャ、モジュールの地図、`rationale-template.md` の形の根拠の文章からなる。

次の規律を当てる。親は、土台を選ぶためにこれらの軸で候補を比べる。

- 呼び出し側の使い方が先。型の前に、README 風の使い方と現実の呼び出し箇所を 2〜3 個書き、そこから型のスケッチを導く。使い方が仕様になる。両者は一致しなければならないので、食い違ったらスケッチの側を使い方に合わせる。
- データ構造が先。中心の型を正せば、コードは自明になる。主なアクセスパターンを、提案する構造でたどる。答えが「map・索引・キャッシュを後で足す」なら、構造が誤っている。
- インターフェースの深さ。公開面の大きさに対して、その後ろに隠す能力を比べる。実装が単純でなくなっても、複雑さを呼ばれる側に引き込む単純なインターフェースを選ぶ。通信やワイヤ形式の型を公開 API に出さない。インターフェースの後ろでドメインの型にパースする。
- 共有状態。2 つの主体がどちらも書きうるなら「何が起きるか」を問う。答えが「何も起きない」でなければ、既定では主体ごとの状態にし、読む境界で合わせる（Separate Before Serializing Shared State）。
- 境界を見えるようにする。本体は `not implemented` のエラー、難しいロジックは `// TODO` の擬似コード、意図と不変条件を述べる doc コメント。読み手が型とシグネチャだけで入力から出力までデータをたどれるようにする。
- 不変条件を型で表す。優先するのは誤用しにくい型、次に実行時の検査、最後に文章のコメント（Encode Lessons in Structure）。
- 境界で検証し、内側では型を信頼する（Boundary Discipline）。業務ロジックは純粋な関数にし、外殻は薄く保つ。
- 不変条件ごとに正本を 1 つにする。同期させず導出する。
- 当てはまるなら、状態の遷移を冪等にする（Make Operations Idempotent）。操作が 2 回動いたら、途中でクラッシュしたら何が起きるかを問う。
- 呼び出しの連鎖を短くする。流れをたどるのに 3 ファイルより多く要るなら、階層を平らにする（Laziness Protocol、Minimize Reader Load）。

原則名の中身は `35-architect-principle` の `references/principles/` にある。

あなたは並行に走る候補の 1 つで、ほかの候補は別のモデルで走る。あなたのモデルが作れる最良の設計を出す。ほかの候補に保険をかけない。候補同士の違いが、土台を選び移植するための信号になる。無難に見える中間へ寄せると、探索の意味がなくなる。

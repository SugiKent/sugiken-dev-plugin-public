# 足場を固める（仕組みと経緯の調べ方）

`35-architect-sketch` の Phase A と、`openspec-apply-change` のバグ修正・リファクタリングの task が、触る仕組みを掴むときに使う。どちらもコードを変えない。

## 仕組みを説明する

サブシステムに入る上級エンジニアが、動く頭の中のモデルを組める程度に説明する。注釈付きのソースコードのように細かくしない。

範囲が曖昧なら、自分の解釈を述べて調べる。人間は後から向きを変えられる。

1. **複雑さを見積もる。**
   - **単純**（1 つのモジュール、小さなユーティリティ、「関数 X はどう動くか」のような狭い問い）。自分で読んで、手順 4 の形で説明する。
   - **複雑**（複数のファイルやサービスにまたがるサブシステム、横断的な機能、アーキテクチャ全体の概観）。手順 2 へ進む。迷ったら単純な道を取る。
2. **並行に探る（複雑なときだけ）。** 問いを 2〜4 の切り口（サブシステムの別々の断面）に分け、切り口ごとに Explore サブエージェントを 1 つの発言でまとめて起動する。各サブエージェントには、ファイルの場所、主要な型とシグネチャ、実行時の流れ、自明でない点を、`file:line` の出典付きで返させる。ソースの中身は貼らせない。
3. **まとめる（複雑なときだけ）。** 全員の報告が揃ったら、1 つの説明に統合する。サブエージェントの報告をそのまま並べない。
4. **説明する。** 次の節で書き、当てはまらない節は落とす。
   - **概要。** これは何で、何のためにあるか。
   - **主要な概念。** 読み手が持つべき型・用語・不変条件。
   - **動き方。** 入力から出力まで、実行時に何が起きるか。
   - **置き場所。** どのファイル・モジュールが何を持つか。
   - **落とし穴。** 自明でない挙動、触ると壊れやすい点。

## 経緯を掘る

今の形がなぜそうなっているかを調べる。設計が所有や層の分け方を変えるとき、退行の原因を探すときに使う。

- まず source control から掘る。`git log -L`、`git blame`、関係するコミットと PR の本文を読む。
- MCP で課題管理・長文の docs・チャット・監視の記録に届くなら、それも引く。届かない情報源は、調べていないと書く。
- 直接の証拠と推測を分けて書く。記録が薄いなら「〜のように見える」と書く。誰も理由を書き残していないことも、それ自体が答えになるので報告する。

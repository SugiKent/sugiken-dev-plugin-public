# 根拠の雛形

型のスケッチに添えて出す文章。1 ページに収める。見出しは文の形にし、決まり文句を入れない。斜体の注記を実際の内容に置き換える。SDD では design.md の該当する節に書く。

## 問題

*1 段落。何をしようとしているか、既存のシステムや制約の何のせいで形が自明にならないか。Phase A で、設計が守るべき制約（相互に動く既存の型、壊せない呼び出し元、境界をまたいだ不変条件）が見つかったなら、ここで名指しし、読み手が同じ制約を見られるようにする。*

## 使い方（呼び出し側から見て）

*型のスケッチより先に書く。利用者が読む README かクイックスタートと、利用者自身のコードでの現実的な呼び出し箇所を 2〜3 個示す。何を import し、何を呼び、何が返るか。「形」の節の型のスケッチは、ここから導く。両者は一致しなければならない。食い違ったら、スケッチの側を使い方に合わせる。呼び出し側の体験が仕様で、型はそれに仕える。*

## 形

*推す構造。データ構造を先に書く。次に、データがシグネチャをどう流れるか。重荷を負う判断を名指しする。どの不変条件を型で表すか、検証をどこに置くか、システムが意図してしないことは何かを書く。インターフェースの深さをはっきり判断する。公開面が何の複雑さを隠し、何を呼び出し元にさらしたままにし、なぜインターフェースが必要以上に大きくないかを書く。各判断の裏の原則を挙げる（例: `Boundary Discipline に従う`）。原則の中身は書き写さない。*

## 統合の判断

*Phase B で書く。どの候補を土台にしたかとその理由、ほかの各候補から何を取り込んだか、何をなぜ退けたか。*

## 受け入れたトレードオフ

*選んだ形が行うトレードオフを 1 つ 1 行で。形は「Y と引き換えに X を受け入れる」。未来の読み手が見落としと取り違えそうなものは名指しする。早すぎる最適化や早すぎる単純化に見えるものも含める。*

## 検討した代替案

*必須。具体的な別の形を少なくとも 1 つ挙げ、負けた理由を 1 行で書く。各代替案は、実装の単純さに加えてインターフェースの深さで判断する。それが呼び出し元にさらす複雑さと、隠す複雑さを名指しする。設計空間に本物の対抗馬があったなら 2〜3 個挙げる。制約が答えを決めたなら 1 つでよく、結論を「この形しか成り立たなかった。理由は…」と書く。同じ形の色違いを並べない。この節は、選んだ形が検討して退けた設計の代替案を書く場所で、ほかの候補の一覧ではない。*

## 未決の問いとリスク

*スケッチの間に気付いた、人間が判断すべき点と、実装を始める前に知らせるべきリスク。人間の答えがそのまま解決になるよう、問いの形で書く。*

## 次の実装の一歩

*スケッチに沿って最初に作るもの。1 文。統合の直後（確認点を置いたなら承認の後）にすぐ書き始めるもの。*

# テスト監査

3 つのモードで、1 つの価値基準を共有する。

* **作成モード**: 新規・変更テストを書く時点で「作成ゲート」を通す。
* **監査モード**: ソースを再表明するテスト、より強い証明と重複するテスト、振る舞いを実装に結合させるテスト、テスト専用の本番の継ぎ目を延命させるテストを、範囲を絞って一掃する。広い監査は、まとまりのある後続 PR に分けて続ける。削除件数ではなく、確信度を最大化する。
* **キャンペーンモード**: 1 つのサブシステム（1 つのモジュール・パッケージ・サービス・プラグインなど、所有境界 1 つ）が持つテストファイルをすべて棚卸しして刈り込む。始める人だけが、着手前に [references/campaign.md](references/campaign.md) を読む。

## 作成ゲート

テストを追加する前に、次の 4 問に答える。答えられない問いがあれば、まだ追加しない。

1. どの観測可能な振る舞い、不変条件、独立した契約を守るのか。
2. どんな現実的なリグレッションで失敗するのか。
3. なぜ既存のカバレッジではその失敗を捕まえられないのか。各契約には、最も強い境界に主担当のテストが 1 つある。別のレイヤーでもテストするなら、主担当が届かない固有のリスク（通信やライフサイクルの失敗など）が要る。ほぼ同じテストを足すより、テーブル駆動のケースや共有フィクスチャを拡張する。重複したセットアップは同じ変更で統合する。
4. 本番の呼び出し元が必要としない本番の継ぎ目（export、フラグ、ラッパー、注入フック）を要求するか。要求するなら、テストを実際の境界へ移す。

次に、テストを「ジャンクパターン」の各項目と照らし合わせる。1 つでも該当すればゲート不合格とする。ただし「残す基準」に照らして、そのテストが独立に守っている契約を名指しできる場合は通す。振る舞いを変えないリファクタリングで壊れるテストは、振る舞いではなく実装を検証している。追加する前に、所有境界で書き直す。

バグのリグレッションテストは、修正前のコードで意図した理由により失敗し、所有境界での修正後に成功しなければならない。失敗を実際に確認していないリグレッションテストは、修正ではなくモックを証明している。バグ 1 件につき、所有境界のリグレッションテスト 1 つで足りる。バグが通過するすべてのレイヤーで同じシナリオを再生しない。

## ジャンクパターン

作成ゲートと監査の共通チェックリスト。作成ゲートは該当する新規テストを却下し、監査は該当する既存テストを探す。

* アサーションのないカバレッジ稼ぎ
* 自分自身との比較、値をそのまま写すだけの恒等コピー
* フィクスチャ・一覧・マニフェスト・export 一覧の写し
* ソース・import・文字列の完全一致 grep
* 実際の境界で検証済みの内容を、private な述語や呼び出し形で重ねて検証するテスト
* 同じ契約の重複呼び出し
* 共有ヘルパーを、利用側ごとに再生するテスト
* テスト専用の export・グローバル・ラッパーを残すことだけが目的のテスト
* テストからしか呼ばれていない、使われていない本番コード
* テスト対象のヘルパーやレンダラー自身が生成した期待値
* 検証対象の振る舞いをモックが実装しているもの、異なる API を 1 つの同一モックで代用しているもの
* 本来は所有者が生成すべき受領記録・受付結果・コールバック順序をフィクスチャが与えているもの、処理経路が書き込まないストアに対して永続化を検証しているもの
* 宣言されたフラグを言い直すだけで、フラグが約束する配送や応答を実行しない機能テスト
* 無関係な理由で成功する否定側の対照テスト（別のガードによる拒否、本番経路が到達しない拒否など）
* 入力が実際に行う以上のことを約束する名前・フィクスチャ（例: 「ウィンドウを閉じる」という名前で、ウィンドウが閉じられていないことを検証しているテスト）

## 価値基準

テストは、振る舞い、現実的なリグレッション、独立して意味のある契約のいずれかを守ることで、保守コストに見合う。監査において、振る舞いを変えないソースの再編で変更が必要になる既存テストは「疑わしい」のであって、自動的に削除してよいわけではない。新規テストは作成ゲートで却下する。

候補を判定する前に、テストの全文と本番の所有コード、そのエントリーポイント、呼び出し元、呼び出し先、兄弟実装、重なるテスト、CI でのテストの振り分け、関連する履歴を読む。最初に、リポジトリのルートと対象ディレクトリにあるエージェント規約ファイル（`AGENTS.md`、`CLAUDE.md` など）を読む。テストが依存ライブラリの振る舞いを前提にしている場合は、依存先のソースや型を直接確認する。

## 探索

探索は読み取り専用で行い、編集前に証拠を報告する。範囲が広い場合は、使えるなら並列の探索レーンを走らせる。レーンは対象システムの構成を見て決める。典型的な分け方は次のとおり。

* コアと共有ライブラリ
* プラグイン・拡張・機能モジュール
* UI、アプリ、スクリプト、ツール類
* 横断的なパターンの一掃

キャンペーンモード以外では、大量の推測的な一覧より、確信度の高い少数の候補を優先する。探すのは「ジャンクパターン」に該当するテスト。

## 残す基準

テストが次のいずれかの契約を独立に守っているなら残す: 公開 API、外部向け SDK・拡張ポイント、プロトコル、設定、マイグレーション、ストレージ、セキュリティ、プラットフォーム、デフォルト値、バイト単位で固定された出力（プロンプト、シリアライズ形式など）、言語をまたぐ生成物、パッケージ、リリース、アーキテクチャ。加えて次も残す。

* 順序が観測可能な振る舞いであるときの呼び出し順序
* 現実的な失敗モードを持つリグレッション
* ソース検査が最も安い独立したガードである場合。契約（ユーザーに見えるキー、バイト、パス）が変わると失敗し、識別子だけのリファクタリングでは壊れないもの
* ベースラインで失敗している残すべきテスト。製品のバグの可能性として扱い、再現し、テストを消さずに所有コードを直す

静的であること、遅いことは削除理由にならない。実装に似たテストも独立した契約である可能性がある。削除する前に、そうでないことを証明する。

## 候補の証拠

編集する前に、候補ごとに次の項目をすべて記録する。欠けている項目がある候補は、削除できる状態にない。

* テストの正確な名前と場所
* そのテストが実際に検出できる失敗
* カバー対象の本番コードやテスト支援の継ぎ目の、テスト以外の呼び出し元
* 所有境界に残る、より強い証明。または証明が不要な理由
* 関連する履歴と、テストや継ぎ目が存在する理由
* 削除によって消せる本番コード・テスト支援コード
* リスクと、範囲を絞った検証コマンド

## 編集の形

所有境界ごとに、まとまりのあるバッチを 1 つ選ぶ。使われなくなったテスト専用の export・グローバル・ラッパー・本番の死んだ経路は、エイリアスで残さず削除する。残すリグレッションテストは、正式な所有者のテストへ移す。パッケージや依存関係についての繰り返しのアサーションは、1 つの汎用的な契約に統合する。

本番コードの行数が純減する変更を優先する。同じ実装を言い直す代替テストを足さない。削除件数を増やすために、確信の持てない候補を掃除に回さない。

## 検証

テストランナーがチェックアウト上で実行中のときは、ソースもテストも編集しない。実行中のプロセスが編集途中のファイルを読み、結果が信用できなくなるため。対象リポジトリにテスト規約や重いテストの実行手順があれば従う。

実行コマンドは、`package.json` などのマニフェスト、タスクランナーの定義、CI 設定、エージェント規約ファイルを読んで特定する。

1. 所有者と兄弟の最小単位のテストを、パスやフィルタを指定して実行する。
2. ソース grep や計画に対するアサーションを削除した場合は、実際の契約を持つ実行スクリプトやドライランを実行する。
3. 変更ファイルに対象を絞ってフォーマッタを実行し、`git diff --check` を実行する。
4. 変更パスに応じて必要な検証を決める仕組み（変更ファイル単位のゲート、影響範囲の判定スクリプトなど）があれば、それで分類してから、リポジトリの方針が求めるゲートを実行する。なければ、変更したパッケージ・モジュールのテスト、lint、型チェックを実行する。
5. `git diff --numstat` を確認し、本番コード・ツール類と、テスト・テスト支援コードを分けて報告する。
6. 監査の最後の編集の後、リポジトリで定められたコードレビュー手順を実行する。なければ `35-architect-code-review` でレビューする。

## 取り込みと継続

commit、push、PR 作成、マージは、許可されたときだけ行う。リポジトリに PR の作成・マージ手順があれば従う。まとまりのある PR を 1 本ずつ取り込む。取り込み後は最新のデフォルトブランチから始め直し、次の確信度の高いバッチのために読み取り専用の探索をやり直す。

## 報告

次を報告する。

* 根本原因と、削除した低価値テストの分類
* 本番の所有コードの簡素化
* 残した偽陽性と、それが価値を持ち続ける理由
* 実際に実行した、範囲を絞った証明と全体の証明
* 本番コードとテストの行数
* PR とマージの状態
* 名前を付けた後続作業

# マーケティング現状分析スキル

「マーケティングを考えたい」という依頼に一般論（SNS を運用しましょう、ASO を見直しましょう）で答えず、**リポジトリを一次情報として証拠ベースで現状分析し、打ち手を優先順位付きで出す**スキル。

マーケティングの問題の多くはリポジトリ内に証拠として残っている。特に個人開発では、実装が先行して外向きの文言が置き去りになるドリフトが頻繁に起きる。これは推測ではなく差分として確定できる。

## 責務の境界

| やること | やらないこと |
|---|---|
| 現状分析・ドリフト検出・打ち手の優先順位付け | ストア文言の書き換え → 別スキル（プロジェクトに存在すれば、そちらへ引き継ぐ） |
| 一次情報（コード・ストア資産・仕様変更履歴）からの機械的な事実収集 | プロダクト分析ツール上での深掘り分析（本スキルは所在の切り分けまで） |

書き換えを担うスキルがプロジェクトに存在する場合は、Step 7 の施策表を渡してそちらに引き継ぐ。存在しない場合は施策表の提示までで完了とする。

`plugins/analytics/` は分析手法そのもののスキル群であり、本スキルはマーケ観点での現状把握なのでレイヤーが異なる。深掘り分析が必要になったらそちらに引き継ぐ。

## Step 0: 目的を先に確定させる

**分析を始める前に** `AskUserQuestion` で、獲得（新規 DL）／定着（継続率）／収益化のどれを動かしたいかを確定させる。この 3 つは打ち手が完全に別物になるため、目的を決めずに進めると一般論に戻ってしまう。

このとき、収益化の受け皿（課金実装）が無いのに獲得だけ増やす、といった構造的な矛盾が Step 1 の調査でわかっていれば、選択肢の説明に添えて提示する。

## Step 1: プロダクトの現在地を一次情報から取る

推測せず、リポジトリから機械的に取得する。パスはプロジェクトに合わせて読み替える。

```bash
# 開発期間・現在のバージョン
git log --diff-filter=A --format='%ad' --date=short -- app.json | tail -1
grep -E '"version"' app.json 2>/dev/null || grep -E '"version"' package.json

# 認証方式（登録障壁の有無は獲得ファネルに直結する）
grep -rli "signin\|signup\|auth" --include="*.ts*" src app 2>/dev/null | head -20

# 計測基盤の導入有無とイベント設計の粒度
grep -rl "amplitude\|analytics\|track(" --include="*.ts*" src app 2>/dev/null | head -20

# 収益化の実装有無（課金・サブスク・アフィリエイト）
grep -rli "purchase\|subscription\|iap\|stripe\|revenuecat" --include="*.ts*" src app 2>/dev/null | head -20
```

各項目を「あり／なし／不明」で確定させる。不明なまま Step 7 に進まない。

## Step 2: マーケ資産を棚卸しする

- ストアメタデータ一式（名称／サブタイトル／キーワード／説明文／リリースノート）
- スクリーンショット・アイコン等の画像資産
- LP の URL 設定、サポート導線
- SNS 導線、シェア機能とその拡散先設計

**「空欄になっている項目」自体が発見になる**。設定ファイルの空文字列は、意図的な未実施ではなく単なる漏れであることが多い。棚卸し表に「空欄」も明示的に記載する。

## Step 3: ドリフトを差分として検出する（★このスキルの核）

仕様の変更履歴（`PROJECT.md` の変更履歴、`openspec/`、`git log`）と、外向きの文言を突き合わせ、次の 2 方向のズレを検出する。

| 方向 | 内容 | リスク |
|---|---|---|
| 訴求 → 実装が無い | 廃止・変更した機能が外向き文言に残存 | 期待外れによる初日離脱、低評価レビュー、表示の正確性の問題 |
| 実装 → 訴求が無い | 実装済みの主要機能が文言・検索語に未収載 | 作った資産をそのまま捨てている |

```bash
# archive 済み capability = 実装済みと見なせる（openspec 採用プロジェクトの場合）
ls openspec/specs/ 2>/dev/null

# 未 archive の change は「まだ出荷されていない」候補
ls openspec/changes/ 2>/dev/null | grep -v '^archive$'
```

検出結果は次の表で提示する（これが本スキルの成果物の核）。

| 機能 / 記述 | 実装 | 外向き文言 | 判定 |
|---|---|---|---|
| 例: 機能 A | あり | 記載なし | **訴求漏れ → 追記候補** |
| 例: 「◯◯ができます」 | 実装なし | 記載あり | **虚偽表示 → 削除候補（最優先）** |

**これは意見ではなく差分**なので、指摘に反論の余地がなく、修正の合意が速い。

## Step 4: 資産の「系統」を分けて健全性を見る（★見立てを誤りやすい箇所）

外向き資産は**画像系統とテキスト系統で別々に腐る**。片方だけ更新されて、もう片方が放置される事故が実際に起きる。

- **ファイル名・キャプション定義ファイル・メタデータだけで判断してはいけない**
- **画像は必ず実物を Read ツールで開いて内容を確認する**（テキスト側の記述だけから「画像も古いはず」と推測しない）

テキストと画像それぞれについて、最終更新日・突き合わせ結果を分けて報告する。

## Step 5: 枠の使用率を定量化する

各テキスト枠について「現在の文字数 / 上限 / 空き」を表にする。これにより **「順位への寄与が大きい一等地が空いている」が機械的に検出できる**。

```bash
check() { printf '%-40s %5s / %s\n' "$1" "$(tr -d '\n' < "$1" | wc -m | tr -d ' ')" "$2"; }
# 例（フィールド名・上限はストアの規約に合わせる）
```

併せて、枠をまたいだ重複（上位の枠に既出の語を、下位の枠に再登録している等）による空費も検出する。

## Step 6: 数値の所在を切り分ける

- プロダクト分析ツール（Amplitude 等）が持つのは**アプリ起動後**の行動データ
- 獲得ファネルの前段（表示回数 → インストール転換率）は**ストアコンソール側にしかない**

この境界を明示せずに「データを見ます」と言うと、目的に対して答えの出ないデータを掘ることになる。**目的が獲得なら、行動データは「増やした先の受け皿が機能しているか」の検証に使う**、と役割を定義してから触れる。

## Step 7: 打ち手をコストと効果の表で出す

| 優先 | 施策 | 想定コスト | 効く理由 |
|---|---|---|---|

特に **「コード変更ゼロで反映できるもの」を最優先に置く**。個人開発では実装コストが最大の律速になるため、設定ファイルの更新だけで動くものの費用対効果が突出して高い。

Step 0 で確定した目的（獲得／定着／収益化）に対して効かない施策は表に含めない。

## 完了条件

Step 3 のドリフト表と Step 7 の施策表を user に提示したら完了。ストア文言そのものの書き換えは行わず、書き換えを担うスキルがプロジェクトにあればそちらへ引き継ぐ。
